# 双系统合并分析（BPI-R4 × 2 套系统）

日期：2026-11-02  
分析对象：
- 我方：开发板 192.168.240.1（在线，可直接 SSH）+ 仓库 `bpi-r4-wireless-tuning`
- 对方：`D:\Desktop\sdcard.img.gz`（另一位同学的 SD 卡整盘镜像）

---

## 0. 一句话结论

`sdcard.img.gz` 是**另一位同学（构建主机 `sean@LZD-20250922YZS`）的 BPI-R4 SD 卡整盘镜像**：

| 项 | 对方 | 我方 |
|---|---|---|
| OpenWrt | 24.10-SNAPSHOT `r29251-a1ea57bd05` | 24.10.0 `r28427-6df0e3d02a` |
| 内核 | **6.6.151** | **6.6.73** |
| rootfs | 精简版，**无 LuCI**（1169 文件） | 完整版，带 LuCI（1475 文件） |
| LAN | 192.168.7.1 | 192.168.240.1 + 192.168.1.1 |
| SSID | `interruption` | `BPI-R4-5G` / `BPI-R4` |
| mac80211 补丁 | `wifi_dscp` tracepoint（DSCP 统计） | WDRR 调度器（`fq_weight`） |
| mt7996e 补丁 | EDCA（**与我们的二进制完全相同**） | EDCA / A-MPDU / MCS / txrate 多套 |
| 其它 | `dscpstats` + `dscpstats.awk` | `oaf.ko`、L2 视频、VIP、failover |

**核心矛盾：两边内核基线不同（6.6.73 vs 6.6.151），预编译 `.ko` 不能互换。**
但两边打的都是**同一个 mac80211 backports-6.12.6 源码树**，所以补丁本身是可以合并的，只是需要重编。

## 1. 镜像解剖（实测证据）

### 1.1 总体

```text
sdcard.img.gz        51,848,282 B
解压后 sdcard.img     7,935,623,168 B  (7.39 GiB)
```

GPT 分区（主表有效、备份表损坏，属正常 dd 产物）：

| 分区 | 名称 | 起止扇区 | 大小 | 内容 |
|---|---|---|---|---|
| p1 | bl2 | 34–8191 | 4 M | `SDMMC_BOOT` 头，BL2 |
| p2 | ubootenv | 8192–9215 | 512 K | U-Boot 环境文本 |
| p3 | factory | 9216–13311 | 2 M | 空 |
| p4 | fip | 13312–21503 | 4 M | FIP（TF-A） |
| p5 | recovery | 24576–90111 | 32 M | OpenWrt FIT（recovery） |
| p6 | install | 90112–131071 | 20 M | `SPINAND!` 安装镜像 |
| p7 | production | 131072–1048575 | 448 M | **生产 FIT + F2FS overlay** |

### 1.2 production 分区 = 真正的系统

偏移 `0x4000000`（=67,108,864）起是一个 OpenWrt FIT：

```text
kernel-1                       6,285,134 B   ARM64 OpenWrt Linux-6.6.151 (gzip)
fdt-1                             47,638 B   bananapi_bpi-r4 基础 DTB
fdt-...-emmc                       1,546 B
fdt-...-rtc                          285 B   ← 只把 pcf8563 置 okay，上游自带
fdt-...-sd                         1,474 B
fdt-...-wifi-mt7996a               2,289 B
rootfs-1                      11,071,488 B   squashfs (xz)，即 OpenWrt rootfs
```

- squashfs 头在 `0x4610000`，`bytes_used = 0xA8E7B0`，实际结束于 `0x509E7B0`。
- **F2FS overlay（fitrw）紧接其后**：superblock 在 `0x509F000 + 0x400`，magic `10 20 f5 f2`，F2FS 1.16，总 431 MB，已用约 52 MB。
- 这正是 OpenWrt 的 `/dev/fit0`（只读 rootfs）+ `/dev/fitrw`（可写 overlay）机制 —— 我方板子 `mount` 输出完全一致，两边同构。

### 1.3 对方 rootfs（`fit/rootfs-1.bin`）

```text
/etc/openwrt_release:
  DISTRIB_RELEASE='24.10-SNAPSHOT'
  DISTRIB_REVISION='r29251-a1ea57bd05'
  DISTRIB_DESCRIPTION='OpenWrt 24.10-SNAPSHOT r29251-a1ea57bd05'
/etc/config/  只有 dhcp / dropbear / firewall  （network/system/wireless 首启生成）
/lib/modules/6.6.151/  含 rtc-pcf8563.ko（与 24.10.0 一样是上游自带）
无 luci / rpcd / uhttpd
```

对比我方 24.10.0 rootfs 的文件清单：差异只有「内核版本目录名」+「LuCI 那一套」+ mbedtls 版本 + `/init` + 一个 profile 脚本。
**结论：对方 rootfs 本身是干净的上游构建，没有塞私货。**

### 1.4 对方的真正改动：F2FS overlay 的 upper 目录（31 个文件）

```text
/root/reload.sh                              模块热重载脚本（wifi down → rmmod → modprobe → wifi up）
/root/dscpstats                              7,672 B，POSIX sh 脚本
/root/dscpstats.awk                          DSCP 统计聚合（ENQ/DEQ/ACK/RX + 重传）
/lib/modules/6.6.151/mac80211.ko             8,358,768 B，2026-10-14   ← 带 wifi_dscp tracepoint
/lib/modules/6.6.151/mac80211.ko.bak-20261014
/lib/modules/6.6.151/mt7996e.ko              196,656 B  2026-10-27   （= .orig，未打补丁）
/lib/modules/6.6.151/mt7996e.ko.orig
/lib/modules/6.6.151/mt7996e.ko.bak-20261015
/lib/modules/6.6.151/mt7996e.ko.patched-20261027-120214   201,744 B   ← EDCA 补丁
/etc/config/{wireless,network,system,dhcp,firewall}
/etc/board.json
/root/wireless.bak-*、network.bak-*、dhcp.bak-*
/etc/dropbear/*_host_key、/etc/urandom.seed
```

**关键哈希对照：**

```text
对方 mt7996e.ko.patched-20261027-120214
  sha256 18d5f2e0ac847e0437ea0336a2c1ae20109a6041c9763454603d636ad97f223a
我方仓库 mt7996e-edca.ko
  sha256 18d5f2e0ac847e0437ea0336a2c1ae20109a6041c9763454603d636ad97f223a   ← 完全相同
```

即：**mt7996e 的 EDCA 补丁双方共用同一份二进制**（201,744 B，vermagic 6.6.151）。
说明 EDCA 补丁源码已经在两边之间流转过，或者由对方用 6.6.151 重编了我们的补丁。

对方的 `mac80211.ko` 里可以看到：

```text
WIFI_DSCP_ENQ / WIFI_DSCP_DEQ / WIFI_DSCP_ACK / WIFI_DSCP_RX
WIFI_DSCP_DIR_TX / WIFI_DSCP_DIR_RX
"dir=%u stage=%u dscp=0x%02x len=%u skb=%p ts=%llu acked=%u retry=%u"
```

配合 `dscpstats.awk` 的注释：stage 0=ENQ 1=DEQ 2=ACK 3=RX，用 skb 关联，统计每个 DSCP 的
pkts/bytes、queue 延迟、access 延迟、e2e 延迟（avg/min/max）、ACK/失败、重传 P/avg/max。
**这是一套按 DSCP 粒度的 Wi-Fi 时延/吞吐/重传测量工具 —— 正好是我们 OAF→DSCP→EDCA 方案缺的那块「量化验证」。**

## 3. 真正的冲突点（必须解决的）

### 冲突 1：内核基线不一致（最硬的）
- 我方 6.6.73，对方 6.6.151。
- `vermagic` 不同 → 所有预编译 `.ko` 不能跨用。
- 我方有 24.10.0 的完整 SDK + 全部 apply 脚本；对方有 24.10-SNAPSHOT 的可启动整盘镜像。
- **必须二选一作为合并基线，然后把另一方的补丁源码移植过去重编。**

### 冲突 2：mac80211 补丁互斥（同一文件）
- 我方：WDRR（`fq_weight` module param，改 `fq.h`/`fq_impl.h`/`tx.c`）。
- 对方：`wifi_dscp` tracepoint（改 `net/mac80211/trace.h` + `tx.c`/`rx.c` 埋点）。
- 两者**不冲突**，可以同时存在，但必须合并到同一棵 backports-6.12.6 源码里重编一次。
- 目前只有对方的**二进制**，没有源码补丁 → 需要向对方索取，或从二进制反推。

### 冲突 3：mt7996e 已一致，但板子上跑的不是那一版
- 双方 EDCA 二进制相同（`18d5f2e0…`），很好。
- 但我方板子当前加载的是 `tr-mt7996e.ko`（txrate 变体，`e3915b8c…`），不是 EDCA 版。
- 需要确定合并后到底要哪一版（EDCA / A-MPDU / MCS / txrate 是互斥构建）。

### 冲突 4：配置层
| 项 | 我方 | 对方 |
|---|---|---|
| LAN | 192.168.240.1 + 192.168.1.1 | 192.168.7.1 |
| hostname | OpenWrt | BPI-R4-Bai |
| SSID | BPI-R4-5G / BPI-R4 | interruption |
| 5G 信道/带宽 | ch149 HT20（当前） | ch36 VHT80 → HE80 |
| 2.4G | 开 | 对方当前配置里 disabled |
| STA | phy0.0-sta0 → DianGroup103 | sta Bai（当前 disabled） |
| LuCI | 有 | 无 |

### 冲突 5：userspace 两套工具
- 我方：`oaf*`、`l2*`、`vip*`、`wifi_failover*`、`edca_set`
- 对方：`dscpstats` + `dscpstats.awk` + `reload.sh`
- 两者不冲突，直接并存即可（注意 `reload.sh` 里硬编码 `6.6.151`）。

## 4. 合并方案

### 方案 A（推荐）：以对方的 6.6.151 为基线
- 理由：对方有**完整可启动的整盘镜像**和 6.6.151 构建环境；24.10-SNAPSHOT 更新；
  对方已经有把我们的 EDCA 补丁在 6.6.151 上重编成功的先例（`18d5f2e0…`）。
- 做法：
  1. 拿到 6.6.151 对应的 OpenWrt 源码/构建树（或 24.10-SNAPSHOT 的 SDK）。
  2. 把 `_build/apply_wdrr.py` 移植到该树的 mac80211 backports（大概率版本相同，直接可用）。
  3. 把 `apply_v*.py` 移植到该树的 mt76 包。
  4. 合并 mac80211：WDRR + `wifi_dscp` tracepoint 一起编。
  5. 把我们的 userspace（oaf / l2 / vip / failover）复制进 overlay。
  6. 决定网络配置（IP/SSID/信道）。
- 风险：需要对方的构建环境；我方现有 SDK 不能用。

### 方案 B：以我方 6.6.73 为基线
- 理由：我方 SDK、全部 apply 脚本、板子、备份都齐；改动量最小。
- 做法：向对方索取 mac80211 `wifi_dscp` 补丁源码，打进我们的 backports-6.12.6，
  和 WDRR 一起编出一个 mac80211.ko（6.6.73），连同 `dscpstats` 一起部署。
- 风险：24.10.0 较旧；如果对方后续还要维护 6.6.151 就不统一。

### 方案 C：不合并，运行时切换（不推荐）
- 两边各留一套 `.ko`，按实验需要 `cp + reboot` 切换。
- 无法同时用 WDRR 和 DSCP 统计；且跨内核不可行。

**推荐：方案 A**，但前提是能拿到 6.6.151 的构建环境；
若拿不到，退化为**方案 B**（只需对方的 mac80211 补丁源码，成本最低）。

## 7. 分析可复现命令

```bash
# 解压（WSL）
gunzip -c /mnt/d/Desktop/sdcard.img.gz > sdcard.img
# 分区
fdisk -l sdcard.img
# 取 production 分区
dd if=sdcard.img of=p7.bin bs=1M skip=64 count=448
# 列 FIT
dumpimage -l p7.bin
# 取 rootfs 并解压
dumpimage -T flat_dt -p 6 -o rootfs.bin p7.bin && unsquashfs -d rootfs_other rootfs.bin
# 取 overlay（F2FS 起点 0x509F000）
dd if=sdcard.img of=overlay.img bs=1 skip=$((0x509F000)) count=$((0x20000000-0x509F000))
mount -t f2fs -o ro,loop overlay.img /mnt/ovl && ls -R /mnt/ovl/upper
```
