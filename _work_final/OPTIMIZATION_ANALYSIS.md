## 0. 结论摘要（先看这一页）

当前"OAF 识别 → ct mark → DSCP EF → AC_VO"的**机制链路是通的**，但**无法在 A/B 中测出收益**，根因不是"参数没调好"，而是三件事没解决：

1. **治疗剂量被稀释**：实测 accel 组 EF 只覆盖**下行 11.9% 的包 / 16.8% 的字节**（全量 4.6% 包 / 2.6% 字节），
   而且**最大的两条下行流（123.6.122.178 446 包、218.98.57.88 178 包）EF 命中为 0**。也就是说，真正承载豆包交互的流量基本没被加速。
2. **瓶颈没被工程化**：HE80 + MCS8–11（860–1200 Mbit/s 链路）下只施加 280 Mbit/s 负载，空口利用率约 1/4，队列几乎不积压，**AC 优先级没有可重排的对象**。
3. **度量口径不是体验口径**：TTFT 自动采集仍被 uiautomator 卡住；现有 pcap 里几乎没有重载交互（上行约 45 kbit/s、下行约 7 kbit/s 的小流），且两组时长不一致（161 s vs 190 s），SYN RTT / 重传反而"变差"属于不受控对比。

**因此下一步顺序应为：先补"识别覆盖 + 瓶颈可控 + 度量可信"，再谈 EDCA / 调度参数调优。**
调参本身不是瓶颈——板端已验证 EDCA 免重载、亚毫秒级生效；瓶颈在"给谁加速"和"在什么条件下验证"。

## 3. 定量分析：现有 A/B 为什么测不出收益

用 [\`analyze_pcap.py\`](<_work_final/analyze_pcap.py>) 复算 \`doubao_base.pcap\` / \`doubao_accel.pcap\`（手机 192.168.240.219）：

### 3.1 标记覆盖率（最致命的数字）

| 口径 | 基线 | 加速 |
|---|---|---|
| EF 包占比（全量） | 0.2% | **4.6%** |
| EF 字节占比（全量） | 0.0% | **2.6%** |
| **下行 EF 包占比（到手机）** | 0.0% | **11.9%** |
| **下行 EF 字节占比（到手机）** | 0.0% | **16.8%** |
| 上行 EF 占比（手机发出） | 0.3% | 0.0% |
| 下行 Top1 流 123.6.122.178（446 包） | EF=0 | **EF=0** |
| 下行 Top2 流 218.98.57.88（178 包） | EF=0 | **EF=0** |

- 命中的只有 \`111.19.181.176\`、\`222.192.187.33\` 两条次要流；**主力下行流完全没被标记**。
- **推论**：即便 AC_VO 给出完美优先级，最多也只作用于 ≤17% 的下行字节；TTFT 的改善上限被"覆盖率"锁死。
  这解释了 \`phone_ab_metrics.md\` 里"机制通过、体验无改善"的结果——**不是优先级没用，是几乎没加速到点上。**

### 3.2 一个被忽略的既有 QoS：CS5

- 基线/加速两组中 **DSCP=40（CS5）占 23–25% 的包**，且集中在**下行**。
- CS5 经 mac80211 映射到 **AC_VI**。也就是说**基线本身就已经有一部分流量在 VI**，而我们的 EF→VO 只覆盖了另一个小子集。
- 来源待确认（终端自标？上游 CDN 标记？）。**若不查清，会把"既有 VI 的效果"误判成"我们 EF 的效果"。**

### 3.3 拥塞与瓶颈

- 链路：HE80、MCS8–11 → 860–1200 Mbit/s；负载仅约 280 Mbit/s（\`phone_ab_metrics.md\`）→ **空口利用率约 1/4**，队列不积压。
- EDCA 只在**排队竞争**时才产生差异；负载远低于容量时，优先级没有可重排对象，测出来必然在噪声里。
- 强拥塞那次（622 Mbit/s）出现 TTFB p50 −27%、手机 RTT p50 −30%，正是"瓶颈被压出来"的证据。
- **结论：演示必须把 WiFi 空口工程化为确定性瓶颈**（HE40 / 2.4G / 多流 / 限速 / 强干扰），否则任何 EDCA 调参都测不出差异。

### 3.4 度量口径

- SYN RTT p50：基线 55.9 ms → 加速 75.5 ms；dup-seq 重传 40 → 60。看起来"变差"。
- 但两组**时长不同（161 s vs 190 s）**、场景不一致、样本少，属**不受控对比**，不能作结论。
- pcap 里几乎全是小流（上行 ≈45 kbit/s、下行 ≈7 kbit/s），**没有真实的豆包重载交互**。
- **TTFT 未采集** → 无法回答"首字是否变快"，而这才是验收指标。

### 3.5 构建与环境

- 当前是**强制默认 EEPROM 的诊断构建 + 私有 WDRR + A+ token bucket** 的混合栈。
- 对**相对 A/B** 可接受（两组同栈），但绝对吞吐不代表原厂水平；且不同实验若换了模块，前后就不可比。
- **必须先冻结一个基线栈**，两条臂使用同一 md5。

## 4. 根因归纳

1. **识别覆盖不足**：特征只有 \`tcp443/doubao.com\`，漏掉 QUIC/UDP、CDN、图片/语音/WebSocket 域名 → 治疗剂量被稀释到 ~17%。
2. **瓶颈未工程化**：HE80 低负载下 AC 优先级不可观测。
3. **AC 选择不适配混合业务**：VO（AIFS1/CW3-7/TXOP47）为语音设计，突发媒体走 VO 会**自我伤害**（历史 5G 403→210 Mbit/s）。
4. **缺少链路可见性证据**：无 EDCA 回读、无"EF 字节进入 VO txq"的计数，机制正确性靠推断。
5. **度量不可信**：TTFT 缺失、样本少、场景不一致、非随机顺序。
6. **环境漂移**：模块版本与文档不符、遗留进程、诊断 EEPROM。

## 6. 优化设计（分层，按依赖顺序）

### L1 识别覆盖（最高优先级，收益上限）
- 先做**流量测绘**：手机运行豆包（文字/语音/图片/视频）时在 br-lan **不加协议过滤**抓包，导出 SNI / IP / 端口 / 协议清单，区分"信令/语音/媒体"三类。
- 扩展 OAF 特征：\`doubao.com\` 之外的 ByteDance/火山系域名；确认 OAF 是否支持 \`udp;;443\`（QUIC）匹配。
- QUIC 无法按 SNI 识别时，用 **nft set + IP/端口兜底**打标。
- **KPI：豆包"标记字节覆盖率" ≥90%**（当前下行 16.8%）。

### L2 打标与映射
- 打标点放在 **forward/postrouting 下行路径**（现有 postrouting 可用），并确认首包时序。
- **分级映射**：交互信令/语音 → EF→**VO**；图片/视频/下载 → CS3→**VI**（避免 VO 自我伤害）。
- 增加**映射验证**：统计 \`ct mark=1900\` 的字节数 vs nft counter vs 手机下行 EF 字节，三者应闭合。

### L3 EDCA 参数调优（需要回读）
- **先恢复 EDCA 回读**：装 \`mt7996e_edca_eeprom.ko\`（先确认 md5），或把回读补丁合入冻结栈。
- 单变量扫描（每次只动一个 AC），用可控拥塞 + 豆包探针：
  - VO TXOP：47 → 94 → 127（1.5 → 3 → 4 ms）；
  - VI TXOP：94 → 191；
  - 必要时 VO AIFS/CW 微调。
- 每档记录：豆包 TTFT p50/p95、豆包吞吐、背景吞吐、VO/VI/BE 队列占用。
- **护栏**：背景吞吐跌幅 ≤20%；总空口效率不塌陷。

### L4 调度与隔离
- 主用 **nft per-STA policer** 压背景（已验证 2:1/4:1 稳定），EDCA 做优先级、policer 做配额。
- 可小幅开启 ATF；**不要依赖 WDRR per-AC 与 A+ 帧 token**（已证无效/不稳）。
- 探索 AQL 调参降低尾延迟。

### L5 度量体系（与调参同等重要）
- **TTFT 采集**：\`adb screencap\` 200–300 ms 轮询 + 回答区像素差/OCR 判定首帧；或 UiAutomator instrumentation。弃用 \`uiautomator dump\`。
- **可控拥塞发生器**：固定背景流数量与速率，使空口进入确定性拥塞（HE40 或限速），保证可复现。
- **A/B 协议**：5 道固定复杂题；随机化臂顺序；每臂 ≥5 轮；固定 STA 位置/信道；两组同栈同 md5。
- **日志**：每轮记录 EF counter、标记覆盖率、队列计数、背景吞吐、TTFT/TTFB/RTT/重传。

## 8. 风险与回退

- **VO 自我伤害**：突发媒体走 VO 会降自身吞吐（403→210）→ 媒体走 VI / 调大 TXOP。
- **背景饿死**：VO TXOP 过大 + policer 过紧 → 设置背景吞吐下限。
- **诊断 EEPROM**：绝对数值不代表原厂；所有结论限定为"同栈相对值"。
- **改动影响所有 STA**：EDCA 为全局参数，实验后必须回默认。
- **2.4G 自干扰**：AP 与 sta0 同信道，2.4G 打流实验需先停 sta0。
- **回退**：\`_work_recover/backups/backup_sem_20261029.tar.gz\` + SD 卡/串口恢复（见交付文档 §9）。
