# OAF 驱动的 AI 业务识别与 EDCA 自主调优方案

版本：v1.0  
日期：2026-10-30  
目标平台：BPI-R4 / OpenWrt / MT7996；OAF 应用识别模块

## 1. 方案目标

构建一条可观测、可回退、能用对照实验验证的闭环：

```text
识别 AI 业务流
  → 绑定到实际 STA / 业务类别
  → 在必要方向打 DSCP / UP
  → 读取空口负载与队列状态
  → 选择受约束的 EDCA 档位
  → 回读配置并观察体验、背景业务及稳定性
  → 收益不足、误识别或副作用超限时回退
```

目标不是永久把 AI 流量强塞进 VO，也不是用“链路打通”替代体验证明。最终要回答三个问题：

1. OAF 是否覆盖了目标交互的关键流量，而非仅命中少量控制连接？
2. 在可重复的拥塞竞争下，闭环是否选择了正确的 AC/EDCA 档位，并且驱动/固件确实采用？
3. TTFT/首响或抖动是否改善，同时普通流量没有不可接受的退化？

## 2. 对现状的判断

### 已有基础

- OAF 能基于特征识别部分豆包 TCP/TLS 流，并在 conntrack mark 低位写入 AppID。
- nft 可读取 mark 并设置 DSCP；此前有 EF 计数及流量进入高优先级路径的间接证据。
- `edca_set` 可在不重载 Wi-Fi 的情况下下发 EDCA；历史实验报告了亚毫秒级命令确认时延和 AC 竞争变化。
- 看板已有手动加速开关、基础流量/RTT/TTFB 展示和 CSV 记录，可复用为实验采集界面。

### 不能当作已证明的部分

- 静态 EDCA 配置或看板开关不等于自主调优。当前可见看板调用的是安装/删除 nft 规则；未见基于观测反馈自动选择 EDCA 档位的闭环。
- `mark=1900` 不等于“目标手机的豆包主回答流都被识别”。另一份现场分析记录到 mark 来源可能是 PC，且抓包中主要下行流未命中；交付文档的手机 IP、标记计数和现场状态也可能随时间变化。
- EF 计数只能证明 nft 规则命中，不能单独证明 MT7996 空口队列确实按期望的 AC 发送。需要验证实际 DSCP/UP、TXQ/AC 计数或可重复的 AC 竞争行为。
- TTFB 是 HTTP 探针/特定连接的首字节时间，不等同于手机 App 的 TTFT，也不能直接代表语音视频的口到耳时延。
- 已有数据来自不同日期、固件/驱动构建、无线条件和业务场景；不能拼接成一个统一 A/B 结论。
- OAF 对 TLS SNI 类 TCP 流的识别不能自然覆盖 QUIC、加密 ClientHello、复用连接、媒体 UDP 或 CDN 流。扩大域名/IP 规则可能误标共享 CDN 上的非 AI 流量。
- EDCA 是 AP/信道层级的竞争参数，不是只对单个 App 生效。改 AC 参数会影响同一 BSS 中所有使用该 AC 的客户端；高优先级可能伤害背景吞吐或自身聚合效率。
- “链路速率高于业务码率，所以 EDCA 不可能有用”不是普遍成立的判断。关键是是否存在同一无线介质上的竞争和排队，尤其是突发、重传、队列积压及空口占用，而非只比较标称速率。
- 已有 OAF、EDCA 及 Dashboard 部署材料存在版本差异；应冻结实际软件栈、模块哈希和无线配置后再开展新结论。

## 3. 目标架构

```text
数据面
手机 STA → OAF 流识别 → ct mark(AppID/类别) → nft 分类策略
         → DSCP/UP → mac80211 AC 队列 → MT7996 固件 EDCA → 空口

控制面（板端守护进程）
OAF/conntrack + nft 计数 + STA/PHY/队列观测
         → 状态估计与策略状态机
         → 安全档位选择 → edca_set → 回读/日志/回退

验证面（PC/手机）
真实 AI 交互探针/录屏 + 背景流 + pcap + 配置快照
         → 每轮结果与置信区间
```

数据面应保持低延迟、逐包执行；控制面低频采样，不在每个包上运行复杂策略。板端控制服务建议以 1 秒左右周期采样，状态稳定后再决定是否切档，并设置最短驻留时间，避免频繁振荡。

## 4. 自主调优策略

### 4.1 不先做任意参数搜索

先定义并验证有限档位，避免在线探索把全网带入不稳定状态。每档都记录完整 4 个 AC 的值、驱动构建、无线配置和预期影响。

初期建议最多三种策略状态：

| 状态 | 进入条件 | 行为 |
|---|---|---|
| NORMAL | 无已确认 AI 交互，或无线未拥塞 | 恢复已验证的默认 EDCA；不额外提升流量 |
| AI_ACTIVE | 目标 STA 有高置信度 AI 交互，但无明显竞争 | 仅按业务类别设置 DSCP/UP；不改全局 EDCA |
| AI_CONGESTED | AI_ACTIVE 且有竞争/排队证据持续达到阈值 | 应用经过离线验证的温和 EDCA 档位；持续监测护栏 |

建议从“业务分类优先于参数改动”开始：文本/首响等小包交互可测试 BE→VI 或 BE→VO；连续视频/媒体优先评估 VI，不能未经测试就统一打 EF/VO。OAF 若无法区分业务类别，先只验证整条流进入 VI 的效果；不要把未识别媒体伪装成已覆盖。

阈值初值必须由测量校准，不能凭空固定。状态判定至少同时满足：

- 目标 STA/流的 OAF mark 在观察窗内有新增包/字节，且目标 MAC/IP 绑定明确；
- AI 相关流确有无线下行发送；
- 同信道竞争或队列/延迟达到拥塞阈值（例如队列持续非空、重传/RTT 上升、背景流有效占用）；
- 条件连续多个采样窗成立。

仅有“AI 活跃”但无线空闲时，不改全局 EDCA。竞争消失、AI 流结束、识别失效或观测数据异常时返回 NORMAL。

### 4.2 档位与护栏

- 先固定 BE/BK/VI/VO 的规范值，验证单位、AC 编号和工具参数顺序。以驱动回读为准，不能只看 `edca_set` 的成功退出码。
- 只改变最少必要参数；一次实验只改变一个 AC 的一个参数（优先从 TXOP 档位开始），其余参数固定。
- 设置最大优先级、最大 TXOP、最短驻留、回退冷却时间及每日/单次变更上限。
- 出现任一条件即回退：背景吞吐低于预设下限、AI 丢包/时延变差、总吞吐明显塌陷、固件命令失败、回读不符、采样缺失、状态振荡。
- 启动时先加载经验证的安全默认档；控制进程退出或心跳丢失时由 watchdog 恢复默认值。保留 SSH/串口人工总开关。
- 记录每次切换前后配置和原因；禁止静默改写启动脚本或永久写入未经验证的档位。

初期算法选用带迟滞的规则状态机，而不是强化学习或黑盒优化。在线学习需要安全探索、可靠奖励定义和大量重复样本，目前项目的测量质量尚不足以支撑。

## 5. 分阶段实施

### 阶段 0：冻结并核实现场

1. 在板端记录 OpenWrt/内核版本、OAF/mt76/mac80211 模块哈希、特征文件哈希、hostapd 配置、频道/带宽、所有 EDCA 原始回读值。
2. 清点所有 `edca_set`、nft、OAF 启动脚本及看板实际版本；确认当前加速规则、force_rate、背景流和 STA 状态。
3. 校验工具参数 AC 编号、`cwmin/cwmax` 是窗口值还是指数、TXOP 单位、nft 规则命中方向。
4. 创建可一键恢复的基线脚本，先在非关键维护窗口测试回退。

**通过条件：** 两次重启/重连后配置可复现；控制命令、回读和日志能对应同一套版本。

### 阶段 1：建立识别真值与覆盖率

1. 分开采集豆包文字、语音、图片、视频/RTC 的手机侧流量；同时抓取 AP LAN/WAN 两侧包。
2. 每条流记录五元组、方向、SNI（若可见）、协议、持续时间、DSCP、连接来源 STA、应用操作时间。
3. 以“手机操作时间 + 抓包 + OAF mark + conntrack/NAT 映射”核实命中来源，防止 PC 或其他设备造成假阳性。
4. 报告按包和字节计算 precision/recall 或可解释的覆盖率；分别给文字、媒体、控制流结果。不要把共享 CDN IP 直接等同于豆包。
5. 明确 OAF 对 QUIC、TLS ECH、连接复用和 IPv6 的能力；能力不足时将其列为边界，不用设备级规则冒充应用识别。

**通过条件：** 至少一个明确业务类别能稳定识别；命中流来源可追溯；误标率有测量值。未达到时，不进入“应用级自主调优效果”验收。

### 阶段 2：证明分类到 AC 的链路

1. 确认下行打标位置及 conntrack mark 匹配规则；分别检查 IPv4、IPv6、重连接和已建立连接。
2. 抓包核对 DSCP；根据标准映射核对 UP/AC，同时检查 hostapd WMM 参数及 AP 下行实际队列证据。
3. 使用可控测试流构造不同 UP/AC 的竞争对照，证明目标流相对 BE 的发送优先级，而不是只看 nft counter。
4. 检查 AP 自己生成/转发的方向边界：AP 能控制手机下行；手机上行的分类通常由 STA 决定，不能声称由 AP 侧 nft 直接提升。

**通过条件：** mark → nft → DSCP → UP/AC 的每一跳都有独立证据；至少一种直接 AC/TXQ 观测，或清楚标注证据限制的竞争实验。

### 阶段 3：构造可重复的竞争场景

1. 使用同一个 AP/信道/STA 产生背景负载；避免把有线或另一信道的负载当成空口竞争。
2. 先做空载、轻载、竞争三种场景，确认拥塞确实影响目标指标且未导致物理层断连。
3. 记录 AP/STA airtime、重传、队列、实际吞吐、RSSI/MCS；固定位置和终端状态。
4. 不把 force_rate=6M 当作常规实验条件。该功能有断电恢复和稳定性风险，只能单独维护窗口验证；优先用可控同频背景流形成竞争。

**通过条件：** 基线竞争场景下目标体验指标可观测，重复轮次波动可接受；空载组不应凭空显示巨大收益。

### 阶段 4：离线选择安全档位

采用随机化、交叉顺序的对照矩阵：

| 组 | 分类 | EDCA | 场景 |
|---|---|---|---|
| A | 原始 DSCP/BE | 默认 | 空载与竞争 |
| B | AI 流分类 | 默认 | 空载与竞争 |
| C | AI 流分类 | 候选温和 EDCA 档 | 空载与竞争 |
| D | AI 流分类 | 更高优先级候选档 | 仅在护栏允许时 |

每个条件至少做 10 个有效交互样本；至少 3 个独立时段重复。随机化题目/顺序，冷却终端，确保同一软件栈和负载参数。若单轮回答由多个阶段构成，记录请求发出、首字/首音、结束时间及网络侧指标。

主指标：

- 文本：真实 App TTFT（用户提交到首个回答 token 可见）；服务端生成时间与网络时间无法拆分时，如实称为端到端 TTFT。
- 语音/视频：用户说完到 AI 首响的时延；媒体冻结/断续率作为次指标。
- 网络侧：目标下行流 RTT/抖动/重传、队列等待代理指标、有效吞吐。
- 护栏：背景 STA 吞吐、总吞吐、丢包、连接稳定性及不同 STA 公平性。

用中位数和 p95/置信区间报告，不用单次“最好值”。只有统计上稳定、跨时段复现且护栏通过，才选入在线档位。

### 阶段 5：实现在线控制器

控制器按以下流程运行：

```text
采集 → 数据有效性检查 → 目标 STA/AI 活跃判断
     → 竞争判断 → NORMAL / AI_ACTIVE / AI_CONGESTED 状态决策
     → 若状态变化且越过迟滞/驻留限制，应用已验证档位
     → 回读确认 → 观察窗口评估主指标与护栏
     → 保留或自动回退 → 写入审计记录
```

状态至少包括：`NORMAL`、`AI_ACTIVE`、`AI_CONGESTED`、`DEGRADED/SAFE`。实现幂等设置、进程锁、超时、失败重试上限、启动默认值、看门狗回退和手动禁用。所有决策写结构化日志：时间、输入观测、AppID/STA、旧/新档位、命令结果、回读值、触发原因及回退原因。

### 阶段 6：自主性与效果验收

分两类验收，不能混为一谈：

1. **控制闭环验收：** AI 空闲→不改；AI 活跃无拥塞→不滥用激进档；AI 活跃且竞争→自动切换；业务结束/数据异常→自动恢复；失败可回退。
2. **用户收益验收：** 在预注册的竞争场景中，真实 TTFT p50 有实际改善、p95 不恶化；背景吞吐和丢包护栏通过；至少三个独立时段重复。

建议初始目标设为 TTFT p50 改善至少 20%，且 p95 不劣化、背景吞吐下降不超过 20%。这是项目验收门槛建议，不是当前已达到的结果；如样本方差大，应先增加样本，而不是降低统计标准。

## 6. 部署与安全回退

- EDCA 对 BSS/AC 有共享影响，所有档位应有“适用频道、固件版本、终端数量、最大 TXOP、背景吞吐下限”标签。
- 每次启动先校验接口存在、STA 在线、回读可用、OAF 已初始化；任一必要观测缺失进入 SAFE。
- EDCA 下发 ACK 成功后必须回读。若当前构建不能回读，就先补足回读能力或以可复现实验验证，不能把 ACK 单独视为固件状态证明。
- 配置更新采用“先验证参数范围，再单次写入，再读取，再记录”的事务式流程；超时或不一致立即应用基线档。
- 保留物理/远程人工停用方式；不要自动修改模块、刷写固件、重载 Wi-Fi 或使用 force_rate。
- 用户体验看板必须区分“识别命中流量”“被规则打标流量”“实际进入无线 AC 的流量”“真实体验指标”，不能用一个 EF 计数代表整条链路。

## 7. 关键风险与应对

| 风险 | 后果 | 应对 |
|---|---|---|
| SNI/域名覆盖不完整 | AI 主回答流未被提优先级 | 按业务类型测绘；明确支持边界，不能仅增加猜测域名 |
| 误识别共享 CDN/设备流量 | 普通业务被提升、干扰公平 | 绑定 STA、流生命周期、置信度和误报审计；低置信度不调参 |
| AC 映射/DSCP 被覆盖 | 规则命中但无线队列不变 | 端到端逐跳验证并抓包 |
| 空口不拥塞 | A/B 看不出收益 | 建立同频可控竞争；空载负对照 |
| VO/TXOP 过激 | 普通业务饿死、聚合效率下降 | 先 VI/温和档，设护栏和自动回退 |
| 上下行混淆 | 把 AP 无法控制的上行收益归因给 EDCA | 分方向测量，限定结论范围 |
| 服务器/应用波动 | 错把远端波动归因于无线 | 随机交叉、多轮、多时段；报告端到端口径 |
| 软件栈版本漂移 | 实验不可比较或回退失败 | 固定模块哈希及配置快照 |
| 控制器异常/看板 SSH 卡顿 | 参数滞留在激进档 | 板端独立守护、watchdog、进程退出自动回默认 |

## 8. 交付物

1. `baseline_snapshot.json`：版本、模块哈希、无线配置、EDCA 回读、特征库哈希。
2. `flow_coverage.csv`：操作场景、五元组、方向、mark、DSCP、包/字节、真值标签。
3. `ab_trials.csv`：随机化条件、TTFT/首响、背景负载、无线指标、有效/无效原因。
4. 板端控制器：状态机、限幅、回读、审计日志、看门狗和手动关闭接口。
5. 测试说明：可复现实验步骤、验收统计、局限和回退方式。
6. 最终报告：明确区分“当前证据”“方案假设”“已实现功能”“验证结果”。

## 9. 建议执行顺序与近期决策

首个迭代只做以下工作：

1. 以 2026-10-30 的实际板端状态重新采集快照，不假设 6M、背景流、规则或看板仍处于文档所述状态。
2. 选定唯一目标场景，建议先做文字问答；语音/视频作为后续独立工作流。
3. 先证明目标手机的关键下行流确实被 OAF 命中，并量化覆盖与误报。
4. 恢复 EDCA 回读或增加可审计回读；冻结一套软件栈。
5. 建立同频竞争下的离线 A/B，先比较“仅分类”和“分类+候选 EDCA”，同时记录真实 App TTFT。
6. 只有离线结果通过护栏后，才实现板端自动状态机。第一版控制器不在线搜索参数，只在默认与一个已验证档之间切换。

暂不建议：

- 直接扩写大量 ByteDance/CDN/IP 规则并宣称覆盖率提高；
- 让所有豆包流量固定进入 VO；
- 仅凭 TTFB p90 一次性下降宣称用户体验提升；
- 用设备级 VIP 或 nft policer 的效果证明 OAF 应用识别与 EDCA 自主调优；
- 在尚无可靠观测、基线和回退前引入强化学习或自动扫描。

## 10. 结论

项目已有“部分应用识别、DSCP 分类和 EDCA 实时下发”的技术积木，但现有材料不足以证明已实现自主 EDCA 闭环，也不足以把所有观察到的 TTFB/RTT变化归因于该闭环。合理路径是先冻结现场并证明目标流覆盖及 AC 映射，再建立受控竞争和真实体验测量，离线选出一个安全档位，最后实现带迟滞、回读、护栏和自动回退的有限状态控制器。

成功标准不是“EDCA 参数能写进去”，而是：**识别可信、切换有因、参数可核验、体验可复现、副作用可控、异常能回退。**
