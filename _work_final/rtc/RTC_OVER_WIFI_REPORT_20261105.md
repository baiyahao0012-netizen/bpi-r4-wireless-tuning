# RTC over WiFi 实验报告与交付说明

生成时间：2026-11-05
代码目录：`_work_final/rtc/`
实验平台：BPI-R4（mt7996，5G AP）+ 两台 Windows 笔记本

---

## 1. 摘要

本项目在 **802.11 二层直接构建实时音视频传输协议**，去掉传统 WebRTC 所依赖的 UDP 层与 IP 层。目前已实现并在真机两机环境验证的功能包括：

- 自定义二层分片协议（28 字节帧头，替代 RTP+UDP+IP 共 40 字节）
- 帧级 XOR FEC
- NACK 重传
- PLI 关键帧请求
- 自适应抖动缓冲与统一播放时钟
- Opus 音频复用
- 音视频同步
- 双向反馈与跨机单向时延测量

**核心结论：干净链路上已实现视频 30 fps 零丢帧、音频零丢帧、A/V 同步 p95 < 40 ms。丢包场景下 FEC/NACK/PLI 三套恢复机制全部生效，解码异常为 0。**

## 2. 协议规范

### 2.1 帧头（28 字节）

```
struct rtc2_hdr {          // 网络字节序
    uint32_t magic;        // 0x52544332  "RTC2"
    uint8_t  type;         // 0=video 1=audio 2=feedback 3=control
    uint8_t  flags;        // bit0=parity bit1=keyframe bit2=frame_start
                           // bit3=frame_end bit4=retransmit bit5=probe
    uint8_t  stream_id;    // 0=video 1=audio
    uint8_t  rsv;
    uint16_t seq;          // 全局分片序号
    uint16_t chunk_idx;    // 帧内分片下标（0xFFFE = FEC parity）
    uint16_t chunk_cnt;    // 本帧分片总数
    uint16_t payload_len;  // 有效负载长度
    uint32_t frame_id;     // 帧序号（每个编码包唯一）
    uint32_t pts;          // 采集时间戳（90 kHz）
    uint32_t send_ts_us;   // 发送时刻（微秒，用于时延测量）
};
```

### 2.2 EtherType 分配

| EtherType | 用途 |
|---|---|
| `0x88B5` | 音视频数据 |
| `0x88B6` | 反馈帧（20 Hz） |
| `0x88B7` | 控制帧（时钟同步 SYN、NACK、PLI） |

### 2.3 控制消息

| 消息 | Magic | 载荷 |
|---|---|---|
| 时钟同步请求 | `SYN1` | 发送时刻 + 序号 |
| 时钟同步响应 | `SYN2` | 原时刻回显 |
| NACK | `NAC1` | 最多 64 个 uint16 缺失 seq |
| PLI | `PLI1` | 无载荷 |

## 3. 已实现机制

### 3.1 FEC（帧级 XOR）

每帧发送完毕后，对该帧所有分片做按字节异或，生成 **1 个 parity 分片**（`chunk_idx=0xFFFE`）。接收端在帧内仅缺 1 个分片（且不是尾片）时可直接异或还原。

**设计取舍**：RTC1 参考实现是"每 8 个数据块生成 1 个 parity"（跨帧流式），本项目改为**帧内**，原因是解码器需要的是完整帧，帧内恢复更直接；对于典型 8 分片的帧，开销同为 12.5%。

### 3.2 NACK 重传

- 发送端缓存每个已发分片 **3 秒**
- 接收端只在两种时机请求：**帧的最后一个分片到达时**（此时缺口确定）、或帧存在超过 **15 ms**（兜底）
- 同一缺口只请求一次（防止重传风暴），每帧最多 2 次

### 3.3 PLI 关键帧请求

整帧彻底丢失时（FEC/NACK 都无法挽救），接收端发 PLI，发送端将下一帧强制编码为 IDR。限速 100 ms 一次。

### 3.4 抖动缓冲与统一播放时钟

```
play = pts + tmin + D
```

- `tmin`：两条流共享的传输延迟下界
- `D`：自适应缓冲深度，范围 40~200 ms，由到达抖动的 p95 推算
- 音频与视频**共用同一个 tmin 和 D**，因此同一 PTS 的画面与声音在同一墙钟时刻播出

**重要结论：音频不能使用独立的缓冲深度**，否则同一 PTS 会在不同时刻播出，人为制造固定偏移（实测 p50 从 16.3 ms 劣化到 88.7 ms）。

### 3.5 双时间轴

| 流 | 时间轴来源 | 说明 |
|---|---|---|
| 视频 | `pts = frame_id * 90000 / fps` | 由文件帧序号决定 |
| 音频 | `pts = samples_sent * 90000 / 48000` | 由累计样本数决定 |

两者都完全由文件内容决定，不受采集抖动影响。**这是漂移从 −0.30% 降到 −0.02% 的关键改动。**

### 3.6 音频

Opus 64 kbps、48 kHz 单声道、20 ms 一帧，与视频共用分片/FEC/NACK 机制，靠 `stream_id` 区分。

## 6. 关键发现

1. **720p 时发送端只能编码 26 fps**，导致时间轴与真实时间脱节；降到 640×480 后稳定 30.0 fps。
2. **帧丢失率是高频噪声指标**（同配置 3 轮横跨 0%~10%），不能用于参数选型；应使用 **A/V p95** 与**解码帧数**。
3. **音频独立缓冲深度会破坏同步**，两条流必须共用同一播放时钟与同一 D。
4. **深缓冲会掩盖漂移**：干净链路下自适应收敛到 40 ms，上限参数不生效；只有丢包场景才暴露差异。
5. **Npcap 用户态抓包引入额外延迟**（实测中位 +5.6 ms，p95 +39.6 ms），测时延时需注意。

## 7. 缺陷修复记录

| # | 缺陷 | 现象 | 修法 |
|---|---|---|---|
| 1 | 反馈帧解析误用 `payload_of()` | 发送端反馈长期为 0 | 改为 `raw[14:14+FB_LEN]` |
| 2 | 时钟同步符号写反 | 单向时延为负 | `ref = a64 + _off` |
| 3 | NACK 在 `unpack_sync` 之后判断 | NACK 被异常吞掉 | 提前判断 magic |
| 4 | 同一缺口重复请求 | 重传风暴（10255 次） | 每缺口只请求一次 |
| 5 | 已完成帧被迟到重传"复活" | 凭空产生假缺口与重复计数 | 已完成帧抑制窗口（仅视频） |
| 6 | 多个编码包共用 `frame_id` | 接收端混帧重组 | 每编码包分配唯一 ID |
| 7 | 抑制窗口被音频帧号推高 | 视频帧全被丢弃 | 抑制窗口仅对视频生效 |
| 8 | 干扰注入把重传包再丢一次 | 恢复不收敛 | 每个 seq 只丢一次 |
| 9 | 音频用墙钟推导 PTS | 漂移 −0.30% | 改用累计样本数 |

## 10. 码率控制对照实验（2026-11-05 追加）

### 10.1 实验设计

以板端 MAC 埋点驱动码率控制器，判据初版为：

```
q  = aql_pending.total          # 自身队列积压（微秒）
rr = Δ(tx retries + tx failed) / Δ包数
q 高 且 rr 低  -> 自致拥塞 -> 降码率
q 高 且 rr 高  -> 空口被抢 -> 保持
q 低 且 rr 低  -> 有余量   -> 升码率
```

### 10.2 结果

| 场景 | 现象 |
|---|---|
| 无负载 | 1500 → 5696 kbps 连续爬升，q=140~616 µs，rr=0 |
| 无负载（高包率） | 20000 → 38974 kbps，rr 从 0 升到 0.033 |
| 94.6 Mbps 背景流 | q 从 92 µs 跳到 12060 µs，rr 仍为 0，控制器从 2420 降到 1263 kbps |

**升码率与降码率两个分支均验证通过。**

### 10.3 关键发现：初版判据被证伪

背景流场景下 AQL 升到 12 ms（顶到上限），但**重传计数完全为 0**——介质本身是干净的，额外的负载只是把 AP 发送队列塞满，并不产生冲突重传。

结果是控制器把外部负载判成自致拥塞并降了码率，**与 GCC 会犯的错误完全相同**。

| 场景 | AQL | 重传率 | 初版判据判断 | 实际成因 |
|---|---|---|---|---|
| 无负载 | 低 | 0 | 有余量 | — |
| 外部负载 | 高 | 0 | 自致拥塞（错） | 外部 |

**两类拥塞在"AQL + 重传率"二维空间里落在同一点，无法区分。**

### 10.4 实验设计的缺陷

需注意：本次背景流的目标 IP 与视频流是**同一个 STA**（`192.168.240.232`）。对 AP 而言两股流进入同一个 per-STA 队列，因此该场景在设计上更接近"自身负载增加"，**并不构成真正的第二站竞争**。

真正的"外部干扰"至少需要以下之一：
- 第二个 STA 同时传输
- 非 WiFi 干扰源（微波炉、蓝牙、邻道 AP）

### 10.5 判据修正方向

改用**单位字节空口成本**作为主判据：

```
cost = Δ(per-STA TX airtime) / Δ(已发送字节数)    # µs/KB
```

- 自致拥塞：队列积压，但每字节的空口成本基本不变
- 外部争用：每字节需要更多空口时间（重传、退避），成本上升

该指标已在发送端作为诊断量输出，待下一轮实验验证。

## 11. 空口时间占比判据（2026-11-06 追加）

### 11.1 问题

初版判据（AQL + 重传率）被证伪：外部负载不产生重传，两类拥塞在二维空间里重叠。

进一步发现 `cost = Δ空口时间/Δ字节` 也被**包长污染**：码率下降后包变大，每包固定开销被摊薄，干扰下反而更低。

### 11.2 新判据

```
share = Δ(我方站点 tx duration) / Δ(所有站点 tx duration 之和)
```

数据来自 `iw dev <if> station dump` 的 `tx duration` 字段（累计空口时间，微秒）。

- **自致拥塞**：我方占比升高（空口被自己占满）
- **外部争用**：我方占比骤降（空口被别人占走）

该指标不受自身码率影响，因为分子分母同时变化。

### 11.3 决定性对照实验

| 场景 | AQL | share | 重传率 | 控制器动作 |
|---|---|---|---|---|
| 无负载 | 0–2024 µs | 0.04–0.13 | 0.006–0.05 | 升码率 |
| 负载打到**本站**（80 Mbps） | 14344 µs | **0.33–0.48** | 0.29–0.40 | **降码率** 2550→2168→1842→1566 |
| 负载打到**他站**（80 Mbps） | 12048 µs | **0.01** | 0.00–0.035 | **保持不动**（hold 计数 2→8） |

**两种成因的 AQL 完全相同（都在 12 ms 上限），但 share 相差 30 倍，控制器做出了相反决策。**

这正是 GCC 做不到之处：它只看端到端时延，两种情况都会误降码率。

### 11.4 实现要点

- 板端代理每 100 ms 采集：AQL 总量、我方 tx packets/bytes/duration/retries/failed、全部站点 duration 之和
- 单次 `iw station dump` + 单次 awk 提取，采样率 10 Hz
- 控制律：
  ```
  AQL 高 且 share >= 0.10  -> 自致拥塞 -> 码率 x0.85
  AQL 高 且 share <  0.10  -> 外部争用 -> 保持，交给 FEC/NACK
  AQL 低 且 重传率低        -> 有余量   -> 码率 x1.10
  ```

### 11.5 待办

- share 门限已按 3 场景 x 3 轮标定为 **0.10**（见 11.6）
