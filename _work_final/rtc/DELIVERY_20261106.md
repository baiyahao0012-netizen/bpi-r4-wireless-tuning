# RTC over WiFi 交付文档

日期：2026-11-06
代码：`_work_final/rtc/`
版本：v0.6.10（见 `VERSION` 与 `CHANGELOG.md`）
平台：BPI-R4（mt7996）AP + 两台 Windows 笔记本

---

## 1. 项目目标

在 802.11 二层直接构建实时音视频传输协议，**去掉 UDP 层与 IP 层**，同时保持 RTC 层应具备的能力：

- 分片与重组
- 丢包恢复（FEC / NACK / PLI）
- 抖动缓冲
- 音频传输与音视频同步
- **码率控制**（并且能利用 MAC 层信号，做到 GCC 做不到的拥塞成因区分）

---

## 2. 系统架构

### 2.1 拓扑

```
发送端（笔记本 A）                 接收端（笔记本 B）
以太网 192.168.240.2 ──┐      ┌── 以太网 192.168.240.221（SSH / 反馈 / 控制）
                       ├─ BPI-R4 ┤
                       │  br-lan │
                       └────┬────┘
                            │
                   5G AP phy0.1-ap0   或   2.4G AP phy0.0-ap0
                            │
                   Realtek 8812BU（USB）192.168.240.232
```

- 媒体面：**二层裸帧**，EtherType 0x88B5
- 反馈面：有线（Windows 无法在 WiFi 上注入裸帧）
- 控制面：MAC 埋点上报走 TCP（板端 busybox 的 nc 只支持 TCP）

### 2.2 协议帧头（28 字节）

```
magic(4) type(1) flags(1) stream_id(1) rsv(1)
seq(2) chunk_idx(2) chunk_cnt(2) payload_len(2)
frame_id(4) pts(4) send_ts_us(4)
```

对比标准 WebRTC 的 RTP(12)+UDP(8)+IP(20)=40 字节，**净省 12 字节**。

### 2.3 EtherType 分配

| EtherType | 用途 |
|---|---|
| 0x88B5 | 音视频数据 |
| 0x88B6 | 反馈帧（20 Hz） |
| 0x88B7 | 控制帧（时钟同步 / NACK / PLI） |

### 2.4 主要模块

| 文件 | 职责 |
|---|---|
| `rtc2.py` | 协议定义：帧头、分片、FEC parity、NACK、PLI |
| `txport.py` | 传输抽象（l2 / udp 可切换） |
| `l2sock.py` | Npcap 封装 |
| `sender.py` | 采集/编码/分片/FEC/重传缓存/MAC 码率控制 |
| `receiver.py` | 重组/FEC 恢复/NACK/抖动缓冲/解码/播放 |
| `mac_agent.sh` | 板端 MAC 埋点采集与上报 |
| `webrtc_peer.py` | aiortc 对照实现 |
| `long_run.py` / `sweep_jb2.py` | 自动化实验脚本 |

## 3. 已实现并验证的能力

### 3.1 传输与恢复

| 能力 | 实现要点 | 验证结果 |
|---|---|---|
| 分片/重组 | 1200 B 分片，frame_id + chunk_idx | 累计 6000+ 帧零错误 |
| **FEC** | 每帧 1 个 XOR parity | 实测恢复 12~93 次/轮 |
| **NACK** | 缓存 3 s，末片确认 + 15 ms 超时兜底，每缺口只请求一次 | 实测重传 74~640 次/轮 |
| **PLI** | 整帧丢失时请求 IDR | 解码异常 40 → 0 |

**关键数据**：注入 63 个分片丢失 → **0 帧丢失**。突发丢包下加 PLI 后帧丢失从 11.14% 降到 2.81%。

### 3.2 播放与同步

| 能力 | 实现要点 | 验证结果 |
|---|---|---|
| 抖动缓冲 | 共享播放时钟，自适应 40~200 ms | 干净链路收敛到 40 ms |
| 音频 | Opus 64 kbps，20 ms，与视频共用恢复机制 | 12 轮零丢失 |
| **音视频同步** | 视频用帧序号时间轴，音频用累计样本数时间轴 | **p50 16.7 ms / p95 27.5 ms / max 46.7 ms** |
| 跨机时延 | NTP 式时钟同步 | RTT 23~60 ms |

### 3.3 长时运行

90 秒（5G，含音频）：

```
视频 2694 帧, 0 丢失, 解码 2693, 解码异常 0
音频 4499 帧, 0 丢失, 解码 89.98 秒, 解码异常 0
A/V 偏移 p50=16.7ms p95=27.5ms max=46.7ms
释放间隔: 视频 33.4/33.8ms, 音频 20.0/20.0ms
```

300 秒运行无崩溃、无序号溢出。

## 4. 码率控制：判据的三次迭代

这是本项目相对 WebRTC 的核心差异化，也是踩坑最多的部分。

### 4.1 初版判据（已证伪）

```
AQL 高 + 重传率低 → 自致拥塞 → 降码率
AQL 高 + 重传率高 → 外部干扰 → 保持
```

**证伪**：94.6 Mbps 外部负载灌入时，AQL 升到 12 ms 但**重传率为 0**（介质干净，只是队列被塞满）。两类拥塞在二维空间重叠，控制器把外部负载误判为自致拥塞，与 GCC 犯同样的错。

### 4.2 第二版判据（已证伪）

```
cost = Δ(空口时间) / Δ(字节数)
```

**证伪**：被包长污染。码率下降后包变大，每包固定开销被摊薄，干扰下 cost 反而更低（59 → 29 µs/KB）。

### 4.3 第三版判据（已验证）

```
share = Δ(我方站点 tx duration) / Δ(所有站点 tx duration 之和)
```

数据来自 `iw dev <if> station dump` 的 `tx duration`（累计空口时间，微秒）。

| 场景 | 链路 | 样本 | share |
|---|---|---|---|
| 无负载 | 5G 585M | — | 0.34–0.99 |
| **外部争用** | 5G 585M | 26 | **0.01–0.05** |
| **自致拥塞** | 2.4G 72M | 3 轮 | **0.42–1.00** |

分离度 8~100 倍，**门限取 0.10**（下侧余量 2×，上侧 4.2×）。

### 4.4 归因判断（关键补充）

`share=1.00` 只说明空口被本主机占用，分不清是视频流还是同主机的其他流。实测中 80 Mbps 背景流与 2 Mbps 视频共用同一站点，控制器把码率从 2000 砍到 500，**q 毫无下降**。

补充判据：

```
attr = 视频字节数/PHY速率  ÷  实测 tx duration
AQL 高 且 attr < 0.30 → 不可归因 → 保持
```

**验证**：仅视频 attr=0.48~0.51；视频+背景流 attr=0.02~0.04，hold 计数 10→17，码率未动。

### 4.5 最终控制律

```
if q > 0.5*lim:
    if share < 0.10:   保持   # 空口被别人占
    elif attr < 0.30:  保持   # 空口虽被本机占, 但不是视频占的
    else:              降 15%
elif q < 0.2*lim:
    升 10%                     # 只看队列是否为空
```

**注意**：升码率不能加重传率门限。2.4G 环境下 rr 常年在 14~17（邻居干扰），任何 `rr < 0.05` 的条件都会让码率永久锁死——这个坑已踩过并修复。

### 4.6 分支验证状态

| 分支 | 条件 | 状态 |
|---|---|---|
| 保持（外部） | q 高 + share 低 | ✅ 验证 |
| 保持（不可归因） | q 高 + attr 低 | ✅ 验证 |
| 升码率 | q 低 | ✅ 验证（rr=15 下仍能爬升） |
| 降码率 | q 高 + share 高 + attr 高 | ⚠️ 仅早期验证过，最后一版判据未复测 |

## 5. 已知缺陷与限制

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | 饱和链路下 `iw station dump` 阻塞 4~5 s | 采样率降到约 1/s | 接受 1 Hz，或用更轻的数据源 |
| 2 | 板端无 `nohup` / `setsid` / `pkill` | 代理必须挂持久 SSH 会话；清理要按 PID | 启动用持久会话；清理用 `kill_agents.sh` |
| 3 | 2.4G/5G 切换 | `netsh wlan scan interface=` 语法不被接受 | 需人工在接收端连接 |
| 4 | `seq` 16 位 | 已修为边界留空洞，但 300 s 循环未复测 | 下轮验证 |
| 5 | 降码率分支未复测 | 最终判据下缺乏数据 | 下轮验证 |

## 7. 复现步骤

### 7.1 板端准备

```sh
# 上传代理与工具
cat > /tmp/mac_agent.sh   # 见仓库同名文件
cat > /tmp/kill_agents.sh # 清理用

# 启动代理（必须挂持久会话，不能用 ( ... &)）
/tmp/mac_agent.sh 192.168.240.2 9931
```

代理每 800 ms 采集并上报：AQL 总量、我方 tx packets/bytes/duration/retries/failed、全部站点 duration 之和、PHY 速率。

### 7.2 发送端

```sh
python sender.py --transport l2 \
  --dst 40-A5-EF-26-E3-47 --src 40-C2-BA-52-70-95 \
  --fb-iface GbE --video clip.mp4 --audio-file clip.mp4 \
  --width 640 --height 480 --fps 30 --seconds 90 \
  --bitrate 2000000 --fec 1 --audio file --audio-pts samples \
  --mac-ctl 1
```

### 7.3 接收端

```sh
python receiver.py --transport l2 --iface 8812BU \
  --fb 1 --fb-iface I219 \
  --fb-dst 40-C2-BA-52-70-95 --fb-src E8-80-88-BA-3C-BB \
  --seconds 100 --audio 1 --fps 30 --jb-max 120 \
  --out r.h264 --out-pcm r.pcm
```

### 7.4 关键输出字段

| 字段 | 含义 |
|---|---|
| `MACDBG q=` | AQL 队列占用（微秒），12 ms 为上限 |
| `MACDBG share=` | 我方空口占比 |
| `MACDBG attr=` | 视频对空口的归因比例 |
| `MACDBG hold=a/b` | a=外部干扰保持次数，b=不可归因保持次数 |
| `A/V sync skew` | 音视频偏移，正值表示音频领先 |

## 9. 交接提示

1. **代理必须挂持久会话**：板端没有 nohup/setsid，`( ... &)` 起的进程会随 SSH 会话关闭被杀，表现为「控制器收不到数据」。
2. **清理要用 PID**：板端没有 pkill，用 `kill_agents.sh`（ps + kill）。残留多个代理会导致数据全 0。
3. **测哪类拥塞取决于链路是否饱和**：5G 585 Mbps 下 80 Mbps 负载压不满，必须用 2.4G（144 Mbps）才能触发自致拥塞。
4. **升码率不能加重传率门限**：2.4G 环境 rr 常年 14~17。
5. **音频解码要按 layout 去交织**：libopus 即使单声道也返回交织格式，直接取 row 0 会让音频半速。
