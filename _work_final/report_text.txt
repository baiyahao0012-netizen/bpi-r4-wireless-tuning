BPI-R4 AP 下行 EDCA / A-MPDU / MCS 实时性实测
与私有 WDRR 调度器部署验证报告
OpenWrt 24.10.0 · 内核 6.6.73 · MT7996 · 2026-10-22

一、结论摘要

一句话：EDCA 与 A-MPDU 都可以在 AP 运行中实时改、立即生效、不需要 wifi reload；MCS 的主机侧速率掩码仍然不被 mt7996 固件 RC 消费，属于“命令可下发、下行不生效”；WDRR 私有调度器已完成全链路部署并在真实流量下触发运行标记，但 per-AC 加权在 fq 层的架构性局限仍然成立。
二、实验环境与拓扑

说明：板端 mt7996e 使用“强制默认 EEPROM”诊断构建（卡内 EEPROM 读取异常时的 workaround），因此绝对吞吐会与完全原厂校准状态略有差异；本文所有对比均为同一构建、同一链路条件下的相对测量。
三、EDCA 下行参数实时修改
3.1 下发与回读通道
mac80211 的标准路径为：nl80211 SET_WIPHY(WIPHY_TXQ_PARAMS) → ieee80211_set_txq_params() → 更新 link->tx_conf[ac] → drv_conf_tx() → BSS_CHANGED_QOS → mt7996_link_info_changed() → mt7996_mcu_set_tx() → 固件 EDCA_UPDATE。hostapd 只在启动/重载时走这条路径，因此运行中直接改 hostapd.conf 不会生效；本文用自写的静态 C 工具直接发 nl80211 报文，绕过 hostapd。
回读侧给 mt7996_mcu_set_tx() 增加 last_edca[] 快照，并在 debugfs 暴露 edca 节点，按固件 ACI 顺序（0=BE 1=BK 2=VI 3=VO）打印 raw 值与 fls 指数值。
3.2 下发工具
// 交叉编译为 aarch64 静态二进制，板端直接运行
/root/edca_set phy0.1-ap0 <AC 0=BE 1=BK 2=VI 3=VO> <aifs> <cwmin> <cwmax> <txop>
# 示例：把 BE 改为激进值
/root/edca_set phy0.1-ap0 0 3 7 15 0
# 回读
cat /sys/kernel/debug/ieee80211/phy0/mt76/edca
3.3 回读结果（hostapd 启动后的初始值）

把 BE 改为 aifs=3 / cwmin=7 / cwmax=15 / txop=0 后，同一节点立即回读为 aifs=3 / cwmin=7 / cwmax=15 / txop=0，fls 变为 3/4。写-读之间没有重启 hostapd、没有 down/up 接口。
3.4 下发时延

时延口径：edca_set 进程内 CLOCK_MONOTONIC，从 sendto(nl80211) 到收到内核 ACK；该 ACK 在 mt7996_mcu_set_tx() 等待固件 EDCA_UPDATE 响应之后才返回，因此包含 host→mac80211→驱动→固件→ACK 的完整往返。
3.5 免重载与业务连续性
hostapd 进程 PID 在整个切换过程中保持不变（1919/1867 → 1919/1867）。
STA 的 connected time 从 61 s 连续增长到 76 s，没有 deauth/assoc 事件。
20 s 下行 iperf3：平均 371 Mbit/s，逐秒 343–397 Mbit/s，全程无 0 吞吐空档，Retr=0。
切换 15 次期间没有出现 hostapd “Could not set interface … UP” 或 MCU timeout。
结论：EDCA 四参数可以在 AP 运行中实时下发并立即生效，不需要 wifi reload，也不会导致 STA 断连。
四、A-MPDU 聚合窗口实时修改
4.1 实现
在 mt7996_sta 中增加 agg_win_cap 字段，并在 mt7996_mcu_add_tx_ba() 下发 BA TLV 时把 buf_size 截断到 cap；debugfs 的 agg_win_cap 写入时对所有已关联 STA 重放 TX BA（先删后加），从而在不重连的情况下改变固件聚合窗口。0 表示恢复默认窗口。
cat /sys/kernel/debug/ieee80211/phy0/mt76/agg_win_cap
echo 2 > /sys/kernel/debug/ieee80211/phy0/mt76/agg_win_cap   # 每 A-MPDU 最多 2 个 MPDU
echo 0 > /sys/kernel/debug/ieee80211/phy0/mt76/agg_win_cap   # 恢复
4.2 吞吐结果（5G 下行，10 s，PC→AP 反向 iperf3）

cap 从 0 改为 2 后吞吐下降 80.5%–81.5%；写回 0 后 10 s 内恢复到 402 Mbit/s。整个过程没有断开 STA、没有重载驱动，dmesg 只出现 “agg_win_cap: cap=2 applied to 2 station(s)” 与 “cap=0 applied to 2 station(s)”。
注：write 会遍历所有 wcid，因此板端自身连接 Bai 的 STA 也会被一并限制；本机下行测试不受影响，但说明该 debugfs 是“全局 per-device”语义，不是 per-STA。
五、MCS 锁定尝试
实现：mt76.ko 暴露 force_mcs debugfs（0–7 强制 MCS，255 自动），mt76-connac-lib 在 sta_rec_ra_info 组包时覆盖 rx_mcs_bitmask，试图让固件只使用指定 MCS。

force_mcs 节点可读可写（0/1/255 均回读正确），但 station 的 tx bitrate 与吞吐没有随锁定值变化，dmesg 也没有出现 “mt76: FORCE MCSx”。说明 mt7996 的固件 RC 不消费主机侧 rx_mcs_bitmask（至少 AP 下行路径如此），仅改这个字段无法锁定下行速率。
结论：MCS“命令可实时下发”成立，但“AP 下行实时生效”不成立；若要真正锁速，需要改固件 RC 的 rate table，或改走 STA 模式/驱动 TX rate 强制路径。
六、最小调度粒度

因此，“实时”在软件层是每个包/每个 flow 可调，在固件层是一次 MCU 命令（百微秒级），在硬件层是一个 PPDU/A-MPDU；不存在比 PPDU 更细的硬件调度粒度。
七、私有 WDRR 调度器部署与运行验证
7.1 修改与编译
基于 mac80211 fq 的 DRR 实现，共 5 处修改：fq_flow 增加 quantum；fq_tin_dequeue 按 flow quantum 补充 deficit；fq_flow_init 初始化 quantum=0；tx.c 增加 fq_weight[4] 模块参数；首次 dequeue 时按 txq 的 AC 赋 flow->quantum = fq->quantum × fq_weight[ac]。

7.2 运行验证与架构结论
在真实下行流量下，fq_tin_dequeue_func 被触发，printk_once 打印了 WDRR 标记，证明私有代码路径确实在数据面执行；fq_weight 的写入不需要重载模块，但按当前实现，flow->quantum 只在 flow 首次 dequeue 时赋值，已存在的 flow 不会被后续 sysfs 修改影响。
架构性结论（历史双 AC 实验，本轮未重复）：mac80211 的 fq 是 per-flow 粒度，AC 级调度发生在 txq 层，同一 txq 内所有 flow 属于同一 AC，因此 per-AC 权重在 fq 层会互相抵消；BE:VO=4:1 时双 AC 吞吐仍约 1:1。要真正改变 AC 优先级，应改 txq 层（airtime fairness 或 ieee80211_txq_schedule），而不是 fq 层。
八、总体结论与建议
EDCA：运行中直接走 nl80211 下发，百微秒级生效，不需要 wifi reload；hostapd.conf 只在启动/重载时生效，不能用于运行时调节。
A-MPDU：debugfs agg_win_cap 可实时改聚合窗口，吞吐从 402 降到 74.3 Mbit/s，写回 0 立即恢复；适合做聚合敏感型实验。
MCS：force_mcs 节点可写，但 AP 下行速率不变；mt7996 固件 RC 不消费主机 rx_mcs_bitmask，需改固件 rate table 或走 STA 模式。
最小粒度：软件包/帧，固件 MCU 命令，硬件 PPDU/A-MPDU；不存在比 PPDU 更细的硬件粒度。
WDRR：修改→编译→烧录→加载→运行标记已全链路打通；per-AC 加权在 fq 层架构性无效，后续应改 txq 层。
建议：① 若目标是把 MCS 锁定做成可交付能力，优先评估固件 RC rate table 或 STA 模式，而不是继续改 rx_mcs_bitmask；② 若目标是 AC 级优先级，直接在 txq/airtime fairness 层做加权，不要继续在 fq 层加权重；③ 当前 mt7996e 使用强制默认 EEPROM，正式交付前应在 EEPROM 正常的板子上复测一遍绝对吞吐。
九、关键复现命令
# EDCA 下发 + 回读
/root/edca_set phy0.1-ap0 0 3 7 15 0
cat /sys/kernel/debug/ieee80211/phy0/mt76/edca

# A-MPDU
echo 2 > /sys/kernel/debug/ieee80211/phy0/mt76/agg_win_cap
iperf3 -c 192.168.240.1 -B 192.168.240.126 -t 10 -R -i 2
echo 0 > /sys/kernel/debug/ieee80211/phy0/mt76/agg_win_cap

# MCS
echo 0 > /sys/kernel/debug/ieee80211/phy0/mt76/force_mcs
iw dev phy0.1-ap0 station dump | grep "tx bitrate"
echo 255 > /sys/kernel/debug/ieee80211/phy0/mt76/force_mcs

# WDRR
cat /sys/module/mac80211/parameters/fq_weight
echo 4,1,1,1 > /sys/module/mac80211/parameters/fq_weight
dmesg | grep WDRR
十、数据来源与限制
EDCA 时延为 edca_set 进程内 CLOCK_MONOTONIC 往返，含内核 ACK 与固件 EDCA_UPDATE 响应；样本 50+15 次。
A-MPDU 吞吐为 10 s 反向 iperf3 平均值；cap=2 与 cap=0 在同一链路、同一 PC 位置连续测得。
MCS 测试中 force_mcs 只在 station 重连后检查，仍未观察到速率变化；不排除需要固件 rate table 才能生效。
板端 mt7996e 为“强制默认 EEPROM”构建，卡内 EEPROM 读取异常；绝对吞吐仅供参考。
WDRR 双 AC 打流为历史实验结论，本轮只验证了模块加载、参数读写与 dmesg 运行标记。
