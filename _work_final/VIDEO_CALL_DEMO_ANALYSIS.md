## 0. 结论（针对"视频对话"场景）

文字场景的结论**不能直接搬到视频对话**。五个本质差异决定了方案要改：

| 维度 | 文字回答 | **视频对话** | 对方案的影响 |
|---|---|---|---|
| 协议 | TCP/HTTPS，SNI 可识别 | **RTC，多为 UDP/QUIC/私有协议** | **OAF SNI 识别不到 → 必须走设备级 VIP** |
| 方向 | 下行占绝对主导 | **上下行都大**（上行=你的摄像头） | **加速只覆盖下行；手机上行空口 AP 管不到** |
| 速率 | 几十 kbit/s | **1–4 Mbit/s 突发** | VO 小 TXOP 会伤视频 → **改用 VI(CS3)** |
| 敏感度 | 首字时延 | **端到端"口到耳" + 画面连续性** | 指标从 TTFT 扩到首响/冻结/断续 |
| 打标 | 我们可覆盖 | **App 往往已自标 audio/video** | **不要盲目覆盖 App 的 DSCP** |

**一句话结论：视频对话的演示，"流畅"必须来自"下行优先 + 背景让路"，而不是单靠 EDCA；识别必须设备级；AC 选 VI 不选 VO。**

## 1. 为什么视频对话更难，也更需要工程化

### 1.1 识别层：SNI 失效
- 文字走 HTTPS/TCP443，OAF 能按 \`doubao.com\` 的 SNI 打标（当前 31 条 \`mark=1900\`）。
- 视频对话走 RTC（UDP，可能 QUIC/私有协议，端到端加密），**没有可匹配的 SNI**。
- 结论：**应用级 OAF 对视频对话基本无效**；要么设备级 VIP，要么按 IP/端口兜底。

### 1.2 方向层：上行不可控（最容易被忽略的坑）
- 你的摄像头画面是**手机→AP 的上行**。AP 的 nft 规则在 \`postrouting\`，只影响**下行（WAN→手机）**和上行转 WAN（对空口无意义）。
- 手机上行的 AC 由**手机自己**决定：它给 RTC 包打的 DSCP + AP 在 beacon 里广播的 WMM 参数。
- 所以：**"加速后不卡"主要来自下行画面变顺 + 背景让路（policer），而不是我们直接提升了上行。** 演示话术要如实。
- 进阶杠杆：AP 侧 \`hostapd\` 的 \`wmm_ac_*\`（广播给 STA 的上行 EDCA）可调，但**要 \`wifi up\`、会断连**，只能提前设好。是否有效取决于 App 是否按 DSCP 选 AC。

### 1.3 AC 层：视频该进 VI，不是 VO
- VO：AIFS1 / CW3-7 / TXOP47（1.5 ms）——为语音小包设计。
- VI：AIFS1 / CW7-15 / TXOP94（3 ms）——为视频设计。
- 历史实测：把 1–4 Mbit/s 的突发流量打进 VO，**自身吞吐从 403 掉到 210 Mbit/s**。
- 视频对话是 1–4 Mbit/s 的连续突发 → **用 CS3→VI**；只有音频小包才适合 VO。
- **但 RTC 常把音频/视频复用在同一 5 元组**，路由器按 IP 分不开 → 折中：**整条流进 VI**。

### 1.4 打标层：别覆盖 App 已有的标记
- 不少 RTC App 已经：音频 EF/VO、视频 AF41/VI。
- 我们若无条件 \`ip dscp set ef\`，会把视频也提到 VO → 自我伤害。
- 建议规则：**只提升未标记/低优先的包**，例如
  \`\`\`sh
  # 只把 BE(0) 的下行提升到 CS3(VI)，保留 App 自己的 EF/AF41
  nft add rule ip vip_demo post ip daddr 192.168.240.219 ip dscp 0 counter ip dscp set cs3
  \`\`\`

## 2. 视频对话的"卡顿"长什么样、能不能被检测

| 现象 | 网络成因 | 可检测性 |
|---|---|---|
| 画面定格（冻结） | 下行丢包/排队，视频帧没到 | ✅ 逐帧差分，低差分持续=冻结 |
| 马赛克/糊 | 丢包后无参考帧 | ⚠️ 难量化，可人工标注 |
| 声音断续/机械音 | 音频包延迟抖动/丢失 | ✅ 音频能量包络找异常静音 |
| 音画不同步 | 音视频路径时延差 | ⚠️ 需对齐，较难 |
| **响应变慢**（AI 迟迟不说话） | 上行传不出去 + 下行首帧延迟 | ✅ **VAD 测"用户说完→AI 开口"** |

**最关键的可量化指标就是最后一项——视频对话版 TTFT。**

## 3. 指标体系

| 指标 | 定义 | 采集方式 | 目标 |
|---|---|---|---|
| **首响时延 TTFT-v** | 用户停止说话 → AI 第一个响应音/首帧 | 录屏音频 VAD（首选）/ 画面活动（兜底） | 加速后 ↓≥30% |
| **端到端时延 M2E** | "口到耳"，含服务端 | 音频对齐 | 参考 |
| **视频冻结** | 冻结次数 / 总时长 / 占比 | cv2 帧差 | 加速后显著 ↓ |
| **音频断续** | 断续次数 / 总时长 | 音频包络 | 加速后显著 ↓ |
| **网络 RTT** | p50 / p95 | 板端 pcap | ↓ |
| **丢包 / jitter / 重传** | 率 | 板端 pcap | 不劣化 |
| **下行加速覆盖率** | EF/VI 字节占比 | pcap + [\`analyze_pcap.py\`](<_work_final/analyze_pcap.py>) | ≥90% |
| **背景吞吐** | PC 侧 | iperf3 | 护栏（跌幅≤20%） |
| **主观分** | 1–5 | 人工 | 加速后 ↑ |

> 视频对话一次通话通常有 3–6 轮问答 → 每轮一个 TTFT 样本；每臂 3 通电话、随机顺序。

## 4. 采集与自动化流水线（本机已具备全部依赖）

### 4.1 录屏

\`\`\`sh
# 需要同时录系统音频（Android 10+）；通话音频可能录不到，见 4.4
adb shell screenrecord --bit-rate 12000000 --size 1080x1920 --time-limit 180 --audio /sdcard/call_A.mp4
adb pull /sdcard/call_A.mp4
\`\`\`

- 单段上限 180 s；长通话分多段。
- 手机当前**未连 adb**，先确认 \`adb devices\` = \`109be14a device\`。

### 4.2 板端抓包

\`\`\`sh
ssh root@192.168.240.1 "tcpdump -i br-lan -w /tmp/call_A.pcap host 192.168.240.219"
\`\`\`

### 4.3 自动化分析（无需安装 ffmpeg）

本机已确认可用：**PyAV 17.0.1（可直接解 MP4 的视频帧+音频 PCM）、opencv 4.11、numpy 1.26、scipy 1.15、soundfile 0.13**。

\`\`\`text
PyAV 解容器 → 视频帧流 + 音频 PCM
  ├─ cv2/numpy：AI 画面区域逐帧差分 → 冻结区间 → 次数/总时长
  ├─ scipy：音频能量包络 + 阈值 VAD → 语音段
  │        → "用户段结束" 到 "AI 段开始" = TTFT-v
  └─ 时间轴输出：首响/冻结/断续 事件表 + 曲线
板端 pcap → RTT p50/p95、丢包、重传、下行 DSCP 分布
\`\`\`

### 4.4 音频录不到的兜底（最大不确定性）

\`screenrecord --audio\` 通常只录 media 流，**通话音频可能录不到**。三级兜底：

1. **手机自带录屏**（多数能录系统音，含通话）；
2. **外接录音**（PC 麦克风录环境音），与录屏按拍手/提示音对齐；
3. **纯视觉**：AI 画面开始明显运动 / 字幕出现 = 首响（精度略低，但可用）。

**开录前必须做一次 10 秒试录，确认音频轨里有 AI 的声音**，否则 TTFT-v 只能靠视觉。

## 5. 演示脚本（三段式）

### Clip 1 — 基线（卡顿）
1. 5G 降到 HE40/HE20；PC 起背景流（反向 iperf3，参数固定）。
2. **加速 OFF**（\`nft list table ip vip_demo\` 不存在）。
3. 开始录屏 → 发起豆包视频对话 → 问 2–3 个固定问题 → 结束通话 → 停录。
4. 取证：背景吞吐、板端 pcap、卡顿曲线。

### Clip 2 — 加速（流畅）
1. 背景流**参数完全一致**。
2. **加速 ON**：设备级 VIP，**CS3→VI**（见 §1.4 的"只提升 BE"规则）。
3. 同题、同流程录一遍。
4. 取证：nft counter、pcap 下行 VI/EF 覆盖率、背景吞吐。

### Clip 3 — 同一通话内切换（★ 最有力）
1. 背景流同上，**先 OFF**，开始录屏，发起视频对话。
2. 对话进行到一半，**中途装上 VIP 规则**（对已建立 RTC 流逐包生效，不用挂断、不用重拨）。
3. 继续问到结束。
4. 效果：**同一通电话**，切换点之后画面/声音明显变顺 —— 天然抵消服务端波动与题目差异。
5. 取证：切换时刻 counter 前后对比。

## 6. 实验矩阵

| 组 | 加速策略 | 拥塞 | 目的 |
|---|---|---|---|
| G0 | OFF | HE40/HE20 + 背景 | 基线卡顿 |
| G1 | CS3→VI（只提升 BE） | 同上 | **推荐主方案** |
| G2 | EF→VO（整条流） | 同上 | 验证 VO 是否反而更差 |
| G3 | CS3→VI + 背景 policer | 同上 | 最强"流畅"（含让路） |
| G4 | 无拥塞对照 | 无背景 | 证明差异来自拥塞下的优先级 |

每组 3 通电话、随机顺序；每通 3–6 轮问答。

## 7. 风险与兜底

| 风险 | 影响 | 兜底 |
|---|---|---|
| **音频录不到** | TTFT-v 无音频依据 | 自带录屏 / 外录 / 视觉兜底（4.4） |
| **上行不可控** | 你的画面本身卡，AI 看不清 | 如实说明；用 policer 让路降低上行竞争 |
| **App 自适应降码率** | 网络差时自动降分辨率，掩盖卡顿 | 同时记录分辨率/码率变化；以"冻结+首响"为主指标 |
| 服务端波动 | 两次通话本身快慢不同 | **同通话内切换** + 多轮取分布 |
| VO 自我伤害 | G2 可能更差 | 主用 VI；VO 仅作对照 |
| 手机过热降频 | 假卡顿 | 控时长、散热、冷却后重录 |
| 2.4G 自干扰 | 结果不稳 | 2.4G 实验前停 \`sta0\` |

## 8. 执行清单

1. **接手机**：\`adb devices\` 出现 \`109be14a device\`。
2. **试录 10 s**：确认录屏音频轨能录到 AI 声音（决定 TTFT-v 走音频还是视觉）。
3. **造瓶颈**：5G→HE40/HE20；PC 反向 iperf3；确认队列积压。
4. **定规则**：设备级 VIP，**CS3→VI 且只提升 BE**（§1.4）。
5. **Pilot**：先录 1 组 G0/G1，跑 §4.3 分析，确认"冻结/首响"前后差 ≥3× 再正式录。
6. **正式录 3 段**：Clip 1/2/3，每段留 counter + pcap。
7. **出指标表**：TTFT-v、冻结、断续、RTT、覆盖率、背景吞吐。
8. **恢复现场**：删 \`vip_demo\`、5G 回 HE80、停背景流。

> 一句话：**视频对话的演示 = 设备级 VIP（CS3→VI，只提升 BE）+ 过载空口 + 同通话内切换；TTFT 用录屏音频 VAD 测，本机 PyAV/cv2/scipy 已能全自动算。**
