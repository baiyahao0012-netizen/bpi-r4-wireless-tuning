# L2 AI 传输演示：反馈机制 + 两个调度器（真机实现）

日期：2026-11-24
目标：把 `ns3-agent-dev_l2/contrib/genai` 里的三个核心机制在**我们的真实链路**上实现并演示——不是仿真，是可跑的程序。

---

## 1. 拓扑与协议

```
Pi 5 (wlan1 90:de:80:1c:6a:7a)  --Wi-Fi-->  BPI-R4 AP (L2 bridge)  --Eth-->  笔记本 (40:c2:ba:52:70:95)
      l2_ai_client.py                                                          l2_ai_server.py (scapy+Npcap)
```

- 复用我们自己的 12 字节 shim（`!BBHHBBHH`）+ CRC，`tools/l2_ai_common.py`；
- EtherType：`0x88B6` AI 文本、`0x88B7` bulk 干扰、`0x88B8` ACK；
- 记录头 `!IHHQI`：msg_id、kind、plen、t0_ns、flags；时间戳随记录携带（对应 t0/t3 观测点）。

## 2. 三个机制的实现位置

| 机制 | 仿真里的对象 | 真机实现 | 说明 |
|---|---|---|---|
| 反馈 | `ai-text-reliability` + `AiClientApplication` 的 trace 回调 | `l2_ai_client.py` 的 outstanding 表 + ACK/超时 | 本地丢弃立即补发；无反向 NACK；ACK 退订；最多 8 次；服务端按 msg_id 去重 |
| 入队调度（quota 准入） | `QuotaWifiQueueScheduler::HasToDropBeforeEnqueue` | `Scheduler.enqueue()` 的 quota 分支 | 按字节公平份额；`MinPerFlow` 保底；队满时驱逐超标流最老帧；控制帧不参与 |
| 出队调度（AI-first） | `AiFirstWifiQueueScheduler::GetPriority` + AI 驱逐 | `Scheduler.pop()` 的 ai-first 分支 + `_evict_bulk()` | AI 流优先级 0；同流 FCFS；AI 到达时可驱逐 bulk 队头 |

**为什么在用户态而不是内核**：mt76 的 MAC 队列在驱动/固件里，用户态无法改其逐包顺序。本实现把队列放在应用层（等价于他们设计里的 TC/应用边界），并用令牌桶把发送速率压到链路容量以下，使**这个队列成为瓶颈**——这正是策略应当生效的工作点。

## 3. 实测结果

四臂（各 10 s，AI 每 100 ms 一次请求，bulk 40 Mbps 压满，发送速率 20 Mbps，队列容量 200 包）：

| 模式 | 送达 | TTFT p50 | TTFT p95 | 重传 | 驱逐 |
|---|---|---:|---:|---:|---:|
| fifo（基线） | 100/100 | **77.1 ms** | 92.2 ms | 0 | 0 |
| quota（仅入队） | 100/100 | 75.5 ms | 97.2 ms | 2 | 0 |
| **ai-first（仅出队）** | 100/100 | **9.7 ms** | 46.1 ms | 5 | 0 |
| **both** | 100/100 | **8.4 ms** | 47.5 ms | 3 | 0 |

- **出队调度把 p50 从 77.1 ms 压到 9.7 ms（约 8 倍）**，p95 从 92.2 ms 降到 46.1 ms；
- 送达率四臂均 100%，因为**反馈机制在兜底**——这正是设计意图：可靠性由反馈保证，调度器决定时延；
- quota 单独不改善 TTFT：它只保证 AI 能入队，入队后仍排在 bulk 后面（FCFS），所以需要出队调度配合。

反馈专项（无 bulk，注入 30% 本地丢包）：

| 指标 | 结果 |
|---|---|
| 请求 / 送达 | 100 / **100** |
| 重传次数 | 29 |
| TTFT p50 / p95 | 7.7 / 28.4 ms |

去重专项（服务端注入 40% ACK 丢失 + 40% 响应丢失，客户端超时重发）：

| 指标 | 结果 |
|---|---|
| 服务端收到请求 | 114（其中 **14 个重复**） |
| 唯一请求（去重后） | 100 → 每个只触发一次推理 |
| 客户端送达 | 84/100（响应重发机制仍在完善，见限制） |

## 4. 与仿真的对齐关系（保真度）

| 机制 | 对齐程度 | 差异 |
|---|---|---|
| 反馈（本地丢弃→立即补发） | 语义一致 | 仿真用 MAC trace（`DroppedMpdu`/`DropBeforeEnqueue`），真机用"队列自身丢弃 + ACK 超时"；空中丢包只能靠 ACK 超时发现（多一个 RTT） |
| quota 准入 | 语义一致 | 仿真在 500 包 MAC 队列上；真机在用户态队列（200 包）上；内核侧真正的 per-flow 准入需 eBPF/custom qdisc |
| AI-first 出队 | 语义一致 | 仿真在 MAC 容器队列；真机在用户态发送队列；若内核队列成为瓶颈（不限速发送）则本调度失效——所以必须限速 |

## 5. 复现

```bash
# 笔记本（服务端，无需管理员）
python tools/l2_ai_server.py --seconds 40 --out srv.json

# Pi（客户端，需要 root 以便 AF_PACKET）
sudo python3 tools/l2_ai_client.py --mode both --dst-mac 40:c2:ba:52:70:95 \
  --seconds 10 --rate-mbps 20 --bulk-mbps 40 --qcap 200 --csv both.csv
# 四臂：--mode fifo|quota|ai-first|both
# 反馈专项：--ai-drop 0.3
```

## 7. 限制与下一步

1. **响应方向的重传还不完整**：服务端只对"已发出但未 ACK"的响应重发，对"被注入丢弃、从未发出"的响应没有补发——这是去重专项送达 84% 的原因，需修。
2. **内核侧落地**：当前队列在用户态。下一步用 TC（HTB/CAKE + cls_flower）在 Pi 出口复现 quota，用 AP 的 per-STA AQL + airtime weight 做 MAC 层对照。
3. **仿真列**：ns-3 侧尚未构建（P0 未跑），所以上表只有真机列，没有"仿真 vs 实物"对比。
4. **单 STA**：AI 与 bulk 共用 Wi-Fi STA，因此只能验证"同队列内的调度"；跨 STA 的 airtime 权重实验需要第二个 STA（笔记本 Wi-Fi 切到 BPI-R4-5G，当前该 SSID 不可见，待排查）。
