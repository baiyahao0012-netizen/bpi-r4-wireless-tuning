# 流式视频 + 同步问答（L2 直发，2026-11-25）

## 1. 场景

```
Pi（720p24 视频帧）──0x88B5 分片(1500B)──► AP ──有线──► 笔记本
Pi（第 5/10/… 秒的问题，绑定 frame_idx）──0x88B6──► AP ──► 笔记本
笔记本：重组 → 取该帧 → Ollama qwen3-vl:2b → 首个 token 立即回传
笔记本 ──0x88B6 答案流(first/delta/final)──► AP ──无线──► Pi（记 t3）
网页：左=MJPEG 实时画面；右=问题/回答滚动；顶=帧数/丢帧/队列
```

## 2. 协议

| 类型 | 内容 |
|---|---|
| `0x88B5` | 视频分片：`frame_idx u32 | pts_us u64 | frag_idx u16 | frag_total u16 | plen u16 | jpeg`，帧长 1500 B |
| `0x88B6` | 问题 `Q01{qid,frame_idx,pts_us,t0_ns,text}` / 答案 `A01{qid,seq,flags,t2_ns,text}` |

**帧长更正**：2296 B 在本路径不可用（`send()` 报 `EMSGSIZE`，MTU=1500），实测 1500 B 可通，故按 1500 B 分片（平均 ~52 片/帧）。

## 3. 运行方式

```bash
# 笔记本（接收 + 网页 + 模型）
python tools/video_rx_web.py --seconds 150 --port 8080 --ledger rx.jsonl
# 浏览器打开 http://127.0.0.1:8080/  （左 MJPEG，右问答流）

# 树莓派（帧已用 ffmpeg 抽到 /tmp/vframes，24 fps）
sudo python3 /tmp/video_tx.py --loop 1 --seconds 122 --preload --out tx.json
```

## 5. 已处理的问题

1. **模型冷加载**：首轮 0 答案，因 VLM 首次加载超过窗口；已加 warmup 请求。
2. **120 s 问题越界**：问题映射到 frame 2881，超过 2880；已改为末帧触发。
3. **结尾答案截断**：发送结束后等待 8 s 收尾（30 s 短测仍有 1 条超出，需按实际调大）。
4. **ledger 编码**：Windows 默认 gbk 导致读取失败，已固定 `encoding="utf-8"`。
5. **网页验证**：`/` 200（1.9 ms）、`/stream.mjpg` 200、`/events` SSE 正常。

## 6. 限制与下一步

- TTFT 主要花在 **prompt_eval（~0.7 s，1100 tokens）**，可降分辨率或裁图；
- 端到端随时间从 0.72 s 涨到 1.96 s：需补 `t1−t0`（问题上行）与 `t3−t2`（答案下行）的逐问记录，区分模型/链路；
- 命中率判分粗糙，需按参考答案人工抽查；
- 视频上行 13.3 Mbps，与回答下行共用射频；后续可加背景流测调度器；
- 若要 4–6 分钟循环（48–72 问），用 `--loop 2/3` 并延长接收窗口。

## 10. 丢包开关与答案反馈（2026-11-25 晚）

### 10.1 页面开关

顶部新增勾选框 **"模拟丢包30%"**：勾选后 `POST /config {"loss":0.3}`，笔记本在发送答案帧时按概率丢弃（模拟空口丢包）；顶部实时显示 `丢/重传/确认` 计数。

### 10.2 反馈机制

- 答案帧带 `(qid, seq)`；Pi 收到后回 **累积 ACK**（`0x88B8`，每 20 ms 一次、发 3 份冗余，确认 `seq ≤ N`）；
- 笔记本维护 `outstanding`，超时 400 ms 重传，最多 8 次；成功收到 ACK 则清除。

### 10.3 实测（30 s × 6 问）

| 指标 | loss=0 | loss=0.3 |
|---|---:|---:|
| 答案帧发送 | 122–130 | 102–139 |
| 模拟丢弃 | 0 | **50（≈33%）** |
| 重传 | 56–64 | 87 |
| 确认 | 58–59 | 57 |
| 首答到达 Pi | **6/6** | **6/6** |
| 空答案 | 0 | 0 |

**结论**：30% 丢包下首答仍 6/6 到达，说明重传路径有效；但确认率只有 ~45%，导致重传与 `ans_failed` 偏高——ACK 截获/解析是当前瓶颈（每帧 ACK 与 2000 pps 视频流争抢截获缓冲）。

### 10.4 回答加长

prompt 改为"用2到3句话回答，说明判断依据，40–80字"，`/no_think` 前置，`num_predict=400`。实测答案 37–85 字、`eval_count` 109–195、**0 空答案**；代价是 TTFT 升至 1.3–2.6 s（冷启动首问 4.9–5.7 s）。

### 10.5 待修

1. ACK 专用截获（独立 filter/线程或减少视频分片竞争），把确认率提到 >95%；
2. 或者改为只对 `first/final` 帧做可靠重传、delta 容忍丢失；
3. 丢包率可做成滑杆（0/10/30/50%）。

## 11. 左栏无画面的修复

**现象**：点击开始后左栏空白，但后端 `/stream.mjpg` 有数据、帧数在涨。

**原因**：页面加载时 MJPEG 流已建立，但当时还没有任何帧；浏览器把这次 `<img>` 加载判为失败后不会自动重试。

**修复**：
1. `/stream.mjpg` 连上后**先发一张 1×1 占位 JPEG**，保证 `<img>` 首次加载成功；
2. 每轮 `reset` 事件时给 `<img>` 换新 URL（cache-buster）重新拉流；
3. `onerror` 每秒自动重试。

**验证**：`/stream.mjpg` 首包为 `--frame` + 合法 JPEG（FFD8 开头，571 字节）；页面含 `/stream.mjpg?r=` 刷新逻辑。

另外这一轮累计 ACK 生效：`ans_acked=62/62、retx=0、failed=0`，说明冗余+累积 ACK 的修复有效。
