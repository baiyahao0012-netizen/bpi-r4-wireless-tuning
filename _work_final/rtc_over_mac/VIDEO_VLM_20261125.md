# 流式视频 + 同步问答（L2 直发，2026-11-25）

## 1. 场景

```
Pi（720p24 视频帧）──0x88B5 分片(1500B)──► AP ──有线──► 笔记本
Pi（第 5/10/… 秒的问题，绑定 frame_idx）──0x88B6──► AP ──► 笔记本
笔记本：重组 → 取该帧 → Ollama qwen3-vl:2b → 首个 token 立即回传
笔记本 ──0x88B6 答案流(first/delta/final)──► AP ──无线──► Pi（记 t3）
网页：左=MJPEG 实时画面；右=问题/回答滚动；顶=帧数/丢帧/队列
```

## 2. 协议

| 类型 | 内容 |
|---|---|
| `0x88B5` | 视频分片：`frame_idx u32 | pts_us u64 | frag_idx u16 | frag_total u16 | plen u16 | jpeg`，帧长 1500 B |
| `0x88B6` | 问题 `Q01{qid,frame_idx,pts_us,t0_ns,text}` / 答案 `A01{qid,seq,flags,t2_ns,text}` |

**帧长更正**：2296 B 在本路径不可用（`send()` 报 `EMSGSIZE`，MTU=1500），实测 1500 B 可通，故按 1500 B 分片（平均 ~52 片/帧）。

## 3. 运行方式

```bash
# 笔记本（接收 + 网页 + 模型）
python tools/video_rx_web.py --seconds 150 --port 8080 --ledger rx.jsonl
# 浏览器打开 http://127.0.0.1:8080/  （左 MJPEG，右问答流）

# 树莓派（帧已用 ffmpeg 抽到 /tmp/vframes，24 fps）
sudo python3 /tmp/video_tx.py --loop 1 --seconds 122 --preload --out tx.json
```

## 10. 丢包开关与答案反馈（2026-11-25 晚）

### 10.1 页面开关

顶部新增勾选框 **"模拟丢包30%"**：勾选后 `POST /config {"loss":0.3}`，笔记本在发送答案帧时按概率丢弃（模拟空口丢包）；顶部实时显示 `丢/重传/确认` 计数。

### 10.2 反馈机制

- 答案帧带 `(qid, seq)`；Pi 收到后回 **累积 ACK**（`0x88B8`，每 20 ms 一次、发 3 份冗余，确认 `seq ≤ N`）；
- 笔记本维护 `outstanding`，超时 400 ms 重传，最多 8 次；成功收到 ACK 则清除。

### 10.3 实测（30 s × 6 问）

| 指标 | loss=0 | loss=0.3 |
|---|---:|---:|
| 答案帧发送 | 122–130 | 102–139 |
| 模拟丢弃 | 0 | **50（≈33%）** |
| 重传 | 56–64 | 87 |
| 确认 | 58–59 | 57 |
| 首答到达 Pi | **6/6** | **6/6** |
| 空答案 | 0 | 0 |

**结论**：30% 丢包下首答仍 6/6 到达，说明重传路径有效；但确认率只有 ~45%，导致重传与 `ans_failed` 偏高——ACK 截获/解析是当前瓶颈（每帧 ACK 与 2000 pps 视频流争抢截获缓冲）。

### 10.4 回答加长

prompt 改为"用2到3句话回答，说明判断依据，40–80字"，`/no_think` 前置，`num_predict=400`。实测答案 37–85 字、`eval_count` 109–195、**0 空答案**；代价是 TTFT 升至 1.3–2.6 s（冷启动首问 4.9–5.7 s）。

### 10.5 待修

1. ACK 专用截获（独立 filter/线程或减少视频分片竞争），把确认率提到 >95%；
2. 或者改为只对 `first/final` 帧做可靠重传、delta 容忍丢失；
3. 丢包率可做成滑杆（0/10/30/50%）。

## 11. 左栏无画面的修复

**现象**：点击开始后左栏空白，但后端 `/stream.mjpg` 有数据、帧数在涨。

**原因**：页面加载时 MJPEG 流已建立，但当时还没有任何帧；浏览器把这次 `<img>` 加载判为失败后不会自动重试。

**修复**：
1. `/stream.mjpg` 连上后**先发一张 1×1 占位 JPEG**，保证 `<img>` 首次加载成功；
2. 每轮 `reset` 事件时给 `<img>` 换新 URL（cache-buster）重新拉流；
3. `onerror` 每秒自动重试。

**验证**：`/stream.mjpg` 首包为 `--frame` + 合法 JPEG（FFD8 开头，571 字节）；页面含 `/stream.mjpg?r=` 刷新逻辑。

另外这一轮累计 ACK 生效：`ans_acked=62/62、retx=0、failed=0`，说明冗余+累积 ACK 的修复有效。

## 12. 统一反馈模块（与仿真同构，2026-11-25 晚）

新增 `tools/reliable.py`，两条路径共用同一套语义：

| 仿真机制 | 实现 |
|---|---|
| Store before send | `add()` 先入缓冲再发首包 |
| `AckedMpdu` | 逐块 ACK：`cum_seq + 32-bit bitmap`（3 份冗余、20 ms） |
| `kMaxResendsPerChunk=8` | `max_sends=9`（初始 + 8 次） |
| 缓冲深度 64 | `--buffer-depth 64`，超限淘汰最老未确认块 |
| `deadline/Expired` | 发送次数耗尽 → `expired` |
| 逐块账本 | `<ledger>.chunks.jsonl`：`acked/expired/evicted` + attempts + RTT |

### 12.1 验证（30 s × 6 问）

| 指标 | loss=0 | loss=0.3 |
|---|---:|---:|
| 答案块（去重） | 61 | ~64 |
| 确认 | 55 | 60 |
| 过期 | 6 | 4 |
| 重传 | 48 | 49 |
| 注入丢弃 | 0 | 26 |
| 首答到达 Pi | **6/6** | **6/6** |
| 空答案 | 0 | 0 |

**账本恒等式**：`发送次数 = 块数 + 重传`、`块数 = 确认 + 过期 + 淘汰 + 在途`，逐块可对。

### 12.2 残余问题

- **0% 注入丢包下仍有 6/61 过期**：ACK 帧在 2000 pps 视频流下被截获缓冲丢弃（~90% 到达率），不是空口丢包；
- 下一步：ACK 用独立 pcap 句柄/线程，或在 AP 侧镜像；也可把 bitmap 扩到 64 位降低 ACK 频率。

**结论**：反馈语义已与仿真同构（逐块确认、上限 8、深度 64、deadline、账本），30% 丢包下首答仍 6/6；ACK 截获是工程残余，不影响语义正确性。

## 14. 调度面板与效果指标（2026-11-25 晚）

### 14.1 页面控件

- 下拉：`调度:关 / fifo / ai-first / quota`
- 数字框：背景流 Mbps（默认 20）+ "应用" 按钮（`POST /sched`）
- 顶栏实时显示：`[模式 深N 越队N 驱逐N ai/bulk A/B]`

### 14.2 实现

- 答案帧与大模型响应仍走 `ReliableBuffer`；调度开启时 `on_send` 改为入队；
- `drain_loop` 按 `--sched-rate-mbps` 令牌桶发送；
- `bulk_loop` 以 `bulk_mbps` 生成 1400 B 背景帧（`0x88B7`）；
- `fifo` 按插入序、`ai-first` 优先 AI 队列并计 `ai_jump`、`quota` 额外在超容量时驱逐最老 bulk；
- 队列深度上限 `--sched-capacity`（默认 500），超出丢最老 bulk 并计 `evicted`；
- 每次 `/start` 重置队列与调度计数。

### 14.3 实测（ai-first，rate 30 Mbps，bulk 40 Mbps，60 s）

| 指标 | 值 |
|---|---|
| 队列深度 | 35（有界） |
| AI 越队 | 34 次 |
| 发送 ai/bulk | 43 / 58,695 |
| ACK | 43/43，补救率 100% |
| TTFT p50 | 1.78 s（模型为主） |
| 帧率 | 24–26 fps |

### 14.4 注意

- 深度积压极大时（rate 10 vs bulk 20、无上限），`fifo` 下答案帧排在数万 bulk 帧后，超过 400 ms RTO 触发大量重传并最终 `expired`——这是真实的"饥饿"现象，不是 bug；
- 因此调度对照应使用有界队列（`--sched-capacity`）与合理 drain 速率；
- 当前 AI 流是**答案帧**（真实），bulk 是合成背景流；与之前 S1–S6 的调度实验口径一致（应用层队列）。

## 15. 左栏"开始后没画面、刷新才有"的最终修复

**根因**：MJPEG 是长连接；页面加载时流里还没有帧（只有占位图），浏览器保持这条"已建立但无新帧"的连接，开始推流后不会重新解码更新。

**修复**：改用**逐帧拉取**：

- 新增 `GET /frame.jpg`：始终返回当前最新帧（无帧时返回 1×1 占位图），`Cache-Control: no-store`；
- 页面每 50 ms 用 `new Image()` 预加载 `/frame.jpg?t=...`，`onload` 后替换 `<img>`，避免闪烁；
- `reset` 时也立即拉一帧。

**验证**：`/frame.jpg` 返回 `200 image/jpeg`；连续两次请求字节数 76,322 / 76,764 且哈希不同，说明画面实时更新；开始后无需刷新即可显示，停止按钮正常。
