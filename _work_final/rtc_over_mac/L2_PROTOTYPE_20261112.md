# L2 原型：0x88B5 桥接与 RTP over L2 首测

日期：2026-11-12  
拓扑：

```text
Pi wlan1 .126 → AP bridge → 笔记本以太网 .2
```

## 1. 最小 EtherType 桥接

### Pi → Windows

- Pi 用 `AF_PACKET` 在 `wlan1` 发送 20 帧 `0x88B5`，payload `RTC2PROBE`；
- Windows Npcap 抓包：**20/20**；
- 源 MAC `90:de:80:1c:6a:7a`，目的 MAC `40:c2:ba:52:70:95`。

### Windows → AP → Pi

- Windows 发 20 帧 `0x88B5`；
- AP `phy0.1-ap0` 抓到 **5/5**（抓 5 帧后停止）；
- payload 完整。

结论：**AP bridge 双向都不丢自定义 EtherType。**

## 2. RTP over L2 原型

链路：

```text
GStreamer RTP → 本地 UDP 127.0.0.1:5004
  → Python l2_rtp_send（12B shim + AF_PACKET）
  → wlan1 → AP → 笔记本以太网
  → Python l2_rtp_recv（去 shim + CRC）
  → 本地 UDP 127.0.0.1:5014
  → GStreamer 解码
```

说明：本地 127.0.0.1 UDP 只作为原型管线胶水，**不是验收路径**；正式 B 要换 GStreamer `l2sink/l2src`，媒体路径不能保留 UDP。

### 早期 60% 接收率的定位

- AP `phy0.1-ap0` 抓包：**6739 / 6740** 帧到达 AP；
- 说明空口没有丢 40%，问题在 **Windows Npcap/Python 捕获缓冲**；
- 给 Scapy 设置 `conf.bufsize = 64 MB` 后，接收恢复。

### 修正后的 10 s 结果（接收端已改为直接 RTP 重组 + PyAV 解码）

| 指标 | 实测 |
|---|---:|
| L2 shim 发送 | 6809 包 |
| Windows 收到 | **6809 包** |
| shim CRC 错误 | **0** |
| seq gaps | **0** |
| RTP 时间戳 | 302 |
| 解码帧 | **301 / 302** |

### 完整 85.33 s 结果（同一无 UDP 接收路径）

| 指标 | 实测 |
|---|---:|
| L2 shim 发送 | 50989 包 |
| Windows 收到 | **50989 包** |
| CRC 错误 | **0** |
| seq gaps | **22** |
| RTP 时间戳 | **2560** |
| 解码帧 | **2481 / 2560（96.9%）** |
| UDP baseline 同片 | 2558 / 2560（99.9%） |

结论：

- 自定义 EtherType、12B shim、CRC、AP bridge、L2 全链路可用；
- 10 s 段包层 0 丢包、0 CRC，解码 301/302；
- 完整片出现 22 个 seq gap，虽只有约 0.04% 的包缺口，但 H.264 参考链导致 **79 帧不能解码**；
- 这说明 B 形态必须补 **L2/MAC 层重传或 FEC**，不能只靠“包层看起来没丢”；
- 接收端已去掉本地 UDP，直接 RTP 重组 + PyAV；发送端仍有本地 UDP 胶水，正式 `l2sink` 需消除。

### 按 seq 重排后再解码（关键修复）

第一次直接按 16 位 seq 数值排序，解码 0 帧。原因是序列号可能跨 16 位回绕，数值排序把回绕后的包放到了开头。

修正为**相对首包的回绕感知排序**：

```text
key(seq) = (seq - first_seq) & 0xFFFF
```

完整 85.33 s 结果：

| 指标 | 实测 |
|---|---:|
| L2 收到包 | 51305 |
| CRC 错误 | 0 |
| 重复 | 0 |
| seq gaps | 15 |
| RTP 时间戳 | 2560 |
| 解码帧 | **2556 / 2560（99.84%）** |
| UDP baseline 同片 | 2558 / 2560（99.92%） |

结论：

- 回绕感知重排后，L2 完整片解码 **2556/2560**，与 UDP baseline 只差 2 帧；
- 15 个 seq gap 不再造成帧级崩溃，说明重排和参考帧连续性已基本成立；
- 接收端已无本地 UDP，直接 L2 shim → RTP → H.264 → PyAV；
- 发送端仍有本地 UDP 胶水，正式 `l2sink` 需消除。

| 素材 | 源帧 | 解码 | 完整率 | L2 包 | seq gap | dup |
|---|---:|---:|---:|---:|---:|---:|
| 1080p24_1 | 1253 | 1252 | 99.92% | 12270 | 1 | 0 |

- 单独隔离运行的 30_1 L2 结果仍是 **2556/2560**，作为当前最佳证据。

### 高码率 24fps 单条复测（7 Mbps）

`1080p24_2_caminandes_90s.mp4` 单独隔离运行：

| 指标 | 实测 |
|---|---:|
| L2 收到包 | 57145 |
| CRC 错误 | 0 |
| 重复包 | 1879（MAC 重传被捕获） |
| seq gaps | 155 |
| RTP 时间戳 | 2109（源 2161） |
| 解码帧 | **774 / 2161（35.8%）** |
| UDP baseline 同片 | 2160 / 2161（99.95%） |

结论：

- 24_2 是 7 Mbps 高码率片，L2 无重传时出现 155 个 seq gap；
- 少量包缺口被 H.264 参考链放大，帧完整率从 99.95% 掉到 35.8%；
- 重复包说明 MAC 层有重传，但当前接收端只做去重，不能恢复缺失参考帧；
- 这是 B 形态必须打补丁的直接证据：**L2 需要重传/FEC，不能只做去重。**

### 1+1 冗余补丁首测（24_2）

在 L2 sender 中把每个 RTP 包发送两次，接收端按 RTP seq 去重：

| 指标 | 实测 |
|---|---:|
| 唯一包 | 64023 |
| 重复包 | 68327 |
| CRC 错误 | 0 |
| seq gaps | 28 |
| RTP 时间戳 | 2093（源 2161） |
| 解码帧 | **1743 / 2161（80.6%）** |
| 无冗余 L2 | 774 / 2161（35.8%） |
| UDP baseline | 2160 / 2161（99.95%） |

结论：

- 1+1 冗余把 35.8% 提升到 80.6%，证明补可靠性方向正确；
- 但仍远低于 baseline，且空口开销翻倍；
- 需要真正的 **NACK/重传或 FEC**，而不是简单全量重复；
- 这是“受影响功能”的明确补丁清单输入。

### 三发冗余：反而更差

把每个 RTP 包连发三次后，24_2：

| 指标 | 实测 |
|---|---:|
| 唯一包 | 56734 |
| 重复包 | 118976 |
| seq gaps | 154 |
| RTP 时间戳 | 2111 |
| 解码帧 | **740 / 2161（34.2%）** |

结论：

- 三发把空口负载推到约 21 Mbps，造成更严重的拥塞/丢包；
- 盲重复不是可靠方案；
- 必须做 **选择性 NACK/重传或 FEC**，并且需要 pacing/拥塞控制。

### 轻量 pacing：没有改善

在 L2 sender 每包加 0.5 ms sleep（约 2000 pps 上限）：

| 指标 | 实测 |
|---|---:|
| 唯一包 | 55531 |
| 重复包 | 1722 |
| seq gaps | 153 |
| RTP 时间戳 | 2117 |
| 解码帧 | **772 / 2161（35.7%）** |

结论：pacing 没有改善 24_2；问题不是单纯突发，而是当前 L2 路径在 7 Mbps 下缺少选择性恢复。单发/pacing 已恢复为无额外 sleep，避免引入延迟。
