**UDP baseline 已经完成并冻结；L2 在 5 Mbps 片源上已接近 baseline，但 7 Mbps 高码率片源因缺少选择性重传/FEC 而失败，B 形态尚未验收。**

## 三、尚未完成的部分

### 1. L2 高码率失败

`24_2`（7 Mbps，90 s）：

```text
UDP baseline：2160 / 2161 = 99.95%
L2 无冗余：774 / 2161 = 35.8%
L2 1+1 双发：1743 / 2161 = 80.6%
L2 三发：740 / 2161 = 34.2%
L2 pacing：772 / 2161 = 35.7%
```

结论：

- 盲重复、三发、pacing 都不是有效补丁；
- 7 Mbps 下 L2 出现 153–155 个 seq gap；
- 少量包缺口被 H.264 参考链放大成大量帧损失；
- 必须做**选择性 NACK/重传或 FEC**。

### 2. 六片 L2 矩阵未冻结

尝试过自动六片矩阵，但出现：

- 24_1：1252/1253；
- 25_3：811/812；
- 24_2：621/2161（矩阵中）；
- 30_1：2440/2560（矩阵中，单独运行是 2556）；
- 重复包、旧 sender、捕获状态污染导致结果不可信。

所以六片 L2 不能冻结。

### 3. 正式 `l2sink/l2src` 未实现

当前是 Python 原型：

- 接收端已无 UDP；
- 发送端仍有本地 `127.0.0.1 UDP` 胶水；
- 这不满足正式 B 验收路径。

### 4. RTCP/SRTP/A-V 未接

- 未在 L2 上跑 RTCP SR/RR；
- 未做 L2 SRTP；
- 未做 A/V sync；
- 跨机时钟未纳入。

### 5. L0 残留

- T7 NACK/PLI/RTX 本地闭环未完成；
- 六片 UDP 的严格 11761/11761 未达到（每片差 1–2 帧尾部）；
- 不影响当前传输 baseline，但仍是媒体层完整性缺口。

## 五、核心问题分析

现在的瓶颈不是“L2 能不能承载 RTP”，而是：

> **L2 没有选择性恢复机制，H.264 参考链把少量丢包放大成帧级崩溃。**

这正好对应研究背景里的判断：

- 去掉 UDP/IP 后，可靠性不能消失；
- MAC 重传不够，因为当前只看到重复包，不能恢复缺失参考帧；
- 需要跨层可靠性：NACK/重传、FEC、pacing、拥塞控制；
- 不能靠盲重复，三发已经证明会恶化。

## 六、下一步建议

### 优先级 1：NACK/选择性重传

```text
shim control 类型
→ 发送端缓存最近 RTP
→ 接收端检测 seq gap
→ 发 NACK
→ 发送端只重传缺失包
```

目标：24_2 从 35.8% 提升到 ≥99%。

### 优先级 2：FEC

如果 NACK 在 RTT/突发下不够，再加 XOR/ULPFEC。

### 优先级 3：正式 `l2sink/l2src`

去掉 Pi 侧本地 UDP 胶水，满足 B 验收路径。

### 优先级 4：六片 L2 矩阵

先落 pcap 再离线解析，避免 Npcap 实时捕获重复/过载。

### 优先级 5：RTCP/SRTP/A-V

在 L2 稳定后接入，再做影响矩阵、补丁和 B 验收。

---

## 七、需要你拍板的事

1. **先做 NACK 还是先做 FEC？**  
   建议先 NACK，针对 24_2 的 155 个缺口，开销最低。

2. **B 验收是否必须用正式 GStreamer `l2sink/l2src`？**  
   如果必须，当前 Python 原型只能算功能验证，不能算最终 B。

3. **六片 L2 是否接受 pcap 离线解码作为正式结果？**  
   当前实时 Npcap 捕获在矩阵中有重复/过载，离线更稳。

你确认“先做 NACK、正式元素必须做”后，就可以从 L2 control 帧和发送端缓存开始落地。
