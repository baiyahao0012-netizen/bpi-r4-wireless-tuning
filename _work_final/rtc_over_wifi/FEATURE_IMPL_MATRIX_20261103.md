# 特性实现方法对照表（样机能力矩阵）

> 2026-11-03。回应课题组指导：对每个特性，明确「只改配置 / 改应用 / 改源码重编 / 需固件」分别能做到什么程度。
> 表中标 ✅ 的为本样机已实测验证，标 ⚠️ 的为已确认接口存在但未做端到端验证，标 ❓ 的为待定位确认。

---

## 0. 方法论：四级实现阶梯

| 级别 | 手段 | 生效时间 | 回滚成本 | 适用场景 |
|---|---|---|---|---|
| **L0 配置** | uci / nft / iw / tc / debugfs 写入 | 秒级 | 重启即恢复 | 先穷尽这一层，能解决就不动源码 |
| **L1 应用层** | 改用户态协议、封包、调度 | 分钟级 | 换二进制 | RTC 层本身的绝大多数功能 |
| **L2 源码重编** | 改 mac80211 / mt76 / 内核，重编模块部署 | 10 分钟~1 小时 | 保留旧模块 | L0/L1 做不到的 MAC 层行为 |
| **L3 固件** | MT7996 固件、硬件队列 | 不可行 | — | 需厂商支持，暂不碰 |

**工作流（课题组建议的"对照源码 + 真机实验"）：**

```
1. 在 SDK 源码里 grep 定位开关           → 确认它属于 L0 还是 L2
2. 在真机上用 L0 试，记录能做到什么       → 得到"配置级能力边界"
3. 若不够，改源码重编模块 + 部署 + 验证   → 得到"源码级能力边界"
4. 把两条边界写回本表                     → 形成可复用的结论
```

这套循环在本样机上已经跑通过多次（EDCA、WDRR、tracepoint 都是这样落地的），是成熟路径。

## 5. 两个必须提前解决的技术细节

### 5.1 回环必须只收入向

拓扑是 **PC(Wi-Fi) → AP → hairpin → 同一 PC(Wi-Fi)**，所以帧的 `src MAC = dst MAC = 本机`。
Npcap 会同时抓到**发出的副本**和**收回的副本**，两者内容完全相同，靠 MAC 分不开。

**必须用 `pcap_setdirection(handle, PCAP_D_IN)` 只收入向**，否则到达时间戳会被发送副本污染，q(i) 全废。

scapy 不直接暴露这个调用，需要用 ctypes 调 `wpcap.dll`。

### 5.2 同机收发会自竞争

同一块 Wi-Fi 网卡先发后收，是半双工。这**恰好真实反映了中继的信道行为**（两个发射机交替占用），但会带来两个影响：
- 有效吞吐约为单向的一半
- 本机 TX/RX 切换开销

**对策**：把它当作"中继惩罚"如实建模，而不是当作测量误差。
