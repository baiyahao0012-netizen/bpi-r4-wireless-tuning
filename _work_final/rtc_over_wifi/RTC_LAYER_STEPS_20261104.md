# RTC 层实现方案（分步骤）

> 2026-11-04。范围：**只加 RTC 层**。不改内核、不改板子、不碰 MAC 特性。
> 现有 L2 通路（AF_PACKET + 0x88B5）已经是"去 UDP/IP"状态，直接在其上补 RTC 层。

---

## 0. 边界

| 做 | 不做 |
|---|---|
| RTC2 封包、帧边界、时间戳 | 不改 mac80211 / mt76 / 内核 |
| 抖动缓冲、音视频同步 | 不动板子配置（板子只做桥中继） |
| 反馈通道 | 不做 AQL / WDRR / EDCA 调优 |
| GCC 码率自适应 | 不做选择性重传的 MAC 层部分 |
| 真实摄像头 + 麦克风采集 | 不做 AI 差异化传输 |

数据通路（板子仅中继，上下行都走 Wi-Fi）：

```
PC 摄像头/麦克风 → 编码 → RTC2 封包 → Wi-Fi 发出
                                          ↓
                              板子 AP（桥 hairpin 转发）
                                          ↓
PC Wi-Fi 收到 → 重组 → 抖动缓冲 → 同步 → 解码显示
                                          ↓
                                   反馈帧（50ms）
```

## 1. RTC2 帧格式（28 字节）

```c
struct rtc2_hdr {
    uint32_t magic;        /* "RTC2" */
    uint8_t  type;         /* 0=video 1=audio 2=feedback */
    uint8_t  flags;        /* bit0 FEC奇偶 bit1 关键帧 bit2 帧首块
                              bit3 帧末块 bit4 重传 */
    uint8_t  stream_id;    /* 0=video 1=audio */
    uint8_t  rsv;
    uint16_t seq;          /* 全局递增，丢包检测 */
    uint16_t chunk_idx;    /* 帧内块号 */
    uint16_t chunk_cnt;    /* 帧内总块数 */
    uint16_t payload_len;
    uint32_t frame_id;     /* 帧序号 */
    uint32_t pts;          /* 采集时刻 90kHz，音视频共用时基 */
    uint32_t send_ts_us;   /* 发送时刻 微秒，GCC 基准 */
};
```

- `0x88B5` 数据帧 / `0x88B6` 反馈帧
- 负载 1200 B，头开销 2.3%

反馈帧：

```c
struct rtc_fb {
    uint32_t magic;         /* "FBK1" */
    uint32_t fb_seq;
    uint32_t window_us;
    uint32_t recv_bytes;
    uint32_t q_us;          /* 时延梯度，GCC 主输入 */
    uint16_t loss_permille;
    uint16_t jitter_us;
    uint32_t frames_ok;
    uint32_t frames_lost;
    uint32_t max_frame_id;
    uint16_t rsv;
};
```

## 3. 分步骤实施

### 步骤 1：环境自检（0.5 天）
**做**：确认摄像头/麦克风可打开、PyAV 能编 H.264/Opus、Npcap 能发收自定义 EtherType、`pcap_setdirection` 可用。
**验收**：`env_check.py` 全绿，输出设备名、分辨率、编码器版本。
**风险**：摄像头被占用、Npcap 权限（需管理员）。

### 步骤 2：RTC2 协议层（1 天）
**做**：`rtc2.py` 封包/解析 + 单测。
**验收**：编解码往返一致；边界值（chunk_cnt=0、payload_len=0、seq 回绕）正确；单测全绿。
**交付**：可被收发两端直接 import。

### 步骤 3：发送端（视频单流）（2 天）
**做**：cv2 采集 → PyAV 编码 → 按帧切块 → RTC2 封包 → 按码率 pacing 发出。
**验收**：
- 接收端能重组出完整帧并解码播放
- `frame_id` 连续、`pts` 单调、关键帧标记正确
- 8 Mbps 下发送不丢块
**注意**：必须 pacing，不能一帧所有块一口气发完。

### 步骤 4：接收端 + 重组 + 抖动缓冲（2 天）
**做**：收帧 → 按 `frame_id` 位图重组 → 超时丢弃 → 抖动缓冲 → 按 `pts` 播放。
**验收**：
- 注入乱序/丢块，重组正确率 100%
- 超时帧整帧丢弃，不喂半帧给解码器
- JB 深度自适应收敛，模拟抖动 ±30ms 画面不花
**注意**：`pcap_setdirection(PCAP_D_IN)` 必须生效，否则 TX 副本污染时间戳。

### 步骤 5：反馈通道（1 天）
**做**：接收端每 50ms 算 `q(i)`/丢包/接收速率，发 `0x88B6`；发送端收并去重。
**验收**：50ms 周期稳定；故意丢 30% 反馈帧仍能工作；发送端实时打印 q(i)。

### 步骤 6：GCC 码率自适应（2 天）
**做**：时延梯度（滑动最小基线）→ 趋势估计 → 过载检测（自适应阈值）→ AIMD → 下发码率 → 编码器切换。
**验收**：
- 拥塞注入（背景打流）后 ≤1s 码率下降，撤掉后回升
- 无持续震荡（码率曲线收敛）
- 真实 ABR：编码输出码率跟随目标值，误差 < 20%
**注意**：码率切换点强制关键帧。

### 步骤 7：音频接入 + 音视频同步（2 天）
**做**：麦克风 → Opus 编码 → 复用 RTC2（`stream_id=1`）；接收端双流独立 JB + 共享播放时钟 + 音频主时钟。
**验收**：**ΔAV ≤ 40ms**；注入 ±1% 时钟漂移后 2s 内收敛。
**注意**：同一台机器采集+播放会有声学回授，测量阶段音频输出到空设备。

### 步骤 8：联调与验收（1 天）
**做**：三场景（5G 空闲 / 5G+背景流 / 2.4G）× 指标汇总。
**验收**：完整性 ≥99%、ΔAV ≤40ms、E2E 时延 P95 有数、码率自适应曲线可复现。

## 5. 两个已知技术点

1. **只收入向**：回环拓扑下 `src MAC = dst MAC`，必须 `pcap_setdirection(PCAP_D_IN)`，否则时间戳被发送副本污染。
2. **半双工自竞争**：同一块网卡先发后收，有效吞吐约为单向一半，如实建模为中继惩罚。
