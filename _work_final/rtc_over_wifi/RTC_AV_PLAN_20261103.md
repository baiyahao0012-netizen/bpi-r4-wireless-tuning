# RTC over WiFi → RTC on MAC：音视频自适应传输总体方案

> 版本 2026-11-03。前提：搁置 354/355 补丁相关工作（已合并完成，作为可用的观测能力保留）。
> 本方案的起点是现有 RT-L2（AF_PACKET + 0x88B5 + RTC1 头 + XOR FEC + NACK）的**视频单流、固定码率**实现。

---

## 0. 目标分解

| 阶段 | 目标 | 判定标准 |
|---|---|---|
| G1 | 音视频联合封装 + 音视频同步 | 任一场景下 ΔAV（音画偏移）稳定 ≤ 40 ms |
| G2 | 去掉 UDP/IP，跑通 RTC over WiFi | 单二层域内 A/V 完整传输，无 IP/UDP 封装 |
| G3 | 上行码率自适应（GCC 控制环 + MAC 反馈） | 拥塞时码率收敛 ≤ 1 s，无持续过冲 |
| G4 | RTC on MAC（把状态机融进 MAC） | AC 分类 / AQL / WDRR 与 RTC 状态联动生效 |

**G2 是华为"RTC over MAC"路线，G4 是"RTC on MAC"路线**（见交接文档附录的官方定义）。本方案按 G1→G2→G3→G4 推进，每阶段独立可验收。

## 1. 首先必须解决的一个事实约束

板子上**没有音频设备、没有摄像头、没有编码器**：

```
/proc/asound/cards   -> 空
/dev/snd/*           -> 不存在
/dev/video*          -> 不存在
ffmpeg / x264        -> 未安装
CPU                  -> 4 × Cortex-A53，4 GB RAM
```

这意味着**不能假设"板子接麦克风+摄像头实时采集"**。三条可选路径：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 文件驱动**（推荐起步） | 预编码 H.264 + 预编码 AAC/Opus，按 PTS 节奏"回放"式发送 | 完全可控、可复现、隔离传输层问题 | 不是真实时采集 |
| B. USB 声卡/摄像头 | 插 USB UVC 摄像头 + USB 音频，opkg 装 ffmpeg | 真采集 | 需硬件；A53 软编 640×480@30 勉强 |
| C. PC 侧采集，板子只做转发 | PC 编码后走 L2 发给板子，板子转发 | 编码压力外移 | 板子不再是发送端，链路角色变复杂 |

**建议：A 起步把传输层做扎实，B 作为验收前的"真采集演示"。** 文档里的 18 次对比本来就是文件驱动的，沿用同一口径可比性最好。

### 1.1 接收端也要换

现有接收端是 Windows + Scapy。Scapy 是 Python 逐包解析，**8 Mbit/s 已经接近瓶颈，加入音频+反馈后必然成为新瓶颈**，而且会污染时延测量（用户态调度抖动）。

**建议接收端改为 C 程序**（AF_PACKET/Pcap 直读 + 环形缓冲），ffmpeg 只负责最后解码。这一步不做，后面所有 RTT/时延数据都不可信。

## 2. 帧格式重新设计：RTC1 → RTC2

现有头（20 B）只有 `magic / seq / len / flags / rsv`，缺 5 类必需字段。新设计：

```c
struct rtc2_hdr {          /* 24 字节，8 字节对齐 */
    uint32_t magic;        /* 0x52544332 "RTC2" */
    uint8_t  type;         /* 0=video 1=audio 2=feedback 3=control */
    uint8_t  flags;        /* bit0 parity, bit1 keyframe, bit2 frame_start,
                              bit3 frame_end, bit4 retransmit */
    uint8_t  up;           /* 802.11 User Priority 0..7 -> WMM AC */
    uint8_t  stream_id;    /* 多流区分（0=video 1=audio） */
    uint16_t seq;          /* 每流递增，16 位回绕 */
    uint16_t chunk_idx;    /* 帧内块号 */
    uint16_t chunk_cnt;    /* 帧内总块数 */
    uint32_t frame_id;     /* 帧序号 */
    uint32_t pts;          /* 采集时间戳，90 kHz（音视频共用时基）*/
    uint32_t send_ts_us;   /* 发送时刻，us（GCC 测量用）*/
    uint16_t payload_len;
    uint16_t group_id;     /* FEC 组号 */
};
```

**五个关键新增字段及其作用：**

| 字段 | 解决的问题 |
|---|---|
| `up` | **补上被去掉的 DSCP 通路**。L2 裸帧没有 IP 头，`nft ip dscp set` 失效，`skb->priority` 恒 0，`wifi_dscp` 埋点一个都不触发。必须由应用直接给 UP，映射到 AC_VO/VI/BE |
| `pts` | 音视频共用 90 kHz 时基 → **同步的唯一依据** |
| `send_ts_us` | GCC 的 `send_time`，没有它算不出排队时延 |
| `frame_id / chunk_cnt` | 帧边界。现有实现按"整文件切块"，无法做帧级丢弃/重传/解码启动 |
| `stream_id` | 音频/视频在 L2 上共用 EtherType，必须显式区分 |

**开销**：24 B / (1200+24) ≈ 2%。与 UDP/IP 的 28 B 头相当，但换来的是没有 ARP、没有分片、没有 NAT 开销。

**EtherType 规划**：
- `0x88B5`：数据帧（音视频）
- `0x88B6`：反馈帧（NACK / 时延报告 / 码率建议）
- `0x88B7`：控制帧（会话建立、参数协商）

分 EtherType 而非用 type 字段，是为了接收端能用 BPF 过滤器在内核里直接分流，不必把所有包都拷到用户态。

## 3. 音视频同步设计（G1）

### 3.1 一个被忽略的优势

WebRTC 做 A/V 同步需要 **RTCP SR**：音频和视频是两条独立的 RTP 流，各自用随机 SSRC + 独立时钟，必须靠 SR 里的 NTP/RTP 对映射到同一时间轴，再配合 NTP 同步。

**去掉 IP/UDP 后，这个机制完全不需要**：音频和视频都从**同一个发送端进程**、**同一个单调时钟**出发，`pts` 天生就在同一时基上。这比 WebRTC 简单得多，而且精度更高（不受 NTP 误差影响）。

**这一点值得写进验收材料**——"简化协议栈"不只是省字节，还消掉了一整类同步误差源。

### 3.2 同步算法

接收端每流维护独立抖动缓冲，用一个**共享播放时钟**对齐：

```
1. 缓冲建立期（启动后前 200ms）：
   统计每流 pts 到达偏差，取 P95 作为初始 jitter buffer 深度
   D_play = max(D_video_p95, D_audio_p95) + 安全余量(20ms)

2. 稳态播放：
   T_play(frame) = T0 + (pts - pts0) / 90000 + D_play
   到点才送去解码/播放

3. 偏差监控（每 500ms）：
   ΔAV = (video 实际播放时刻 - audio 实际播放时刻) - (video pts - audio pts)/90000
   若 |ΔAV| > 40ms 持续 1s：
     - 视频落后 → 丢帧追赶（丢到下一个关键帧或直接跳 P 帧）
     - 视频超前 → 插帧/延长前帧显示

4. 时钟漂移：音频为主时钟（audio is master）
   音频设备不可拉伸，视频侧按音频时钟微调（±0.5% 播放速率或丢/重复帧）
```

**主时钟选择**：WebRTC 默认音频为主（人对音频卡顿更敏感）。本方案沿用。

### 3.3 关键设计：同步与拥塞控制解耦

拥塞时如果直接"降码率+丢帧"，会让 ΔAV 抖动。所以：

- **音频永不被 ABR 削减**（Opus 32 kbps 是地板，占总量 <1%）
- **视频码率可调**，但**丢帧必须成组**（同 frame_id 整帧丢，不留半帧）
- **同步控制器只看 pts，不看码率** —— 两条控制回路解耦，否则互相打架

## 4. RTC over WiFi 传输层（G2）

### 4.1 分层结构

```
┌─────────────────────────────────────────┐
│ 应用：H.264 / Opus 帧 + PTS              │
├─────────────────────────────────────────┤
│ RTC 层（本项目核心）                     │
│  ├ 封包：RTC2 头 + 帧边界                │
│  ├ FEC：XOR → 可选 RS/RLNC               │
│  ├ NACK：缓存 + 选择性重传               │
│  ├ 抖动缓冲 + A/V 同步                   │
│  └ 码率控制：GCC 控制环 + MAC 反馈        │
├─────────────────────────────────────────┤
│ L2 适配：AF_PACKET + 0x88B5/B6/B7        │
│          + SO_PRIORITY(up) → WMM AC      │
├─────────────────────────────────────────┤
│ 802.11 MAC（内核，不改）                  │
├─────────────────────────────────────────┤
│ PHY                                      │
└─────────────────────────────────────────┘
```

**这一层就是"RTC over MAC"**：MAC 不动，RTC 在它上面自己实现。

### 4.2 FEC 与码率联动

现有 XOR 8+1 是固定的。建议改为**按丢包率自适应冗余度**：

| 观测丢包率 | FEC 策略 | 冗余开销 |
|---|---|---|
| < 1% | 8+1（现状） | 12.5% |
| 1–5% | 6+2 | 33% |
| 5–15% | 4+3 | 75% |
| > 15% | 降到 3+4，并触发降码率 | 133% |

关键：**FEC 开销要算进码率预算**，否则"有效码率"和"空口占用"对不上，GCC 会误判。

### 4.3 反馈通道（必须早做）

```
接收端 → 发送端（0x88B6，每 50 ms 一次，UP=6/VO）
  ├ NACK 位图（缺哪些 seq）
  ├ 接收速率（过去 500ms 收到多少字节）
  ├ 抖动/时延统计（到达间隔 P50/P95）
  └ 建议码率（接收端侧估算，可选）
```

**抗丢失设计**（拥塞时反馈帧本身会丢）：
- 走 AC_VO，优先级高于视频
- 同一份反馈连发 3 次（不同 seq），发送端去重
- 内容用增量编码，单帧 < 200 B

## 5. 码率自适应（G3）——与上一轮结论一致

### 5.1 为什么不能直接搬 GCC

GCC 是 **delay-based**，测量 `arrival_time − send_time` 的增量。在 802.11 上这个增量混入了：

- CSMA/CA 退避（邻居发流量 → 你的退避窗口被动变大）
- A-MPDU 聚合等待
- MAC 重传（最多 7 次）
- AP 侧下行调度

**这些不是你发太快造成的，但 GCC 会统一归因为"该降速"** —— 这是 GCC 在无线的经典误判。

### 5.2 用 MAC 探针把两类时延拆开

这是本项目的核心技术点，也是"RTC over UDP 做不到、RTC on MAC 才做得到"的实证：

| 观测量 | 来源 | 物理含义 | 该不该降码率 |
|---|---|---|---|
| `DEQ − ENQ` | 354 埋点 | **自己的发送队列积压** | **该**（这是自致拥塞） |
| `ACK − DEQ` | 354 埋点 | 信道接入 + 传输 | 不该（外部竞争） |
| `retry` | 354 埋点 / tx_stats | MAC 重传次数 | 不该（链路质量） |
| `Q depth` | per-STA `aql` | AQL 队深 | 该（缓冲膨胀） |
| `airtime` | per-STA `airtime` | 本 STA 占用信道比例 | 辅助判断 |
| `Tx PER` | mt76 `tx_stats` | 投递率 | 辅助（区分拥塞 vs 弱信号） |

**控制器只用 `DEQ−ENQ` 作为主要拥塞信号**，其余作修正项。

### 5.3 控制环

```
每 50 ms 一个 tick：
  1. 采样 MAC 队列时延序列 q(i) = DEQ−ENQ 的 P50
  2. 趋势估计：滑动窗口斜率（替代 GCC 的卡尔曼，理由见下）
  3. 过载检测（自适应阈值 γ，GCC 同款）：
        overuse  if  m(i) > γ
        underuse if  m(i) < −γ
  4. AIMD 速率控制（GCC 同款系数）：
        overuse :  target *= (1 − 0.85·df)
        normal  :  target += 0.5·(expected − target)·dt
        underuse:  target *= 1.05
  5. 双重钳制：
        target = min(target, 接收端建议码率)
        target = min(target, 链路容量估计)
  6. 映射到编码器：视频 bitrate = target − 音频码率 − FEC 开销
```

**为什么不用 GCC 的卡尔曼滤波器**：GCC 的卡尔曼假设"测量噪声高斯且已知"，为有线链路标定。MAC 队列时延的噪声结构完全不同（长尾、突发）。**用简单滑动窗口趋势 + 自适应阈值更稳**，这是有意的偏离，要在报告里说明。

## 6. RTC on MAC（G4）

G2 完成后的增强，把 RTC 状态真正融进 MAC：

| 能力 | 现状 | on MAC 要做 |
|---|---|---|
| AC 分类 | 应用填 `up` | 内核侧按 `stream_id`+RTC 标志自动映射；新增 **AC_AI** 队列（对应 arXiv 2610.07900 结论） |
| AQL 门限 | 固定 low/high | 按 RTC 报告的 jitter buffer 深度动态调整 |
| WDRR 权重 | 静态 `fq_weight=1,1,1,1` | 按 RTC 码率需求动态调 `sta_weight` |
| FEC 冗余 | 应用层决定 | MAC 侧感知 PER 后反向建议冗余度 |
| 重传 | MAC 自己做（最多 7 次） | 对实时流可配置"快速放弃"（实时帧超时即弃，不重传） |

最后一条尤其重要：**MAC 对实时视频帧的盲目重传是净损失**——迟到的帧对播放无价值，还占空口。这是 RTC on MAC 最值得做的一项。

| 任务 | 产出 | 验收 |

## 8. 验收指标（建议口径）

| 指标 | 定义 | 目标 |
|---|---|---|
| **ΔAV** | 音画偏移绝对值，P95 | ≤ 40 ms |
| **E2E 时延** | 采集 pts → 播放时刻 | P95 ≤ 150 ms |
| **完整性** | 解码帧数 / 发送帧数 | ≥ 99%（含 FEC/NACK 抢救） |
| **卡顿** | 播放中断 > 100ms 的次数 | ≤ 1 次/分钟 |
| **ABR 收敛** | 拥塞注入 → 码率稳定 | ≤ 1 s，过冲 ≤ 20% |
| **空口效率** | 有效载荷字节 / 空口占用时间 | 对比 UDP/IP 基线 |

对照基线三组：**UDP/IP 裸发**、**RT-L2 固定码率**（现有）、**RT-L2 + ABR**（本方案）。

## 9. 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **接收端 Scapy 是瓶颈** | 时延数据全污染 | P0-3 换 C 接收端，**优先级最高** |
| 板子无音频硬件 | 无法真采集 | P1 用文件驱动；验收前插 USB 声卡 |
| 板子无编码器 | 无法真 ABR | P4 用预编码码率阶梯（2/4/8 Mbit/s 三档切换），隔离控制器验证 |
| A53 软编能力有限 | 高码率编不动 | 640×480@30 baseline，x264 ultrafast 可跑；必要时降到 480p |
| MAC 重传掩盖丢包 | 反馈不准 | 用 FEC 抢救计数 + seq 空洞作软信号（交接文档已指出） |
| GCC 参数需重标定 | 震荡 | P4-2 先离线回放调参，再上链路 |

## 10. 与现有工作的衔接

- **保留**：`l2send.c` / `l2nack_send.c` 的 AF_PACKET 框架、`l2fec_send.c` 的 XOR 实现、18 次对比的测试口径与原始数据
