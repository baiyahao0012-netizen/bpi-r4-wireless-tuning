# RTC over WiFi（上行）→ RTC on MAC：修订方案 v2

> 2026-11-03 修订。相对 v1 的两处根本性更正：
> 1. **角色对调**：发送端 = STA（客户端），接收端 = AP（板子）。v1 把板子当发送端，方向错了。
> 2. **DSCP 解耦**：DSCP/EDCA 属另一条工作线（主线 B），不是本方案的前置约束，去掉 UDP/IP 不再需要考虑它。

---

## 1. 拓扑更正及其连锁影响

### 1.1 正确拓扑

```
   正常使用：手机/PC/摄像头（STA） ──上行视频──▶ AP（板子）
                                             │
                                             └─▶ 反馈（下行，每 50ms）
```

这与"上行视频码率自适应"的题目一致：**上行 = STA → AP**。

板子的实际接口（已确认）：

| 接口 | 角色 | 频段 | 备注 |
|---|---|---|---|
| `phy0.1-ap0` | AP | 5G ch149 / 80MHz | **主测试口**（带宽大） |
| `phy0.0-ap0` | AP | 2.4G ch1 / 20MHz | 对照口 |
| `phy0.0-sta0` | managed | 2.4G | 上联 `DianGroup103`，板子的互联网出口 |

`phy0.0-ap0` 已桥进 `br-lan`（与 `lan2`、`eth1` 同桥）。

### 1.2 对调后，v1 的三个结论要改

| v1 的说法 | 对调后的实际情况 |
|---|---|
| "板子没有音频硬件/编码器，是硬约束" | **约束消失**。STA 是 PC/手机，自带声卡、摄像头、ffmpeg/x264。板子只做接收，不需要编码器 |
| "接收端 Scapy 是瓶颈" | **约束仍在但位置变了**。板子成为接收端，且是 C 环境（AF_PACKET），天生比 Scapy 快。原 Windows 端变成发送端，发送比接收轻，Scapy 勉强可用，但仍建议 C |
| "MAC 队列时延（DEQ−ENQ）是主信号" | **部分失效**。上行方向，STA 的发送队列在 STA 侧，AP 看不到。需要重新设计观测（见第 4 节） |

### 1.3 一个意外的好处：拓扑反而更符合 GCC 原生模型

GCC 的标准架构是：

```
发送端打时间戳 ──▶ 接收端计算时延梯度 ──▶ 接收端发反馈 ──▶ 发送端调码率
```

v1 里板子既是发送端又要自己测时延，**这不是 GCC 的模型**（自己测自己没意义）。对调后，STA 打戳、AP 算梯度、AP 发反馈——**正好是 GCC 的原生形态**。实现反而更标准。

## 2. DSCP 解耦说明

v1 把"去掉 IP 层会打断 DSCP 通路"当成前置障碍，这是把两条工作线混在一起了。

| 工作线 | 内容 | 依赖 |
|---|---|---|
| 主线 A（本方案） | RTC over WiFi，去 UDP/IP，A/V 自适应 | **不依赖 DSCP** |
| 主线 B（另一工作） | OAF 识别 → DSCP → EDCA 加速 | 依赖 IP 头 |

**结论：本方案直接去掉 UDP/IP，不需要为 DSCP 做任何兼容设计。**

阶段 1 全部流量走 **BE**（尽力而为）。这不是缺陷，反而是研究上更干净的条件——拥塞控制算法在无优先级保护的条件下验证，结果更保守也更有说服力。AC 分类放到 G4（RTC on MAC）再引入。

补充一个 AP 侧可用的能力：nft 支持 `ether_type` 匹配，需要时可把 `0x88B5` 与普通流量隔离，但这属于工程优化，不是前置条件。

## 3. 各端职责重新划分

| 端 | 职责 |
|---|---|
| **STA（发送端）** | 采集 → 编码（H.264 + 音频）→ 打 `send_ts`/`pts` → RTC2 封装 → FEC → 发送；接收下行反馈 → 调码率 |
| **AP（板子，接收端）** | L2 收帧 → 重组 → 抖动缓冲 → A/V 同步计量 → **时延梯度计算** → **BSS 信道状态采集** → 生成反馈 → 下行发回 |

**关键点：拥塞控制的大脑在 AP 侧，不在 STA 侧。** STA 只执行"码率指令"。这是本方案与常规 RTC 最大的结构差异，也是"RTC on MAC"的自然起点——AP 本来就该管调度。

## 4. 观测能力重新设计（这是核心）

### 4.1 AP 侧对上行能看到什么

| 信号 | 来源 | 精度 | 用途 |
|---|---|---|---|
| **单向时延梯度** | RTC2 `send_ts` + 到达时刻（`SO_TIMESTAMPNS`） | 内核时间戳，不受用户态抖动影响 | **GCC 主输入** |
| 丢帧率 | `seq`/`frame_id` 空洞 | 端到端，含 MAC 重传失败 | 拥塞 vs 弱信号判别 |
| 到达间隔抖动 | 连续帧间隔统计 | us | 抖动缓冲深度 |
| **BSS 信道占用率** | `survey` busy time | 1s 粒度 | **外部竞争判别** |
| 各 STA 的 airtime | per-STA `airtime` | 累计 us | 谁在占空口 |
| AP 侧 AQL 队深 | per-STA `aql` | 实时 | 下行队列对 ACK 的影响 |
| per-STA rx bitrate / signal | `iw station dump` | 每 100ms | 链路质量 |
| `rx_duplicates` | per-STA debugfs | 累计 | STA 重传的间接证据 |
| 当前 STA 数 | `iw station dump` | — | 竞争强度 |

### 4.2 AP 看不到什么（必须承认的盲区）

| 缺失信号 | 原因 | 影响 |
|---|---|---|
| STA 的应用层发送队列积压 | 在 STA 内核里 | 无法直接分离"STA 发太快"与"信道忙" |
| STA 的 MAC 重传次数 | 只有 STA 自己知道 | AP 只能看 `rx_duplicates` 间接推断 |
| STA 的 MCS 选择 | STA 侧 rate control | 只能从 `rx bitrate` 反推 |

**这是上行方向与下行方向的本质差别。** v1 里"用 `DEQ−ENQ` 分离自致拥塞"的思路在下行成立，在上行不成立。

### 4.3 解决办法：不需要时钟同步的时延梯度

RTC2 头里带 `send_ts_us`（STA 应用层入队时刻）。AP 收到后：

```
d(i) = arrival_i - send_ts_i          // 含未知的固定时钟偏移 Δ
d_min = min over 滑动窗口              // Δ + 传播 + 最小处理时延
q(i) = d(i) - d_min                    // 排队时延，Δ 自动抵消
```

**关键：不需要 NTP、不需要时钟同步。** 固定偏移在减法里消掉了，这与 GCC 的做法一致。剩余误差只有晶振漂移（~20 ppm，50ms 窗口内 < 1 us，可忽略）。

这样 AP 就能得到"相对排队时延"的完整时间序列，**这是 GCC 的核心输入**。

### 4.4 核心创新：用 BSS 全域状态区分「自致拥塞」与「外部竞争」

AP 作为接收端，有一个普通 RTC 接收端永远没有的能力——**它看得见整个 BSS**。

```
每个 50ms tick：
  采集 q(i) 梯度、BSS busy、各 STA airtime、rx_duplicates、signal

  判别：
  ┌ q↑ 且 BSS busy↑ 且 其他 STA airtime↑
  │   → 外部竞争。降码率无效（瓶颈不在自己），保持码率，考虑换信道/带宽
  ├ q↑ 且 BSS busy 平稳 且 本流 airtime↑
  │   → 自致拥塞。降码率（GCC 正常路径）
  ├ q↑ 且 rx_duplicates↑ 或 signal↓
  │   → 链路质量差。降 MCS 优先，码率缓降（避免重传放大）
  └ q↓ 或平稳
      → 探测性增码率（AIMD 加性增）
```

**这就是"RTC on MAC"相对"RTC over UDP"的真正价值**：不是省了几个字节的头，而是**接收端获得了信道全域视角，能做出普通 RTC 做不到的归因判断**。

这个论点比 v1 的"用 DEQ−ENQ 分离"更站得住，因为它不依赖 STA 侧的可观测性。

## 5. 帧格式（RTC2，修订）

```c
struct rtc2_hdr {          /* 24 字节 */
    uint32_t magic;        /* 0x52544332 "RTC2" */
    uint8_t  type;         /* 0=video 1=audio 2=feedback 3=control */
    uint8_t  flags;        /* bit0 parity, bit1 keyframe, bit2 frame_start,
                              bit3 frame_end, bit4 retransmit */
    uint8_t  stream_id;    /* 0=video 1=audio */
    uint8_t  rsv;          /* 预留（原 up 字段降级为预留，DSCP 已解耦） */
    uint16_t seq;          /* 每流递增，16 位回绕 */
    uint16_t chunk_idx;    /* 帧内块号 */
    uint16_t chunk_cnt;    /* 帧内总块数 */
    uint32_t frame_id;     /* 帧序号 */
    uint32_t pts;          /* 采集时间戳，90 kHz，音视频共用 */
    uint32_t send_ts_us;   /* 发送时刻 us，**时延梯度基准** */
    uint16_t payload_len;
    uint16_t group_id;     /* FEC 组号 */
};
```

相对 v1 的变化：`up` 字段降级为 `rsv`（因为 DSCP 解耦，阶段 1 不需要）。其余不变。

EtherType 规划：
- `0x88B5` 数据（STA→AP）
- `0x88B6` 反馈（AP→STA）
- `0x88B7` 控制

## 6. 音视频同步（在 AP 侧做）

### 6.1 为什么在 AP 侧做同步是对的

AP 是接收端，也是播放决策点。`pts` 由 STA 统一打（同一进程、同一时钟），所以：

- **不需要 RTCP SR / NTP 映射**：两流天然同一时基
- 同步误差只来自网络抖动，不含时钟域转换误差

### 6.2 算法

```
1. 建缓期（前 200ms）：统计两流 q(i) 的 P95，取 max 作为 D_play 初值
2. 稳态：T_play = T0 + (pts - pts0)/90000 + D_play
3. 每 500ms 检查 ΔAV = 实际播放差 - pts 差
   |ΔAV| > 40ms 持续 1s → 视频侧丢帧/插帧追赶
4. 音频为主时钟；视频按音频微调
```

### 6.3 计量方式

**不需要真的播放**。ΔAV 用"计划播放时刻"计算，这是学术上的标准做法。真解码只用于抽检画面完整性（板子需 `opkg install ffmpeg`，4×A53 解 640×480@30 可行）。

## 7. 反馈通道（AP → STA，下行）

```
每 50ms，0x88B6：
  ├ 目标码率 target_bitrate   ← 核心
  ├ 时延梯度 q(i) 及其趋势
  ├ 丢帧率 / NACK 位图
  ├ BSS busy / 竞争判别结果
  └ 建议 MCS 或建议 FEC 冗余度（可选）
```

下行方向没有 ACK 问题（AP 是发送方），但要防丢：
- 连发 3 份（不同 seq）
- 单帧 < 200 B

**注意：下行反馈本身也占用空口**。50ms × 200B = 32 kbit/s，相对视频码率可忽略。

## 8. 控制环（分布式）

```
AP 侧（每 50ms）：
  1. 算 q(i) 梯度
  2. 采集 BSS busy / airtime / duplicates
  3. 归因判别（第 4.4 节）
  4. GCC 过载检测 + AIMD → target
  5. 钳制：target ≤ 信道容量估计；target ≥ 地板(300 kbps)
  6. 下发 target

STA 侧：
  1. 收到 target → 平滑（避免突变）
  2. 调编码器 bitrate
  3. 若 200ms 未收到反馈 → 保守降 10%（防反馈中断）
```

**为什么控制器放 AP 而不是 STA**：AP 有全域视角，STA 只有自己。这是本方案的结构性选择。

## 9. 分阶段计划（修订）

### P0 环境与基础（1 周）
| 任务 | 产出 | 验收 |
|---|---|---|
| P0-1 STA 发送端（Windows Npcap 或 Linux AF_PACKET） | 能发 RTC2 帧到 AP | AP 侧抓到完整帧 |
| P0-2 AP 接收端（C，AF_PACKET + SO_TIMESTAMPNS） | 重组 + 统计 | 8 Mbit/s 下 0 丢，CPU < 30% |
| P0-3 时延梯度计算 | q(i) 序列输出 | 与人为注入的排队对得上 |

**P0-2 用 C 不用 Scapy**，因为 AP 侧要打内核时间戳，用户态解析会污染测量。

### P3 反馈通道 + FEC 自适应（1.5 周）

| 任务 | 验收 |

## 11. 相对 v1 的实质改进

| 维度 | v1 | v2 |
|---|---|---|
| 拓扑 | 板子发送（错） | **STA 发送，板子接收（对）** |
| 编码/音频约束 | 硬约束 | **消失** |
| GCC 模型契合度 | 别扭（自己测自己） | **原生形态** |
| 主拥塞信号 | DEQ−ENQ（上行不可得） | **AP 侧 OWD 梯度（可行，且免时钟同步）** |
| 核心创新点 | 用 DEQ−ENQ 分离两类时延 | **用 BSS 全域状态归因，接收端在 AP 内** |
| DSCP | 当作障碍 | **解耦，不是约束** |
