# 甩掉 UDP/IP 后的 RTC 层 —— 严谨 A/B 对比结果

日期：2026-11-04
原始数据：_work_final/rtc/bench/main/raw.csv（5 轮 × 2 臂 × 2 条件 = 20 次运行）
复现命令：python bench.py --reps 5 --tag main

---

## 1. 这次实验要回答的问题

在**同一套 RTC 层**之上，把传统的 UDP + IP 两层拿掉、直接跑在以太网/802.11 二层帧上，是否仍然可用？代价是什么？收益是什么？拿掉 UDP/IP 之后，原本由它们承担的职能该由谁接？

这决定了下一步该往哪里投入。

## 2. 上一版实验为什么作废

上一版把两组做成了"功能也不同"：一组有抖动缓冲/反馈/音频，另一组没有。这样测出的差异无法归因——分不清是协议栈的功劳还是功能的功劳。

本版改为**单变量**：两组跑同一份 sender.py / receiver.py，同一摄像机、同一编码器参数、同一码率与节奏控制、同一抖动缓冲、同一反馈、同一路音频。**唯一差别是 --transport**：

| 臂 | 封装 | 层次 |
|---|---|---|
| **udp**（传统链路） | RTC2 帧放进 UDP 载荷，由内核加 IP+UDP 头 | RTC → UDP → IP → 以太网 → 802.11 |
| **l2**（新方案） | RTC2 帧直接放进以太网帧载荷 | RTC → 以太网 → 802.11 |

传输层由 txport.py 抽象，上层代码完全共用，所以差异只能来自封装。

## 3. 方法与严谨性措施

| 措施 | 做法 |
|---|---|
| 重复测量 | 每臂每条件 5 轮，报告均值 ± 标准差 |
| 交错执行 | 每轮内两臂的顺序按奇偶翻转，抵消射频环境的慢漂移 |
| 损伤一致 | 丢包注入用确定性规则（每 200 个视频分片丢第 1 个），两臂注入量完全相同，不用随机数 |
| 输入一致 | 音频用进程内生成的 440 Hz 音调（两臂同一信号、同一包长）；不用回环采集，因为接收端播放会被回环采回形成正反馈啸叫 |
| 原始数据 | 每次运行单独存 rx/tx 日志，指标即时追加进 raw.csv，中断也不丢数据 |
| 时长 | 发送 9 s、接收 12 s，预热 1.8 s（摄像头启动约 2 s） |

## 5. 归因：差异到底来自哪里

### 5.1 功能上没有差别

除时延外，所有质量指标的差异都在一个标准差以内：解码帧数（−0.2% / −1.1%）、帧丢失率、音视频同步、出队间隔、音频零丢失、发送帧率。**在这条链路上，拿掉 UDP/IP 没有让质量变差。**

### 5.2 时延差 +6.5 ms 基本上是测量平台造成的

独立实验（test_capdelay.py）用同一批数据报同时走内核 socket 与 Npcap 抓包：

    内核 socket 收包时延: p50=2.5  ms
    Npcap   收包时延:     p50=12.8 ms
    Npcap − socket:       p50=+5.6 ms

本次 A/B 测得的 p50 差是 +6.54 ms，与 +5.6 ms 高度吻合。也就是说 **约 86% 的时延劣势来自 Windows 上 Npcap 的驱动→用户态投递，而不是"少了 IP/UDP"这件事本身**。在 Linux 上用 AF_PACKET / PACKET_MMAP 走零拷贝，这部分大部分会消失。

残余约 0.9 ms 才是二层直发与内核 UDP 栈的真实差距。

必须注意：这是本方案在 Windows 上的真实代价，不能因为"是平台造成的"就忽略——它确实让端到端时延变长了。

### 5.3 组帧耗时 +20 ms 也来自 Npcap 的批量投递

l2 臂的"组帧耗时 p95"（一帧第一个分片到最后一个分片的时间跨度）是 25.98 ms，udp 臂只有 6.10 ms。但两臂的**单向时延 p95 几乎相同**（30.00 vs 28.78）。

含义：Npcap 会把到达的包攒一下再批量交给用户态，导致同一帧的分片在时间上被摊开，但每个包的绝对时延并没有系统性变差。这种帧内抖动被抖动缓冲吸收掉了——证据是两臂的**出队间隔 p95 几乎完全一致（37.56 vs 37.46 ms）**。

这正好说明抖动缓冲是必要的：它把 Npcap 引入的帧内到达抖动剥掉了。

### 5.4 一个意外发现：l2 臂的抖动缓冲更稳定

干净链路下 udp 臂的缓冲深度 D = 67.80 ± 62.16（40–179 ms 之间大幅跳动），l2 臂 D = 56.80 ± 1.30（稳定在 55–58 ms）。

对应地，udp 臂出现了孤立的大时延尖峰（p95 最大 117.5 ms，p99 最大 134.1 ms），而 l2 臂的 p95 稳定在 25.5–32.0 ms。丢包条件下 udp 的 p99 更是冲到 317 ms。

推测原因：Windows 内核 UDP 接收路径在该线程被调度延迟时会成批积压，产生孤立尖峰；而 Npcap 有独立的捕获缓冲，反而更平滑。这一条需要更多样本确认，但方向一致（两条件、两臂共 20 次运行都体现同样趋势）。

### 5.5 收益：每包 28 字节，约 2.25% 空口开销

传统栈每个包要额外承载 IPv4 头 20 B + UDP 头 8 B = 28 B。在 1228 B 载荷（1200 数据 + 28 RTC2 头）下：

    l2  单包上线: 14(以太网) + 1228 = 1242 B
    udp 单包上线: 14 + 20 + 8 + 1228 = 1270 B
    额外开销 = 28 / 1242 = 2.25%

9 秒运行实测多发出 70190 ± 400 字节，折合约 62 kbps——大致相当于一路音频流的码率。

**结论：在 1201 Mbps 的干净链路上，2.25% 的节省没有实际意义。** 它只有在链路接近饱和、或对功耗/空口占用敏感时才有价值。

## 6. 拿掉 UDP/IP 之后，原来由它们承担的职能清单

这是下一步必须回答的核心问题。逐项对照：

| UDP/IP 原有职能 | 现状 | 结论 |
|---|---|---|
| **端口复用 / 连接标识** | 已由 magic + stream_id + EtherType 承担 | 够用（仅点对点，无会话概念） |
| **校验和（完整性）** | **完全缺失** | **必须补**。UDP 校验和与 IP 头校验和是唯一的数据损坏检测手段，现在没有任何校验；二层 FCS 被网卡剥掉，上层拿不到 |
| 分片与重组 | 应用层自行分片（1200 B），优于 IP 分片 | 已替代 |
| MTU 发现（PMTUD） | 硬编码 1200 B | 当前链路 MTU 1500 够用，跨异构链路会出问题 |
| 乱序检测 | 自有 seq | 已替代 |
| 拥塞信号（ECN） | 无，靠反馈帧 | 需自建（已有雏形） |
| **跨路由转发** | **不可能** | **这是根本性限制**：二层直发只能在同一广播域内工作，无法穿越路由器/互联网。单 AP 场景可用，跨网段不可用 |
| 内核缓冲与背压 | 自己管理 Npcap 环形缓冲，满了静默丢弃 | 需自建丢包可见性 |

**其中两项是真正的短板：数据完整性校验缺失，以及无法跨三层转发。** 前者可以在 RTC 层补；后者是架构性取舍，必须让使用者知情。

## 7. 下一步优先级（基于实测数据）

| 优先级 | 工作 | 依据 |
|---|---|---|
| 1 | **每分片 CRC32 校验** | 拿掉 UDP 校验和后完全没有损坏检测，这是"甩掉 UDP/IP"直接留下的洞，实现成本最低 |
| 2 | **NACK 重传 + PLI 关键帧请求** | 丢包下解码率只有 223.6/269 = 83%。一个分片丢失就永久毁一帧，且只能等周期 IDR（最长 2 s）。这是最大的质量杠杆 |
| 3 | **在 Linux（AF_PACKET）上复测** | 排除 Npcap 的 5.6 ms 投递开销，才能看到本方案的真实时延水平 |
| 4 | 突发丢包模型复测 | 当前均匀丢包低估了真实无线损伤 |
| 5 | FEC | 应对无法重传的深衰落 |

第 1、2 项直接对应"让 RTC 层接替 UDP/IP 原有职能"这一目标，建议先做这两项。

## 8. 方法论局限

- 同一台 PC 收发，共用一块 WiFi 网卡，反馈流量与下行争用射频
- 丢包是接收端注入的确定性模型，不是真实无线丢包（不消耗空口、不触发重传）
- 每格 n=5，标准差已给出；差异小于一个标准差的结论应视为不显著
- 音频用合成音调而非系统声音（避免回环正反馈），包长真实但内容非真实
- l2 臂的 other 计数波动很大（811–9805），是 WiFi 抓包捎带捕获的环境帧，不影响数据帧统计
