# RTC over WiFi v3：AP 作为中转站的双跳实时视频传输

> 2026-11-03 第三次修订。核心更正：**AP 不是接收端，是中转站**。
> v1 把板子当发送端（错），v2 把板子当接收端（仍不真实）。v3 回到真实场景：两个用户，AP 转发。

---

## 1. 真实拓扑

```
   STA1（发送端）                AP（板子，中转）                STA2（接收端）
   ┌──────────┐   上行 802.11   ┌──────────────┐  下行 802.11  ┌──────────┐
   │ 采集+编码 │ ─────────────▶ │  桥转发 + 观测 │ ───────────▶ │ JB+同步+解码│
   │ RTC2 封装 │                │  双跳测量      │               │ 播放       │
   └──────────┘                │  反馈生成      │               └──────────┘
        ▲                       └──────────────┘                     │
        └──────── 反馈（AP→STA1，0x88B6）◀───────────────────────────┘
                                    （可选：STA2 端到端报告回传）
```

**已确认的可行性**（板子实测）：

```
phy0.0-ap0  hairpin=1  isolated=0     ← 同 BSS 中继必需，已开启
phy0.1-ap0  hairpin=1  isolated=0
```

hairpin 已由 netifd 默认开启，**同一 AP 下两个 STA 互传不需要额外配置**。

---

## 2. 这个拓扑为什么让研究价值大幅提升

v2 里 AP 是接收端，它的优势是"看得见整个 BSS"。v3 里 AP 是中转站，优势变成更强的一条：

> **AP 是唯一同时看得见两跳队列的节点。任何端点都看不到。**

| 节点 | 能看到 | 看不到 |
|---|---|---|
| STA1（发送） | 自己的编码/发送队列、自己的 MAC 重传 | 下行状况、接收端体验 |
| STA2（接收） | 端到端时延、抖动、丢包 | 拥塞发生在哪一跳 |
| **AP（中转）** | **上行到达质量 + 下行发送队列 + 全 BSS 信道状态** | STA1 的应用层队列 |

STA2 只能看到"总时延变大了"，**它无法判断是上行堵了还是下行堵了**。AP 能。

这就是 v3 的核心论点，比 v1/v2 都站得住，而且**直接对应真实部署**：家用/办公场景里，摄像头→AP→显示端是标准路径。

## 3. 两跳的测量方法（关键：两种方法，各用其长）

### 3.1 上行跳 STA1 → AP：单向时延梯度

AP 是接收方。RTC2 头带 `send_ts_us`：

```
d(i)  = arrival_i − send_ts_i       // 含未知固定时钟偏移 Δ
d_min = 滑动窗口最小值
q_up(i) = d(i) − d_min              // 上行排队时延，Δ 自动抵消
```

**不需要时钟同步**——固定偏移在减法里消掉，与 GCC 本身做法一致。到达时刻必须用 `SO_TIMESTAMPNS` 取**内核时间戳**，不能用用户态 `clock_gettime()`。

### 3.2 下行跳 AP → STA2：直接读 MAC 队列

**AP 在下行跳是发送方**，所以能直接拿到 v1 里那个"最干净的信号"：

| 信号 | 来源 | 含义 |
|---|---|---|
| `DEQ − ENQ` | **354 tracepoint**（`dir=0`） | AP 中转队列积压，**精确、无需估算** |
| AQL 队深 | per-STA `aql` | mac80211 的 airtime 队列上限 |
| tx retry | 355 补丁 / `tx_stats` | 下行 MAC 重传 |
| tx PER | `tx_stats` | 下行投递率 |
| tx MCS | `tx_stats` | 下行速率选择 |
| airtime | per-STA `airtime` | 占用信道时间 |

**这意味着之前那轮补丁合并工作在这里真正发挥作用**——354 给上行和下行都提供了逐帧观测，355 补下行重传。它们从"要合并的功能"变成了"双跳测量的基础设施"。

### 3.3 两跳方法对照

| | 上行跳 | 下行跳 |
|---|---|---|
| 测量者 | AP（接收方） | AP（发送方） |
| 方法 | 时延梯度（相对） | `DEQ−ENQ`（绝对） |
| 精度 | 受 STA 时钟漂移影响（可忽略） | 内核内直接打点，最精确 |
| 是否需要时钟同步 | 不需要 | 不需要 |
| 是否需要改内核 | 否（用现有 tracepoint） | 否（用现有 tracepoint） |

## 4. 三向归因：v3 的核心算法

AP 每 50ms 采样，做三选一判别：

```
q_total ↑ （STA2 反馈的端到端时延上升）

  ├─ q_up ↑ 且 上行 airtime ↑ 且 BSS busy 平稳
  │     → 上行自致拥塞（STA1 发太快）
  │     动作：让 STA1 降码率                      ← GCC 正常路径
  │
  ├─ q_down ↑（DEQ−ENQ ↑）且 下行 tx retry ↑
  │     → 下行瓶颈（AP 中转队列堆积 / STA2 链路差）
  │     动作：STA1 降码率**无效或有害**；
  │           应做 AP 侧队列管理、降 STA2 的 MCS、或限制 AP 入队
  │
  ├─ BSS busy ↑ 且 两跳 q 都不高 且 其他 STA airtime ↑
  │     → 外部竞争
  │     动作：降码率收益有限，优先考虑换信道/带宽
  │
  └─ 两跳 q 都平稳
        → 探测性增码率（AIMD 加性增）
```

**最关键的一条是第二行**：经典 GCC 在这种情况下会误判成"自己发太快"而降码率，但实际瓶颈在 AP→STA2 这一跳。**降 STA1 的码率不但没用，还会浪费上行容量。**

这是"中转站视角"能给出的、端点式 RTC 给不出的判断。

## 5. 半双工中继的容量惩罚（必须建模）

同信道中继时，一个帧要占用**两次空口**：

```
STA1 ──①──▶ AP ──②──▶ STA2
       上行      下行        两跳共用同一信道（半双工）
```

所以中继链路的有效容量约为单跳的一半。控制器必须知道这一点：

```
C_effective ≈ C_phy × η_mac / 2        （同信道中继）
C_effective ≈ C_phy × η_mac            （跨频段中继，如 5G→2.4G）
```

**如果控制器按单跳容量估，就会持续过冲**，然后在归因上表现为"下行 q 一直高"。这是 v3 必须显式处理的项。

AP 可以直接测：`survey` 的 busy 时间里，属于自己转发的比例 → 实测 η。

## 6. AP 侧中继队列管理 = "RTC on MAC" 的实质

v1/v2 把 "RTC on MAC" 说成"把状态机融进 MAC"，太抽象。v3 里它有了具体内容：

| 能力 | 现状（纯桥转发） | RTC on MAC 要做 |
|---|---|---|
| 队列边界 | 桥 FIFO，可能 bufferbloat | 按 RTC 帧的 `frame_id` 设**截止时间**，过期即弃 |
| 重传策略 | MAC 盲目重传最多 7 次 | **实时帧超时即弃**（迟到的帧对播放无价值，还占空口） |
| 优先级 | 全 BE | 按 `stream_id`/`flags.keyframe` 分级 |
| AQL 门限 | 固定 low/high | 随 RTC 报告的 JB 深度动态调 |
| 准入 | 无 | 下行队列满时对视频流做**主动丢帧**而非无限排队 |

**"实时帧超时即弃"是最值得做的一条**：MAC 为一个已经过了播放时刻的帧重传 7 次，是纯损失。这一条做好了，同场景有效吞吐和端到端时延都会明显改善。

技术落点：`tc` qdisc 作用在 `phy0.1-ap0` 的 egress（`dev_queue_xmit` 路径），**桥转发的帧同样经过**，所以可以在这里做队列管理。这是不改内核就能落地的方案；需要更细粒度（按 frame_id 丢弃）时才动 mac80211。

## 7. 观测的透明性（不干扰转发）

AP 用 `AF_PACKET` + `ETH_P_ALL` 绑定 `phy0.1-ap0`：

- AF_PACKET 在 `__netif_receive_skb_core` 里、**桥处理之前**就拿到帧副本
- 因此**能观测到即将被桥转发的帧，且完全不影响转发**
- 不需要 ebtables、不需要 br_netfilter、不需要把帧从桥里摘出来

反馈帧由 AP 自己构造（源 MAC = AP，目的 MAC = STA1），直接 `sendto` 到 `phy0.1-ap0`。

---

## 8. A/V 同步：移到 STA2

v2 把同步放在 AP，v3 必须移到 STA2——**因为播放发生在 STA2**。

- `pts` 由 STA1 统一打（同一进程、同一时钟）→ **不需要 RTCP SR / NTP 映射**
- STA2 双流独立 JB + 共享播放时钟，音频为主时钟
- ΔAV 用"计划播放时刻"计算（学术标准做法），不依赖人耳人眼
- STA2 把 `q_total`、ΔAV、丢帧数回传给 AP（可走 0x88B6，AP 再合并到对 STA1 的反馈里）

**注意**：STA2 的回传帧也要走 Wi-Fi，会和视频流竞争。周期可以放低（200ms 一次足够），因为它只用于端到端校验，不参与快速控制环。

## 9. 硬件需求

v3 需要**两个可编程的 Wi-Fi 终端**：

| 角色 | 要求 | 现状 |
|---|---|---|
| AP | 板子，能跑 AF_PACKET + 读 tracepoint | ✅ 已有 |
| STA1 发送 | 能发原始 L2 帧、能编码、能调码率 | ⚠️ 需确认 |
| STA2 接收 | 能收原始 L2 帧、能做 JB/同步/解码 | ⚠️ 需确认 |

现有只有 1 台 Windows PC。可选方案：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 第二台笔记本** | 一台发一台收 | 最真实，两端都可编程 | 需设备 |
| **B. PC + USB Wi-Fi 网卡** | 同一 PC 上两个 Wi-Fi 接口分别当 STA1/STA2 | 一台机器搞定，两端都在同一进程里，联调最方便 | 两个射频同机箱，自干扰是伪影 |
| **C. PC(Wi-Fi) + 板子有线口** | STA1=PC 无线，接收端=PC 有线 | 无需新硬件 | 不是"两个用户"，下行不经 Wi-Fi，失去双跳意义 |
| **D. PC + 手机** | 手机当 STA2 只播放 | 最接近真实用户 | 手机不可编程，无法测 ΔAV |

**建议 B 起步**（联调最快，两端可编程），**A 做最终实验**（避免自干扰伪影）。C 只作为打通链路的临时手段。

## 10. 分阶段计划

### P0 双跳打通（1.5 周）
| 任务 | 产出 | 验收 |
|---|---|---|
| P0-1 STA1 发送端（RTC2 + `send_ts`） | 能发到 AP | AP 侧抓到完整帧 |
| P0-2 AP 中继观测（AF_PACKET 旁路 + `SO_TIMESTAMPNS`） | `q_up(i)` 序列 | 与人为注入对得上 |
| P0-3 AP 下行观测（354 tracepoint 消费 `DEQ−ENQ`） | `q_down(i)` 序列 | 与 `aql` 队深趋势一致 |
| P0-4 桥转发验证（hairpin） | STA1→AP→STA2 通 | STA2 收到完整流 |

### P1 音视频与同步（1.5 周）
STA1 编码 A/V + `pts`；STA2 双流 JB + 同步控制器；**离线先调对再上链路**。验收：ΔAV ≤ 40ms。

### P2 全链路（2 周）—— **可交付里程碑**
三场景（5G 空闲 / 5G+背景流 / 2.4G）× 三方案（UDP/IP 基线 / RT-L2 固定码率 / RT-L2+ABR），完整性 ≥99%，ΔAV ≤40ms。

### P3 反馈通道 + FEC 自适应（1.5 周）

### P4 双跳归因 + GCC 控制环（3 周）—— **核心实验**
| 任务 | 验收 |
|---|---|
| P4-1 两跳 q 序列时间对齐 | 采样误差 < 5ms |
| P4-2 三向归因器 | 人为构造"上行拥塞/下行拥塞/外部竞争"三场景，判别正确率 > 85% |
| P4-3 半双工容量模型 | 实测 η 与模型偏差 < 15% |
| P4-4 GCC 闭环 | 拥塞注入后 ≤1s 收敛，过冲 ≤20% |
| **P4-5 对照实验** | 同控制律，输入 = 端到端时延 vs 双跳分离时延；证明后者在下行瓶颈场景误判率显著低 |

**P4-5 是最有说服力的一组数据**：构造一个"下行瓶颈"场景，经典 GCC 会误降码率，双跳归因不会。这个对比直接支撑"AP 中转站视角"的论点。

### P5 RTC on MAC（2.5 周）
AP 侧队列管理（`tc` egress）、实时帧超时即弃、AQL 动态门限、优先级分级。

## 12. 三个必须尽早验证的技术风险

| 风险 | 后果 | 验证方式 |
|---|---|---|
| **hairpin 转发实际吞吐** | 若性能差，同 BSS 中继不可行 | P0-4 先跑 iperf3 测中继吞吐，再谈视频 |
| **桥转发引入的额外时延** | 若 > 5ms 且抖动大，污染测量 | P0-2 用固定包长测桥转发时延分布 |
| **同机双射频自干扰**（方案 B） | 数据失真 | 与方案 A 对比校准；至少做一次交叉验证 |
