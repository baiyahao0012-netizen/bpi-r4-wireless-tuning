## 1. 文档目的与范围

本项目的任务**仅限**在既有 WiFi 链路上加入 RTC 层，不涉及 MAC 层调优、内核修改、板级参数调整。

视频源为 PC 摄像头，音频源为 PC 系统声音（WASAPI 回环）。目标是把音视频经 RTC 层封装后，走"PC 以太网 → BPI-R4 桥接 → PC WiFi"这条链路，并在接收端还原播放，要求音视频同步误差不超过 40 ms。

本文档用于向第三方完整移交现状：架构、协议、实现状态、实测数据、已修复缺陷、已知局限、与真正 RTC 层的差距。

### 已明确不在范围内的事项

- WiFi MAC 层特性（AQL、WDRR、EDCA、速率控制）
- 内核与驱动修改
- BPI-R4 板级测试与固件（该部分工作已完成并关闭，不应重开）
- 研究组给出的 MAC 反馈式 GCC、差异化传输、优先级调度、选择性重传等建议，属于背景参考，未纳入本阶段实现

## 2. 系统架构与部署拓扑

### 2.1 物理链路

    PC 摄像头 ──┐
                ├── RTC2 封装 ──> PC 以太网口 ──> BPI-R4 br-lan 桥 ──> 802.11 → PC WiFi 网卡
    PC 系统声音 ─┘                                        （AP: BPI-R4-5G）

发送端与接收端**运行在同一台 PC 上**，这是当前实验环境的固有特点，带来两个已知影响：

1. 收发共用一块 WiFi 网卡的两个 Npcap 句柄，产生同机捕获争用
2. 反馈流量与下行流量争用同一射频，接收端上报的丢包率高于两机部署的真实值

两机部署后这些假象会消失，但当前所有数据都带有这一前提。

### 2.2 地址与设备

| 角色 | 地址 | MAC | 说明 |
|---|---|---|---|
| PC 以太网 | 192.168.240.2 | 40-C2-BA-52-70-95 | 发送出口 |
| 板子 br-lan | 192.168.240.1 | — | 桥接转发 |
| PC WiFi（Realtek 8852CE） | 192.168.240.147 | C0-35-32-19-CC-FB | 接收口 + 反馈出口 |
| PC WiFi（MediaTek USB，备用） | 192.168.240.126 | 90-DE-80-1C-6A-7A | 未使用 |

AP：BPI-R4-5G，信道 149，HE80，协商速率 1201 Mbps，信号 −43 至 −46 dBm，DTIM 2，beacon 100 ms。

板子 br-lan 端口：lan2、eth1、phy0.0-ap0、phy0.1-ap0、lan3、lan1。

### 2.3 关键技术约束：WiFi 网卡无法注入

Npcap 在本机两块 WiFi 网卡上**都无法注入**数据帧（错误 31，"系统上的设备没有发挥作用"），即使以管理员身份运行。以太网口与 loopback 可正常注入，WiFi 只能捕获。

这直接决定了反馈通道的实现方式（见 5.2）。

## 3. 协议规格

### 3.1 RTC2 数据帧头（28 字节，网络字节序）

格式串：!IBBBBHHHHIII

| 偏移 | 字段 | 宽度 | 说明 |
|---|---|---|---|
| 0 | magic | 4 | 固定标识 |
| 4 | type | 1 | 帧类型 |
| 5 | flags | 1 | 见下表 |
| 6 | stream_id | 1 | 0=视频，1=音频 |
| 7 | rsv | 1 | 保留 |
| 8 | seq | 2 | 全局序号（音视频共用同一序号空间） |
| 10 | chunk_idx | 2 | 分片索引 |
| 12 | chunk_cnt | 2 | 该帧总分片数 |
| 14 | payload_len | 2 | 本分片有效载荷长度 |
| 16 | frame_id | 4 | 帧号（按流独立） |
| 20 | pts | 4 | 显示时间戳，90 kHz |
| 24 | send_ts_us | 4 | 发送时刻，微秒低 32 位，用于单向时延测量 |

flags 位定义：

| 位 | 含义 |
|---|---|
| bit0 | FEC 冗余包（当前未实现） |
| bit1 | 关键帧 |
| bit2 | 帧起始 |
| bit3 | 帧结束 |
| bit4 | 重传（当前未实现） |
| bit5 | 探测包 |

### 3.2 反馈帧（40 字节，网络字节序）

格式串：!IIIIIHHIIIHH，magic 为 'FBK1'（0x46424B31）

| 字段 | 说明 |
|---|---|
| magic | 固定标识 |
| fb_seq | 反馈序号，用于去重 |
| window_us | 本统计窗口时长 |
| recv_bytes | 窗口内接收字节数 |
| q_us | 接收端队列/缓冲深度估计 |
| loss_permille | 窗口内帧丢失率（千分比） |
| jitter_us | 窗口内超额传输时延 p95 |
| frames_ok | 累计成功帧数 |
| frames_lost | 累计丢失帧数 |
| max_frame_id | 已见最大帧号 |
| rsv / rsv2 | 保留 |

注意：loss_permille 统计的是**帧级**丢失率，不是分片级。

|---|---|

## 5. 关键设计决策与理由

### 5.1 绝对时间轴节奏控制

最初版本按帧间隔 sleep，导致帧率被压到 8.9 fps。根因是摄像头每帧耗时抖动被串行累加。

改为绝对时间轴：理想发送时刻 ideal = t0 + 已发送字节数 × 8 / 带宽，只在落后时才 sleep。这样摄像头自身的采集时间也计入预算，节奏器永不成为帧率上限。帧率恢复到 29.4 fps。

带宽预算取目标码率 × 1.3，覆盖 libx264 的超调与每分片 42 字节的封装开销。

### 5.2 反馈通道：MAC 定向反射

由于 WiFi 网卡无法注入（见 2.3），反馈无法直接从 WiFi 发出。采用的方案：

把反馈帧的**目的 MAC 设为 WiFi 网卡自身的 MAC**（C0-35-32-19-CC-FB），从以太网口注入。板子的桥发现该 MAC 在 WiFi 端口上，于是把帧从射频转发出去，PC 侧再从 WiFi 捕获到它。

验证结果：5/5 全部到达，随后在 1 Hz / 20 Hz / 60 Hz 下实测通路容量——1 Hz 单发 100%，20 Hz 单发 62%，20 Hz 三连发 100%，60 Hz 单发 40%。瓶颈在接收侧抓包吞吐，不在空口。

### 5.3 抖动缓冲：基于超额传输时延

对每个分片计算传输时延 t = 到达时刻 − PTS，取历史最小值 tmin 作为最快路径基准，超额 d = t − tmin。

播放时刻 play = 到达 + D − d，等价于 play = PTS + tmin + D，即**与单个包的传输时延无关**。缓冲深度 D 由 d 的 p95 自适应：D = clamp(p95(d) × 1.25 + 20ms, 40..200ms)。

### 5.4 音视频共享播放时钟（关键）

音频与视频**必须共用同一个 tmin**。若各自维护 tmin，两条流会被它们路径时延之差整体错开，表现为恒定音视频偏移。共享后 play = PTS + tmin + D，同一采集时刻的画面与声音在同一时刻出队。

同时规定：**只有 PTS 锚定在墙钟上的流（视频）可以更新 tmin 与 D**，音频只读。原因是若某个采集设备时钟不准，其 PTS 会落后墙钟，看起来像队列持续增长，会把 D 顶到上限并污染视频流。此机制已在实测中验证有效（真实麦克风时钟异常时，D 从 200 ms 恢复到 56 ms，视频指标完全不受影响）。

### 5.5 音频 PTS 采用墙钟而非采样计数

教科书做法是用采样计数作为音频 PTS。但本机回环设备实际只按 0.98 倍实时交付，采样计数 PTS 在 9 秒内落后墙钟约 140 ms，导致所有音频包在播放端被判为迟到。

改用与视频同一个墙钟打时间戳后，迟到从 443/443 降到 0，出队间隔从 16.0 ms 恢复到 20.0 ms。

代价是设备少交付的部分（约 2%）表现为极少量样本缺失，实测缓冲欠载为 0。彻底解决需要加入重采样做时钟校正。

### 5.6 码率自适应需要重开编码器

PyAV 中就地修改 bit_rate 无效，实测必须重建编码器上下文，代价约 3–4 ms 并强制插入 IDR。因此规定切换间隔不小于 0.5 s、幅度变化不小于 6% 才执行。

另需注意：只设 bit_rate 而不设 VBV 约束时，libx264 在 IDR 上会严重超调，目标码率根本落不到线上，节奏器只好压制帧率。必须同时设置 maxrate = 1.2 × 目标、bufsize = 0.5 × 目标。

由于每次切换都插入 IDR 且打断解码参考链，--abr **默认关闭**，仅在需要时显式开启。

### 5.7 解码必须移出接收循环

在接收循环内直接解码会使单帧耗时从 0.2 ms 升到 5.0 ms，并因阻塞抓包导致播放卡顿。改为独立解码线程 + 队列后恢复。

### 5.8 以太网最小帧填充

以太网最小帧 60 字节。短分片会被网卡零填充，抓包侧还可能附加 FCS。接收端必须以头部声明的 payload_len 为准并截断，不能要求长度精确相等。此前严格的等长校验导致 0.5–2.8% 的**幻影丢帧**，长期被误判为无线链路问题。

### 6.5 测量偏差修正：Npcap 投递开销

B 组时延 2.4 ms 而 A/C 为 9.9/12.6 ms，看似 UDP 快 4 倍。用同一批数据报同时走内核 socket 与 Npcap 抓包测量：

    匹配数据报 2251 个
    内核 socket 时延: p50=2.5  p95=9.3   p99=15.7 ms
    Npcap 抓包时延:   p50=12.8 p95=43.3  p99=70.1 ms
    Npcap 减 socket:  p50=+5.6 p95=+39.6 ms

Npcap 从驱动到用户态的投递本身耗时 5.6 ms 中位、39.6 ms p95。扣除后：A 约 4.3 ms、C 约 7.0 ms、B 约 2.5 ms。UDP 确实略低，但差距从 4 倍缩到 1.7 倍，原因是原始 L2 多了一次驱动与用户态拷贝，而非传输技术优劣。

**任何引用 A/C 与 B 的时延对比时必须先声明这一偏差。**

## 7. 已定位并修复的缺陷

| 缺陷 | 根因 | 修复 |
|---|---|---|
| 帧率仅 8.9 fps | 按帧间隔累加 sleep，摄像头抖动被串行累加 | 绝对时间轴节奏控制，恢复 29.4 fps |
| 幻影丢帧 0.5–2.8% | 以太网最小帧 60 字节零填充，严格的等长校验丢弃短分片 | 以头部 payload_len 为准截断 |
| 单帧重组耗时 5.0 ms | 解码在接收循环内阻塞抓包 | 解码移至独立线程，恢复 0.2 ms |
| 反馈冗余无效 | 三连发无时间分集，被同时丢失 | 改为每周期各发最近三次报告各一份 |
| ABR 只降不升 | 基线按 0.002 系数缓慢爬升，超额时延长期钉在阈值以上 | 改为最近 40 条报告的滚动最小值 + 6 条预热 |
| 编码器不遵守目标码率 | 缺少 VBV 约束，IDR 严重超调 | 加 maxrate=1.2 倍、bufsize=0.5 倍 |
| ABR 默认开启反而有害 | 无拥塞时 9 秒重开 17 次编码器，插入 17 个 IDR | 默认关闭，需显式 --abr 1 |
| 音频包全部迟到 | 采样计数 PTS 落后墙钟 | 改用墙钟 PTS |
| 慢时钟设备污染共享缓冲 | 音频也参与更新 tmin 与 D | 仅视频可更新，音频只读 |
| 音视频偏移符号标注反了 | 计算顺序颠倒 | 改为 play_video 减 play_audio |
| 音视频偏移打印单位错误 | 重复乘 1000 | 统一以秒存储、输出转毫秒 |
| 两线程并发使用同一 Npcap 句柄 | 该句柄非线程安全 | 加发送锁串行化 |

## 8. 当前已知问题与局限

### 8.1 麦克风不可用（需人工处理）

本机麦克风被静音或被 Windows 隐私设置拦截：所有采集尝试电平均在 rms 0.3–0.8、peak 2–7 范围（有效信号应为数百以上），且交付速率仅 0.86–0.94 倍实时。

代码路径本身已验证可用（421 帧完整走通采集→编码→传输→解码→扬声器）。需人工在 设置 → 隐私和安全性 → 麦克风 中允许桌面应用访问，并检查设备静音状态。

当前音频改用 WASAPI 回环采集系统声音，工作正常。

### 8.2 音频时钟未做重采样校正

## 9. 与真正 RTC 层的差距分析

### 9.1 最关键的缺失：完全没有丢包恢复机制

一个分片丢失就永久毁掉整帧。三组解码率均只有 74–77%，且抖动缓冲对此毫无改善（已实测）。

| 缺失 | 后果 | 真实 RTC 做法 |
|---|---|---|
| NACK / RTX 重传 | 单分片丢失即丢整帧 | 接收端按 seq 报缺口，发送端缓存约 200 ms 重传 |
| FEC 前向纠错 | 无冗余，突发丢包不可抗 | XOR/RS 冗余包，恢复单包与短突发 |
| PLI / FIR 关键帧请求 | 参考链断裂后只能等周期 IDR（最长 2 s） | 解码失败立即请求 IDR |

这是投入产出比最高的改进方向。

### 9.2 拥塞控制过于粗糙

- 只有丢包判据，没有真正的可用带宽估计
- 真实 GCC 用到达时间序列做 Kalman 滤波求时延梯度；本实现用超额时延 p95 的滚动最小值，是近似
- 上调为每 0.5 秒 1.12 倍的盲目探测，真实拥塞场景下会超调后回退
- 码率切换粒度粗（整体重开编码器 + IDR），本身损失约 2% 可解码率

### 9.3 协议层不标准

- 自定义封装，无法与任何标准实现互通
- 没有 RTP/RTCP：无 SR/RR、无扩展序号、无接收端报告驱动的发送端调速
- 无 RTCP 唇音同步参考

### 9.4 抖动缓冲过于简单

- 单一 p95 目标深度，无播放加速/减速机制
- 无按包级时延趋势自适应
- 无音频/视频差异化策略

### 9.5 音频缺少 RTC 必备能力

- 无 Opus inband FEC
- 无丢包隐藏（PLC）
- 无 DTX 静音压缩
- 无重采样时钟校正
- 无 AEC 回声消除、无降噪、无自动增益（这三项在真实 RTC 中是必需项）

### 9.6 音视频同步未标定

- 16–19 ms 恒定偏差是测量得知的，未做标定补偿，来源是摄像头驱动缓冲（一帧从曝光到 cap.read 返回固有滞后半帧到一帧）
- 无 RTCP 唇音同步参考
- 无"音频主时钟牵引视频"的伺服环
- 当前按 ITU-R BT.1359（音频领先阈值 45 ms）判断为不可察觉

### 9.7 其他

- 无加密、无认证（无 SRTP）
- 无 MTU 发现，固定 1200 字节分片
- 非实时安全栈：Python + GIL、Npcap 用户态拷贝、cv2 DSHOW 采集、无硬件编码
- 帧率 29 而非 30

## 12. 建议的下一步优先级

1. **NACK 重传 + PLI 关键帧请求**——投入最小，对 74% 解码率改善最直接
2. **突发丢包模型下的对比复测**——当前均匀丢包模型低估了真实影响
3. **音频 PLC 与重采样时钟校正**——补齐 2% 样本缺失
4. **音视频偏移标定**——消除 17 ms 恒定偏差
5. **FEC**——应对无法重传的深衰落场景

## 13. 需要决策的事项

1. 是否引入 RTP/RTCP 标准封装以换取互通性，还是保持自定义封装追求最小开销
2. 音频是否补齐 AEC/降噪/AGC（真实通话场景必需，当前完全缺失）
3. 是否接受"仅点对点"定位，不实现多方混流
4. 两机部署验证是否纳入下一阶段（可消除同机争用带来的全部假象）
