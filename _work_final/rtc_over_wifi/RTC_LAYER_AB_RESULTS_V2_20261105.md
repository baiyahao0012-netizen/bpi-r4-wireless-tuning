## 1. 实验原则

- **传统 UDP/IP 臂：不做任何修改**。它是普通 UDP 应用，用标准 socket，测什么、怎么测都按传统方式来。
- **我方协议臂：允许使用我们自己的测量方法**（时钟同步、带内时间戳）。
- 两臂承载**完全相同的 RTC 层**：同一套 RTC2 分帧、同一摄像机、同一编码器、同一码率与节奏控制、同一抖动缓冲、同一反馈帧格式。
- 唯一差别是传输封装：一层直接放进以太网帧，另一层放进 UDP/IP。

## 2. 拓扑（最真实场景）

    有线服务器端（笔记本，摄像头）──以太网──→ BPI-R4 桥接 ──WiFi──→ 无线客户端（笔记本 AX201）
            RTC 发送端                                                    RTC 接收端

真实 RTC 的形态：一端有线/云端，一端无线终端，**恰好一跳无线**。

| 项目 | 发送端 | 接收端 |
|---|---|---|
| 有线 | .2 → lan1，1000 Mbps | .221 → lan2，100 Mbps |
| 无线 | 内置 8852CE（管理/反馈） | **AX201，780 Mbps（数据通路）** |
| 摄像头 | 640×480@15 fps（低光自动降帧） | — |
| 码率 | 2.5 Mbps | — |
| 板子 | 5G AP ch149 HE80，桥接 | 同左 |

UDP 臂与 L2 臂走**同一条物理路径**，保证可比。

## 3. 测量方法

| 指标 | L2 臂（自有方法） | UDP 臂（传统方法） |
|---|---|---|
| 单向时延 | 带内 send_ts + NTP 式时钟同步（实测同步 RTT 5-10 ms） | **不测**，只报传统 RTT |
| RTT | — | ICMP ping，同一路径 |
| 丢帧/解码 | 两端日志统计 | 同 |
| 抖动缓冲/欠载 | 接收端统计 | 同 |
| 反馈 | 反馈帧计数 | 同 |

说明：UDP 臂没有加入任何额外端口、额外报文或自定义机制。

## 5. 分析

### 5.1 功能完整性：完全等价

这是本次实验最重要的结论。去掉 UDP/IP 之后，RTC 层该有的功能一个都没少：

| 功能 | 状态 | 证据 |
|---|---|---|
| 音视频分片与重组 | 通过 | 分片数 3951 vs 3956，误差 0.1% |
| 帧完整性判定 | 通过 | 丢帧数、帧丢失率两臂一致 |
| 抖动缓冲 | 通过 | 两臂都有，欠载数完全相同（19.33） |
| 解码 | 通过 | 干净链路解码率同为 99.5% |
| **反馈闭环** | 通过 | 收到反馈 224.67 vs 222.67 份，差异 <1% |
| 自适应码率所需输入 | 通过 | 反馈携带的丢包率、抖动、队列深度均正常解析 |

**没有任何一项功能因为去掉 UDP/IP 而丢失。**

### 5.2 性能：干净链路无差别

在无损伤链路上，两臂的接收帧数、丢帧数、解码率、欠载数完全相同，反馈投递率一致（L2 略高 0.9%，在噪声范围内）。

**在 1201 Mbps 空口、2.5 Mbps 码率下，去掉 UDP/IP 对传输质量没有可测量的影响。**

### 5.3 代价一：抖动缓冲要深 17 ms

    L2 臂:   D = 57 ms
    UDP 臂:  D = 40 ms

根因在组帧耗时 p95：

    L2 臂:   28.50 ms
    UDP 臂:   1.43 ms

同一帧的分片经 Npcap 用户态抓包后，到达时间被摊开约 28 ms（Npcap 会攒包批量投递），而内核 UDP 只要 1.4 ms。为吸收这种帧内抖动，抖动缓冲必须挖得更深，代价是**端到端时延增加约 17 ms**。

这是本方案在 Windows 上的真实成本，不是测量误差。在 Linux 上用 AF_PACKET/PACKET_MMAP 零拷贝，这部分会大幅缩小。

### 5.4 代价二：丢包下解码率低 3.4 个百分点

    L2 臂:   149.00 / 198.33 = 75.1%
    UDP 臂:  156.00 / 198.67 = 78.5%

必须指出：**这个差异在一个标准差附近**（L2 标准差 6.93，UDP 5.20，差值 7 帧约 1.2 个标准差），n=3 不足以判定显著。两臂解码错误数完全相同（都是 27），说明丢包模式一致。

真正的根因是**两臂都没有丢包恢复机制**：一个分片丢失就永久损失整帧，只能等下一个 IDR。这与传输层无关。

### 5.5 收益：每包省 28 字节

L2 臂每包省掉 IPv4 头 20 B + UDP 头 8 B = 28 B。15 秒内 3951 个分片，共节省约 110 KB，折合 **59 kbps**，约占 2.6 Mbps 总码率的 **2.3%**。

在 1201 Mbps 空口上，2.3% 没有实际意义。**省掉的头部开销不是这个方案的价值所在。**

### 5.6 反馈通道两臂都正常

    L2 臂:   发送 305.00 份，收到 224.67 份（73.7%）
    UDP 臂:  发送 306.33 份，收到 222.67 份（72.7%）

反馈本身有丢包，但靠 3 倍冗余投递，有效接收率约 73%，足以驱动拥塞控制。两臂表现一致，说明反馈机制不依赖传输层。

## 6. 结论

1. **功能上完全等价**：去掉 UDP/IP 后，分片、重组、抖动缓冲、解码、反馈闭环全部正常工作，指标与 UDP 臂一致。
2. **干净链路上性能无差别**：收发帧数、丢帧、解码率、欠载完全相同。
3. **代价是时延**：L2 臂需要更深的抖动缓冲（57 ms vs 40 ms），端到端多约 17 ms。主要来自 Windows Npcap 的用户态抓包路径（组帧 p95 28.5 ms vs 1.4 ms），属平台成本而非协议成本。
4. **收益是 2.3% 的空口开销**：在当前链路上不值得为它牺牲时延。
5. **两臂共同的短板**：都没有丢包恢复（NACK/FEC/PLI），丢包下解码率只有 75-78%。这比传输层更值得投入。

## 7. 局限

- n=3，差异小于一个标准差的结论应视为不显著。
- 丢包是接收端注入的确定性模型（每 200 分片丢 1），不消耗空口、不触发重传，**低估了真实无线丢包的影响**。
- 摄像头在低光下自动降到 15 fps，两臂一致，但不代表 30 fps 下的行为。
- lan2 只有 100 Mbps（线缆只通 2 对线），对 2.5 Mbps 无影响，但高码率实验前必须换线。
- 接收端 AX201 曾被 802.11ax 互操作问题卡在 6 Mbps，现已强制 802.11ac 恢复至 780 Mbps；这是独立于本实验的链路侧问题。
