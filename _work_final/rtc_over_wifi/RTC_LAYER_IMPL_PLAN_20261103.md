# RTC over WiFi —— RTC 层实现方案（待确认）

> 2026-11-03。目标：在**已去掉 UDP/IP** 的 L2 通路上补齐 RTC 层，保留自适应、GCC 等功能。
> 本文是可评审的执行规格，确认后按里程碑逐步实施。

---

## 1. 现状盘点：其实只缺 RTC 层

### 1.1 已经做到的（不用重做）

现有代码 `l2video_send_rt.c` / `l2nack_send.c` / `l2fec_send.c`：

```c
socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ALL));   // 直接 L2，无 IP 栈
frame[12]=0x88; frame[13]=0xB5;                   // 自定义 EtherType
struct hdr { magic, seq, len, flags, rsv };       // 20 字节头
```

**"去掉 UDP/IP"这一项，现有实现已经完成了。** 没有 IP 头、没有 UDP 头、没有端口、没有 ARP、没有分片重组（由应用自己做）。

### 1.2 真正缺的（RTC 层）

| RTC 层组件 | 现状 | 差距 |
|---|---|---|
| 帧边界 | 只按 AUD 切帧发送，头里无帧信息 | 接收端无法判断"这一帧收全了吗" |
| 时间戳 | 无 | 算不出时延、做不了同步 |
| 抖动缓冲 | 无 | 收到就喂解码器，解码器被抖动打死 |
| 音视频同步 | 无（只有视频） | ΔAV 无从谈起 |
| 反馈通道 | 只有 NACK（文本 `"NACK:%d"`） | 没有带宽/时延回传，无法闭环 |
| GCC | 无 | 没有码率自适应 |
| 码率执行 | 无（固定 fps 发固定文件） | 没东西可调 |
| FEC 自适应 | 固定 8+1 | 冗余度不能随丢包变 |
| 关键帧标记 | 无 | 不能做"从关键帧开始解码"、不能切码率 |

**结论：工作量 100% 在"加 RTC 层"，不涉及重做传输通路。**

## 2. RTC2 数据帧格式（可直接照此写代码）

```c
/* 28 字节，全部网络字节序 */
struct rtc2_hdr {
    uint32_t magic;        /* 0x52544332 "RTC2" —— 快速识别 */
    uint8_t  type;         /* 0=video 1=audio 2=feedback 3=control */
    uint8_t  flags;        /* bit0 FEC奇偶  bit1 关键帧  bit2 帧首块
                              bit3 帧末块  bit4 重传  bit5 探测帧 */
    uint8_t  stream_id;    /* 0=video 1=audio */
    uint8_t  rsv;          /* 预留（对齐用） */
    uint16_t seq;          /* 全局递增 16 位，用于丢包检测 */
    uint16_t chunk_idx;    /* 帧内块号，从 0 开始 */
    uint16_t chunk_cnt;    /* 帧内总块数（含 FEC 块） */
    uint16_t payload_len;  /* 本块负载长度 */
    uint32_t frame_id;     /* 帧序号，音视频各自递增 */
    uint32_t pts;          /* 采集时间戳，90 kHz，音视频共同时基 */
    uint32_t send_ts_us;   /* 发送时刻，微秒（低 32 位，单调钟） */
};
```

**五个字段的用途，逐条对应到 RTC 功能：**

| 字段 | 支撑的 RTC 功能 |
|---|---|
| `frame_id` + `chunk_cnt` + `chunk_idx` | 帧完整性判断、按帧丢弃、FEC 分组 |
| `flags.keyframe` | 码率切换的切换点、丢包后重同步、接收端快速起播 |
| `pts` | **音视频同步的唯一依据**；抖动缓冲的排序键 |
| `send_ts_us` | **GCC 的时延梯度基准**（`arrival − send_ts` 取最小值做基线） |
| `seq` | 丢包统计（全局，不受帧边界影响） |

**开销**：28 B / (1200 + 28) = **2.3%**。对比 UDP/IP 的 28 B（20 IP + 8 UDP）——**同样的开销，但换来了 RTC 所需的全部信息**。

EtherType 分配：
- `0x88B5` 数据帧
- `0x88B6` 反馈帧
- `0x88B7` 控制帧（起播/停播/参数协商）

## 3. 反馈帧格式（0x88B6）

```c
struct rtc_fb {
    uint32_t magic;         /* 0x46424B31 "FBK1" */
    uint32_t fb_seq;        /* 反馈序号，接收端去重 */
    uint32_t window_us;     /* 统计窗口长度 */
    uint32_t recv_bytes;    /* 窗口内收到的负载字节 */
    uint32_t q_us;          /* **时延梯度 q(i)**，GCC 主输入 */
    uint16_t loss_permille; /* 窗口内丢包千分比 */
    uint16_t jitter_us;     /* 到达间隔抖动 P95 */
    uint32_t frames_ok;     /* 完整帧数 */
    uint32_t frames_lost;   /* 缺失帧数 */
    uint32_t max_frame_id;  /* 已收到的最大帧号 */
    uint16_t rsv;
};
```

周期 **50 ms**。发送端收到后去重（`fb_seq`），用最新的做决策。

**抗丢**：同一份内容连发 3 帧（不同 `fb_seq`），发送端按内容窗口去重。

## 4. 接收端 RTC 层设计

### 4.1 三段式处理

```
收包 ──▶ ①重组器 ──▶ ②抖动缓冲 ──▶ ③同步调度 ──▶ 解码/播放
         (按 frame_id)   (按 pts)      (共享播放钟)
              │
              └──▶ 统计器 ──▶ 反馈帧（50ms）
```

### 4.2 重组器

- 每个 `frame_id` 维护位图，记录已收 `chunk_idx`
- 收齐 → 标记 complete，释放给抖动缓冲
- 超时（默认 200 ms）→ 标记 lost，整帧丢弃（**不喂半帧给解码器**）
- FEC：同 `group_id` 的块收齐后尝试 XOR 恢复

**关键：按帧丢弃而非按块。** 现有实现是"缺块就 NACK"，但没有"这帧已经过期，别救了"的概念。

### 4.3 抖动缓冲

- 双流各自一个环形缓冲，按 `pts` 排序
- 深度自适应：

```
D_target = P95(到达间隔 - 发送间隔) × 2 + 20ms 安全余量
D_target 限制在 [30ms, 500ms]
每 500ms 更新一次，变化超过 20% 才调整（防震荡）
```

### 4.4 音视频同步

```
共享播放时钟 T0（接收端本地单调钟）

T_play(帧) = T0 + (pts - pts_base) / 90000 + D_target

音频为主时钟（不可拉伸）：
  - 音频按 T_play 直接播放
  - 视频按音频的实际播放进度微调
  - |ΔAV| > 40ms 持续 1s → 视频丢帧/插帧追赶

ΔAV 计量 = (视频实际播放时刻 - 音频实际播放时刻) - (pts_v - pts_a)/90000
```

**不需要 RTCP SR / NTP**：音频和视频由同一个发送进程、同一个时钟打 `pts`，天然同一时基。这是去掉 IP/UDP 后省掉的一整类机制。

## 5. 发送端 RTC 层设计

### 5.1 数据流

```
编码器产出 ──▶ 按帧切块 ──▶ FEC 编码 ──▶ 发送队列 ──▶ 按码率节奏发出
   (带 pts)      (1200B)      (自适应冗余)    (可丢弃)      (pacing)
                                                        │
   码率指令 ◀── GCC 控制器 ◀── 反馈帧 ◀───────────────────┘
```

### 5.2 码率执行方式（分两步）

| 步骤 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| **M5-a** | **预编码码率阶梯**：同一内容预编 2/4/8 Mbps 三档，在关键帧处切换 | 确定性好、控制器验证干净 | 不是真 ABR |
| **M5-b** | libx264 动态 `bitrate` | 真 ABR | 需接编码器 API |

**先做 M5-a**：用阶梯切换验证 GCC 控制器本身是否正确；控制器稳了再上真编码器。

### 5.3 发送节奏（pacing）

不能一口气把一帧的所有块发完（会瞬间打爆 AP 队列，制造假拥塞）。按目标码率匀速铺开：

```
gap = 块大小 / (target_bps / 8)     // 每块之间的间隔
```

这是 **GCC 能正常工作的前提**——不 pacing 的话，测到的时延全是自己造成的突发。

## 6. GCC 控制环设计

### 6.1 输入

| 输入 | 来源 | 说明 |
|---|---|---|
| `q(i)` 时延梯度 | 反馈帧 `q_us` | **主信号** |
| 丢包率 | 反馈帧 `loss_permille` | 辅助（>10% 时强制降） |
| 接收速率 | 反馈帧 `recv_bytes/window_us` | 实际吞吐 |
| 可选：MAC 队列时延 | 板子侧 354 埋点 | 阶段 2 接入 |

### 6.2 接收端如何算 q(i)

```c
d(i)   = arrival_ts(i) - send_ts_us(i);        // 含固定时钟偏移 Δ
d_min  = min(d) over 最近 2 秒滑动窗口;         // Δ + 传播 + 最小处理
q(i)   = d(i) - d_min;                          // 排队时延，Δ 自动抵消
```

**不需要两端时钟同步**——固定偏移在减法里消掉。残余误差只有晶振漂移（20 ppm 在 2 秒窗口内 < 40 μs，可忽略）。

### 6.3 控制律（GCC 同款）

```
每 50ms（收到一帧反馈）：

1. 趋势估计 m(i)：用滑动窗口线性拟合斜率
   （**不用 GCC 的卡尔曼**——它假设高斯噪声、为有线链路标定；
     MAC 队列时延是长尾突发结构，简单趋势线更稳。这是有意的偏离，需在报告中说明）

2. 过载检测（自适应阈值 γ，随时间缓慢增大以抗噪）：
     overuse  : m(i) >  γ
     underuse : m(i) < -γ
     normal   : 其它
     γ 初始 12.5ms，overuse 时 γ *= 0.85，其余 γ *= 1.05（上限 100ms）

3. 速率控制：
     overuse  : target *= (1 - 0.85 * df)          // df 为过载持续度
     underuse : target *= 1.05
     normal   : target += 0.5 * (expected - target) * dt / 1000

4. 钳制：
     target = min(target, 接收速率 * 1.5)          // 不超实际吞吐太多
     target = min(target, 链路容量估计)
     target = max(target, 300 kbps)                // 地板
     target 变化率限制：每 50ms 不超过 ±20%
```

### 6.4 与现有素材的衔接

上一轮合并进来的 354 补丁提供 `DEQ−ENQ`（MAC 队列时延）。**阶段 2** 把它作为第二路输入，用于区分"自致拥塞"与"信道竞争"。阶段 1 先只用端到端 `q(i)`，把闭环跑通。

## 7. 设备受限下的拓扑选择

### 7.1 约束

现有：**1 台 Windows PC + 1 块 BPI-R4**。真实双 STA 拓扑需要两台可编程无线终端。

### 7.2 阶段 1 采用：PC 双接口 + 板子中继

```
   PC(Wi-Fi)  ──STA1 上行──▶  板子 AP (phy0.1-ap0)
                                      │  桥转发 (br-lan)
                                      ▼
   PC(Ethernet) ◀──下行──  板子 eth1 / lan2
```

- 发送端和接收端都在 PC 上（同一进程或两个进程），**调试最快**
- 板子真正执行了桥转发，不是摆设
- 板子侧仍可旁路观测上行（`AF_PACKET` on `phy0.1-ap0`）

**明确的局限（必须记录在报告里）**：
- 下行是**有线**，没有无线下行拥塞 → 双跳归因实验做不了
- 不是"两个用户"

### 7.3 阶段 2 升级

补一台设备（USB Wi-Fi 网卡约 30 元，或第二台笔记本）→ 真正的双 STA 无线双跳，双跳归因实验才成立。

**阶段 1 的产出不会浪费**：RTC 层代码完全复用，只换部署位置。

    rtc_send.c          发送端主程序

**语言选择**：
- 阶段 1（PC 上）：核心用 C（可移植到板子），Python 只做离线分析与绘图

## 9. 实施步骤（每步有独立验收）

| 里程碑 | 内容 | 验收标准 | 预估 |
|---|---|---|---|
| **M1** | RTC2 头 + 封包/解析 + 单测 | 编解码往返一致；边界值正确；单测全绿 | 2 天 |
| **M2** | 重组器 + 帧完整性统计 | 注入乱序/丢块，重组正确率 100%；超时丢弃正确 | 2 天 |
| **M3** | 抖动缓冲（视频单流） | 8 Mbps 下 JB 深度自适应收敛；模拟抖动 ±30ms 不解码失败 | 3 天 |
| **M4** | 反馈通道 | 50 ms 周期稳定；故意丢 30% 反馈帧仍能工作 | 2 天 |
| **M5** | GCC 控制器 + 离线验证 | 用 M4 录的真实 q(i) 回放，码率曲线合理、无震荡 | 3 天 |
| **M6** | 码率执行（阶梯切换） | 拥塞注入后 ≤1 s 收敛；切换点在关键帧，无花屏 | 3 天 |
| **M7** | 音频接入 + 音视频同步 | **ΔAV ≤ 40 ms**；注入 ±1% 漂移后 2 s 内收敛 | 4 天 |
| **M8** | 端到端验收 + 报告 | 三场景数据；与 UDP/IP 基线对比 | 3 天 |

合计约 **22 个工作日**（4~5 周）。

**M1~M6 可以先只做视频**，M7 再加音频——避免音视频问题掩盖传输层问题。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| PC 侧用户态时间戳抖动 (±1ms) | q(i) 噪声偏大 | GCC 阈值 γ 初始设 12.5ms，噪声远小于阈值；阶段 2 移到板子用内核时间戳 |
| 阶梯切换造成画面跳变 | 观感差 | 严格在关键帧切换；切换前后 2 帧缓冲 |
| 下行是有线（阶段 1） | 无法验证双跳归因 | 明确写入局限；阶段 2 补设备 |
| 预编码文件非真实采集 | 说服力弱 | M8 时用 PC 摄像头真采集做一次演示 |
| 板子无线网卡做 AP 时的稳定性 | 影响长时间测试 | 已连续运行 16 h 稳定，104 模块在位 |
