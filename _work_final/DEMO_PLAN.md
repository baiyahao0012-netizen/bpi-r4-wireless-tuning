# 豆包加速录屏演示方案：Before 卡顿 / After 流畅

版本：v1.0 · 日期：2026-10-29
前置分析：[\`_work_final/OPTIMIZATION_ANALYSIS.md\`](<_work_final/OPTIMIZATION_ANALYSIS.md)
现场实测：手机 Redmi-K60 = \`06:65:45:fc:44:3d\` = \`192.168.240.219\`，5G 在线，信号 −29 dBm，tx 960 / rx 1200 Mbit/s

---

## 0. 结论（先看这一页）

**能不能录出"卡顿 vs 流畅"，只取决于三件事，缺一不可：**

| # | 条件 | 现状 | 结论 |
|---|---|---|---|
| 1 | 加速必须覆盖豆包**回答流本身** | EF 只覆盖下行 **16.8%** 字节，Top1/Top2 流命中为 0 | ❌ 不满足，after 也会卡 |
| 2 | 空口必须**过载**（队列持续积压） | HE80 + 1200 Mbit/s 链路，负载仅 280 Mbit/s | ❌ 不满足，before 也不卡 |
| 3 | 用**同一回答内切换**抵消服务端波动 | 未做 | ⏳ 待做（这是最有力的一段） |

**所以：直接拿现在的链路去录，大概率录不出差异。** 必须先做两件工程化的事——**把加速对象扩到 100%（设备级 VIP 或先补识别）**、**把 5G 压到过载（HE40/HE20 或强背景流）**——再录。

> 演示 ≠ 验收。录屏负责"直观可信"，30% 的量化验收仍要用随机化 A/B（见前文 §7）。两者分开做，不要用录屏替代数据。

## 1. 原理：为什么"卡顿"能被录出来

豆包文字回答是一条 **token 流**：小包、低速率（几十 kbit/s）、持续数秒到数十秒。
卡不卡，取决于 **最后一跳 WiFi 的排队时延**，而不是带宽：

\`\`\`text
BE 背景流灌满 AP 下行队列
   → 每个 token 包排在后面，排队 100 ms ~ 1 s
   → 文字"一顿一顿"（肉眼可见）

豆包包进 AC_VO（AIFS/CW 更小）
   → 插到 BE 前面，排队回到几十 ms
   → 文字连续流出（肉眼流畅）
\`\`\`

两个关键约束：

1. **App 有渲染缓冲**。只有排队时延 **远大于** 缓冲时，肉眼才看得到卡；所以必须把空口压到"过载 + 持续积压"，而不是"轻度拥塞"。
2. **只有被标记的包才进 VO**。豆包回答流如果没被识别/打标，after 组照样排在 BE 里 —— 这就是上一份分析里"机制通过、体验无改善"的根因。

## 2. 演示场景设计

### 2.1 选哪个豆包功能

| 功能 | 可见性 | 可控性 | 建议 |
|---|---|---|---|
| **长文字回答** | 高（token 逐个出现） | 高 | ✅ **首选** |
| 语音朗读 / 通话 | 最高（音频卡顿最直观） | 中 | ✅ 加分项，但录屏带音频受限 |
| 图片 / 视频生成 | 中 | 低（服务端耗时占主导，媒体走 VO 反而自我伤害） | ❌ 避免 |

### 2.2 固定题目（重复使用，避免上下文影响）

- 准备 2–3 道**长输出、稳定**的题，例如：
  - "详细讲解 TCP 拥塞控制，不少于 800 字。"
  - "写一篇关于……的说明文，不少于 800 字。"
- 每次**新开对话**；同一题在 A/B 两臂各用一次。

### 2.3 背景负载（造拥塞）

- **必须在同一 5G 射频上**（2.4G 的背景不会拖慢 5G 的豆包）。
- 主力：PC WLAN3 \`192.168.240.126\` 跑反向 iperf3（板端 server → PC 下行）。
- 单路约 400 Mbit/s，在 HE80 下**不足以过载**，二选一：
  - **降带宽**：5G 由 HE80 → **HE40 / HE20**（最可靠，直接砍容量）；
  - **叠流量**：PC 双网卡 + 第三台 STA 同时拉流，或加一路 UDP 洪泛把队列灌满。
- 目标：空口利用率 ≥80%，AP 下行队列**持续积压**（可用 \`/sys/kernel/debug/ieee80211/phy0/queues/\` 与 iperf3 时延观察）。

### 2.4 加速对象（覆盖率）—— 三选一

| 方案 | 做法 | 覆盖率 | 演示稳定性 | 说明 |
|---|---|---|---|---|
| **A. 设备级 VIP** | 手机 \`192.168.240.219\` 的下行整体 \`ip dscp set ef\`；PC 背景 BE | **100%** | ★★★ | **录屏推荐**；是"VIP 设备优先"，不是"仅豆包识别" |
| **B. 应用级识别** | 先扩 OAF 特征 + QUIC/IP 兜底，覆盖豆包回答流 ≥90% | ~90% | ★★ | 最贴合项目主题，但需先做流量测绘 |
| **C. 折中** | 豆包流 EF→VO；手机其余流 CS3→VI；PC BE | 100% | ★★☆ | 兼顾主题与稳定 |

> 建议：**录屏用 A（稳、差异大）**；报告里同时给出 B 的识别覆盖率与效果，讲清"识别→加速"的技术故事。

设备级 VIP 规则（\`postrouting\` 优先级 mangle，作用于下行）：

\`\`\`sh
nft delete table ip vip_demo 2>/dev/null
nft add table ip vip_demo
nft add chain ip vip_demo post '{ type filter hook postrouting priority mangle; }'
nft add rule ip vip_demo post ip daddr 192.168.240.219 counter ip dscp set ef
# 关闭： nft delete table ip vip_demo
\`\`\`

## 3. 录屏技术

### 3.1 adb 录屏

\`\`\`sh
# 单段最长 180 s，需要长回答时连录多段或中途重启
adb shell screenrecord --bit-rate 8000000 --size 720x1280 --time-limit 180 /sdcard/demo_A.mp4
adb pull /sdcard/demo_A.mp4
\`\`\`

- Android 10+ 可加 \`--audio\`（设备支持时）录系统声音，语音卡顿更直观。
- 手机当前**未连 adb**（\`adb devices\` 为空）；开录前先确认 \`109be14a  device\`。
- 备用：手机自带录屏（画质/音频更好，但需手动起停，时序控制差）。

### 3.2 录制环境固定（否则前后不可比）

- 固定手机位置（信号 −29 dBm 已很近，**不要移动**）；
- 关闭通知/自动亮度/其他后台同步；
- 关闭省电模式；手机温度正常（过热会降频，制造假卡顿）；
- 固定题目、固定对话、固定背景流参数；
- 录屏码率适中，避免录制本身拖累 CPU。

## 4. 三段式拍摄脚本

### Clip 1 — 基线（卡顿）
1. 5G 设为 HE40/HE20；手机连 5G，确认 IP \`.219\`。
2. 起背景流：\`iperf3 -c 192.168.240.1 -p 5201 -R -t 300\`（PC 侧）。
3. **确认加速 OFF**：\`nft list table ip vip_demo\`（应不存在）。
4. 开始录屏 → 新开对话 → 输入固定题 → 等待回答完整结束 → 停止录屏。
5. 取证：\`nft list table ip vip_demo\`（无）、PC 背景吞吐、板端 pcap。

### Clip 2 — 加速（流畅）
1. 背景流参数与 Clip 1 **完全一致**。
2. **加速 ON**：安装 \`vip_demo\` 规则，确认 counter 在增长。
3. 开始录屏 → 新开对话 → **同一题** → 等待结束 → 停止。
4. 取证：\`counter packets/bytes\`、pcap 中下行 EF 字节、背景吞吐。

### Clip 3 — 同一回答内切换（★ 最有力）
1. 背景流同上；**先 OFF**，开始录屏，提问，等文字开始流出。
2. 回答进行到约 1/3 时，**中途安装** \`vip_demo\` 规则（对已建立连接立即生效，因为 nft 匹配的是每包 \`ct mark\`/目的 IP）。
3. 继续录到回答结束。
4. 效果：**同一条回答**，切换点之后文字明显变快/变连续 —— 天然抵消服务端波动与题目差异，最有说服力。
5. 取证：切换时刻的 \`nft counter\` 前后对比。

> 提示：中途切换是 nft 层生效，**不需要断连、不需要重开对话**；但 App 渲染缓冲会让效果延迟几百 ms 出现，剪辑时保留这段。

## 5. 把"卡顿"量化成数字（视频分析）

本机 **没有 ffmpeg，但有 \`opencv-python 4.11\` + numpy**，可直接读 MP4：

\`\`\`text
读帧 → 裁出回答文本区域 → 逐帧像素差 → 判定"新文字出现"的时刻序列
     → 指标：最大停顿 / >300ms 停顿次数 / p95 间隔 / 回答总时长
\`\`\`

| 指标 | 含义 | 期望 |
|---|---|---|
| 最大停顿 (ms) | 最长一次文字不更新 | before 大、after 小 |
| >300 ms 停顿次数 | "一顿一顿"的直观计数 | before 明显更多 |
| p95 更新间隔 | 尾部卡顿 | after 显著下降 |
| 回答总时长 | 端到端体验 | after 更短 |

产物：**卡顿计数曲线**可叠加到视频上（画中画），让"卡"这件事变成可视数字，而不是主观感受。

## 7. 风险与兜底

| 风险 | 现象 | 兜底 |
|---|---|---|
| 覆盖不足 | after 也卡 | 用**设备级 VIP**（100% 覆盖） |
| 空口不过载 | before 也不卡 | 降到 **HE20** + 多路背景 + UDP 洪泛 |
| App 缓冲 | 网络抖动被抹平 | 加大拥塞强度；用长回答放大尾部事件 |
| 服务端波动 | 两次回答本身快慢不同 | **Clip 3 同一回答内切换**；重复多轮 |
| 录屏掉帧 | 画面本身卡 | 降码率/分辨率；确认录屏自身流畅 |
| 手机过热降频 | 假卡顿 | 控制时长、散热、冷却后重录 |
| 2.4G 自干扰 | 结果不稳 | 2.4G 实验前停 \`sta0\` |

## 8. 执行清单

1. **接上手机**：确认 \`adb devices\` 显示 \`109be14a device\`。
2. **选加速方案**：录屏用 A（设备级 VIP）；报告补 B（应用级识别）。
3. **造瓶颈**：5G → HE40/HE20；PC 反向 iperf3 起背景流；确认队列积压。
4. **Pilot（关键）**：先录 1 组 A/B 试片，跑第 5 节分析，**确认"最大停顿"或"停顿次数"前后差 ≥3× 再正式录**；差异不够就加大拥塞/换 VIP 方案。
5. **正式录 3 段**：Clip 1 基线、Clip 2 加速、Clip 3 同题切换。
6. **收证据**：nft counter、pcap、背景吞吐、卡顿曲线。
7. **恢复现场**：5G 回 HE80、删除 \`vip_demo\`、停背景流、手机回原输入法/网络。

> 一句话：**录屏成败在"覆盖 100% + 空口过载"这两件事；先把 Pilot 跑出来，别直接开机就录。**
