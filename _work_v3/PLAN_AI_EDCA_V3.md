### 1.2 数据不可信、必须重测或删除的部分

#### （1）5.3 的 TTFB 表 —— **指标定义是错的，必须废弃**

读完 `dashboard.py:52-93` 的实现，这个"TTFB"的真实定义是：

```
上行有负载包到达   → flow_up[五元组] = 时间戳      （每个上行包都覆盖）
下行有负载包到达   → pop 出时间戳，dt = 现在 - 上次上行时刻
```

也就是说它测的是**"最近一个上行包 → 下一个下行包"的间隔**，而不是首字节时间。它混杂了：TCP ACK 往返、应用请求-响应、重传、TCP 拥塞窗口节奏。**它不是 TTFB，也不是 RTT，是一个语义不明的包间隔。**

这直接解释了为什么会出现"P50 从 109 变差到 116、P90 却腰斩"这种反直觉结果——很可能只是包序列模式变了，跟用户感知无关。

**结论：5.3 整张表不能写进报告。** 而且它只跑了一次 60 s，n 未报告，没有置信区间。

#### （2）5.2 的 EDCA 延迟表 —— 自算的，而且算错了

文档写 VO 405.6 µs、VI 356.3 µs、BE 595.4 µs。**VI 比 VO 延迟还低**，这在 EDCA 语义上不可能（VI 的 AIFSN 和 CW 都比 VO 差）。说明公式把 TXOP 错当成了"接入延迟"，或者 AC 到内核枚举的映射算反了。

按 802.11 标准公式重算（5 GHz，slot=9 µs，SIFS=16 µs）：

```
平均接入时延 ≈ SIFS + AIFSN×slot + (CWmin/2)×slot
VO(2,3,7)  : 16 + 18 + 13.5 ≈ 47.5 µs
VI(2,7,15) : 16 + 18 + 31.5 ≈ 65.5 µs
BE(3,15,..): 16 + 27 + 67.5 ≈ 110.5 µs
```

**真实差距只有几十微秒/次接入**，不是 400 vs 600 µs。这个量级本身就是"为什么单 STA 场景看不出效果"的数学解释 —— 见第 2 节。

#### （3）5.4 / 5.5 的 6 Mbit/s 窄带实验 —— 不是正常手段，不能作为方案依据

`force_rate` 是 mt76 的 debugfs 调试开关，作用是把固件速率表钉死，本质是"把链路搞坏"，不是流量整形。它：

- 只有一档（写任何值都落到 6 M）；
- 断电才能复位，软重启无效 —— 这本身就说明它超出可控范围；
- 曾导致 PCIe FLR 卡死（文档 6.4 自己记了）。

拿它当"窄带演示"做出来的效果，答辩时一定会被问"这算加速还是算故意降速"。**建议从方案里降级为"历史尝试/踩坑记录"，不作为演示手段。**

#### （4）5.5 的"跨 STA 2 个不够" —— 与 5.4 自相矛盾

6 Mbit/s 下两路 TCP 拉 300 MB 文件，空口必然打满，RTT 不可能只有 12.5 ms。大概率当时 `force_rate` 没生效，或 `bgload` 没真正跑起来。**这条数据无效，不能用它否定"跨 STA 造压"路线。**

#### （5）"100 Mbit/s 空口 vs 2 Mbit/s 需求" 的归因

方向对，但漏了更关键的一层：**mac80211 的 AQL（airtime queue limit）会把每个 txq 的排队深度压得很浅**，加上 `fq_codel` 在 IP 层已经先排过一次队。队列排不起来 → AIFS/CW 的差异就没有可发挥的"排队时延"。这比"带宽富余"更接近根因。

### 1.3 概念性错误（比数据错误更要命）

| 文档说法 | 实际是什么 | 风险 |
|---|---|---|
| "EDCA 参数自主调优" | 只做了**一次静态下发**（VO 设成 1/1/3/94），没有任何观测-反馈-决策回路 | 答辩被问"自主体现在哪"会答不上来 |
| "对识别出的业务做 EDCA 调优（AC_VO 优先）" | 实际做的是**DSCP 分类 → 选队列**，属于 WMM 标准能力 | 会被质疑"这就是配了个 QoS，创新点在哪" |
| "硬件层实现" | EDCA 在 MAC 层由 mt7996 固件执行，参数由驱动经 nl80211 → MCU 命令下发 | "硬件层自主"不成立，应改为"驱动/固件层实时可编程" |
| "EDCA 让手机侧优先得到 AI 数据" | AP 侧参数**只影响 AP 自己的下行竞争**；STA 上行用它自己的参数 | "手机上传也变快"不成立 |
| "AC_VO 优先" | AI 视频塞进 VO 会挤掉真正的语音业务，且违反 WMM 语义 | 应该 VO 放控制面、VI 放数据面（见 3.3） |

## 2. 根因：为什么现在证明不了"EDCA 调优"

把 AP 下行的排队链路拆开，AI 业务的时延由五段构成：

```
应用生成
  → TCP 发送缓冲（应用层背压）
  → qdisc: fq_codel（IP 层排队，按流隔离）      ← ①
  → mac80211 txq（per-AC per-STA，AQL 限深）    ← ②
  → 硬件队列（mt7996 16 个队列，按 AC 选）       ← ③
  → 固件 EDCA 仲裁（AIFS/CW/TXOP 竞争空口）     ← ④
  → 空口传输
```

**关键认知：**

1. **① 和 ② 决定了 AI 包"排第几"**。只要 AI 包进了 VO/VI 队列，它天然排在 BE 前面 —— 这一步是 `cfg80211_classify8021d` + 队列调度完成的，**和 EDCA 参数无关**。这就是为什么现在"看起来有效果"：效果来自分类，不是调参。

2. **④ 只在"和别人抢空口"时才有意义**。单 STA、AP 是唯一发送者时，AP 几乎每次都能拿到信道，AIFS 差 9 µs、CW 差几 µs，对几百 ms 的端到端时延是噪声。

3. **② 的 AQL 是隐藏杀手**。AQL 会根据空口时延动态压低队列上限，单 STA 低负载时队列深度趋近于 0 —— 队列里压根没有积压，EDCA 当然"调了没感觉"。

**由此推出方案的两条铁律：**
- 要证明"调参"有额外价值，**必须有真实竞争**（其他 STA 或 ≥60% 空口利用率）；否则只能证明"分类有效"。
- 调参的抓手不该是 AIFS/CW（杠杆太小），而应该是 **TXOP（一次抢占能连发多久）** 和 **队列深度上限（AQL/txq limit）**（直接决定排队时延上界）。

## 3. 方案 V3

### 3.1 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│ L5 验证层   三组对照 / A-B-A / 置信区间 / 公平性约束           │
├──────────────────────────────────────────────────────────────┤
│ L4 闭环决策 采样 → 状态判定 → 档位选择 → 滞回 → 下发           │  ← "自主"在这里
├──────────────────────────────────────────────────────────────┤
│ L3 参数面   TXOP / AIFS / CW / AQL-limit / txq-limit           │
├──────────────────────────────────────────────────────────────┤
│ L2 分档    控制面→VO  媒体面→VI  背景→BE/BK（业务内分流）      │
├──────────────────────────────────────────────────────────────┤
│ L1 识别    OAF 特征匹配 → 直接写 skb->priority（不经 nft）      │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 L1 识别层改造

**现状问题：**
- 依赖 nft 规则存在才有 DSCP，nft 表一删就断链；
- 多特征规则会互相覆盖 ct mark 低 16 位；
- QUIC（UDP 443）没有传统 SNI 字段，豆包视频可能走 QUIC；
- 视频媒体 UDP 9924 识别不稳定（文档 6.2 自己承认）。

**改造点：**

1. **打标下沉内核**：OAF 命中后直接 `skb->priority = 256 + N`（N 为 802.1D 优先级，如 6=VO、5=VI）。mac80211 的 `classify8021d` 对 256–263 有特殊处理，会直接取 `priority-256` 作为 802.1D 值 —— 这条路 `_work_final/ac_mix_result.md` 已验证可行。**好处：少一跳、不依赖 nft、识别即分类。**

2. **QUIC 识别**：解析 QUIC Initial 包里的 TLS ClientHello SNI。若 OAF 不支持，退化为"UDP/443 + 目标 IP 段 + 包长节奏"指纹。

3. **媒体流兜底**：无 SNI 的媒体流用 `设备 + 端口 + 双向包长分布` 三元指纹识别，并设置**置信度**；低置信度只进 VI，不进 VO。

4. **与设备绑定**：mark 规则带 `skb->dev == phy0.1-ap0` 条件，避免影响本机（uhttpd/ssh）流量。

### 3.3 L2 分档：业务内分流（核心创新点之一）

把"AI 业务"拆成两类，而不是一股脑塞 VO：

| 子类 | 特征 | 目标 AC | 理由 |
|---|---|---|---|
| 交互控制面 | 小包（<300 B）、突发、与用户操作强相关 | **AC_VO** | 包小、对时延极敏感，VO 的短 TXOP 正合适 |
| 媒体数据面 | 大包、持续、码率 0.5–2 Mbit/s | **AC_VI** | 视频语义，避免挤占语音的 VO 队列 |
| 背景/其他 | 其余 | AC_BE / AC_BK | 兜底 |

**为什么这是创新点：** 现有商用 AP 的 QoS 是"按应用整条流打标"，本项目是**按业务内部角色分流**——同一 App 的控制信令和数据帧走不同 AC。这在答辩上是一个清晰、可验证、有对比组的贡献点。

### 3.4 L3 参数面：哪些旋钮真有用

| 旋钮 | 影响 | 结论 |
|---|---|---|
| AIFSN | 每次接入等的时隙数 | **杠杆小**（µs 级）。只在多 STA 竞争时有效，如实写明 |
| CWmin/CWmax | 退避窗口 | 同上；单 STA 时几乎无影响 |
| **TXOP** | 一次抢占能连续发多久 | **杠杆最大**。决定"AI 包能插到多前面"，也决定 BE 大包被切多碎 |
| **AQL limit** | txq 排队深度上限 | **决定排队时延上界**。深度大→时延高但吞吐稳；深度小→时延低但易空口浪费 |
| **txq limit** | 硬件队列长度 | 同上，作用于固件侧 |
| fq_codel 是否启用 | IP 层二次排队 | 需实测：若 wlan 上 fq_codel 在排队，AC 差异被抹平，应改为 `noqueue` 或调 `quantum` |

**建议的参数档位（三档，带滞回）：**

```
保守档（U < 0.5）：全部默认值，不折腾
平衡档（0.5 ≤ U < 0.75）：VO txop=47, VI txop=94, AQL 默认
激进档（U ≥ 0.75）：VO txop=94, VI txop=188, AQL limit ×1.5, BE CWmin 上调
```

### 3.5 L4 闭环控制器（"自主"的落点）

**采样（200 ms）：**
- `U`：空口利用率（从 mt76 debugfs / `iw` 的 tx busy 或 `/proc/net/...` 估）
- `Q_vo` / `Q_vi`：各 AC 的 txq 深度（`nl80211` TXQ stats 或 debugfs）
- `L_ai`：AI 业务时延滑窗 P95（20 s 窗口，指标定义见 4.1）
- `R_retry`：重传率

**决策（带 10 s 滞回，避免抖动）：**

```
if U < 0.5:                       档位 = 保守
elif L_ai > target × 1.2:         档位 = 上调一档（若已在激进档则不动）
elif L_ai < target × 0.7 and R_retry < 5%:  档位 = 下调一档
else:                             保持
if 其他 STA 吞吐下降 > 20%:        回退一档（公平性护栏）
```

**为什么用离散档位而不是 PID：** EDCA 参数是整数量且硬件生效有 0.1–0.3 s 延迟，连续调节会震荡。离散档位 + 滞回是工程上更稳的选择，也更容易在报告里说清楚。

## 4. 验证方法学（这一段决定项目成败）

### 4.1 指标重建

| 指标 | 定义 | 采集方式 |
|---|---|---|
| **AI 时延** | 应用层请求包 → 首个响应负载包（TCP 用"首个上行 push → 首个下行 push"，UDP 用"请求 → 首包"） | 板端 tcpdump，按五元组配对，**必须报告配对成功率** |
| AI 时延分位 | P50 / P90 / P99 + 样本数 n | 滑窗 + 全量统计 |
| 视频卡顿代理 | 下行包间隔 > 200 ms 的次数/分钟 | pcap 流级分析 |
| 系统 RTT | 板 → 手机 ping | 已有 |
| **公平性** | 其他 STA 的总吞吐下降比例 | iperf3 并发 |
| 空口利用率 | U | debugfs |

> **关键修正：** 现在的 dashboard 把"上行包→下行包"当 TTFB，必须改。改成"首个上行 push → 首个下行 push"仍受 TLS 加密限制，需要在报告里明确标注"这是代理指标"，并同时给出 RTT 作为交叉验证。

### 4.2 三组对照（缺一不可）

| 组 | 配置 | 目的 |
|---|---|---|
| A 基线 | 不打标、不调参 | 参照 |
| B 仅分类 | 打 DSCP EF，EDCA 保持默认 | 证明"分类"贡献 |
| C 分类+调参 | DSCP EF + 闭环调 EDCA | 证明"调参"增量 |
| D 反事实 | 只调参不打标 | 排除"调参本身让所有流量变快"的假象 |

只有 **C 显著优于 B**，才能说"EDCA 调参"有效。否则结论应写成"分类已足够，调参无增量"——这同样是有价值的结论，而且更诚实。

### 4.3 实验协议

- 每段 60 s，**A/B/A 交替**，重复 **5 轮**，随机化顺序；
- 同一台手机、同一位置、同一信道、固定 `txpower`；
- 报告 **均值 ± 95% 置信区间**，不报单次值；
- 造压：`udpflood.py` 同 STA 把空口打到 **75–85% 利用率**（不是 100%，否则全崩）；另一路 iperf3 从 PC 拉流作为"公平性受害者"；
- 每个场景留 CSV + 配置快照。

### 4.4 必须画出来的一张图

**横轴：空口利用率 U（30% → 90%）；纵轴：AI 时延改善率（C 相对 B）。** 这张图能直接回答"EDCA 什么时候有用"，比任何单点数据都有说服力。

## 6. 风险与止损

| 风险 | 概率 | 止损 |
|---|---|---|
| 单 STA 场景闭环收益 < 5% | 高 | 结论改为"低负载无效、高负载有效"，给出阈值曲线 |
| AQL 无法从用户态调 | 中 | 退到 txq limit 或驱动 patch（已有 `mt7996e-*.ko` 编译链） |
| 造压时手机被挤到断连 | 中 | 限速 75–85%，不做 100% |
| 答辩质疑"这是 WMM 标准功能" | 高 | 用 3.3 的业务内分流 + 3.5 的闭环 + 4.2 的四组对照回应 |

## 9. 与 V2 的关系

本方案**不推翻** V2 的技术栈（OAF / edca_set / 看板 / 抓包链都保留），只做三件事：

1. **拆掉不可信的证明**（5.3 TTFB 表、5.2 延迟表、6M 演示）；
2. **补上缺的那一层**（闭环控制 + 业务内分流）；
3. **重做验证方法学**（四组对照 + 重复 + CI + 公平性）。

V2 里最值钱的一句是 section 1 的"EDCA 收益只体现在时延尾部"——这句话是对的，但它需要把"尾部"的定义从"错误的 TTFB 指标"换成"**空口利用率 ≥75% 时的 P95/P99 时延**"，才有说服力。
